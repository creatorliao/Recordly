# 04 · 方案方向：按次启动的会话日志

> 匹配 `01` 的尺子与 `03` 的断点。**不过度设计**：本机文件 + 结构化一行一事。不上云、不引入 Sentry / OpenTelemetry。  
> 未获「开始做」前不改产品代码。

## 1. 目标与六问

| 问 | 答 |
|----|----|
| 服务哪个 G | G1（出问题能对上阶段）、G4（文件即可） |
| 不过度设计？ | 一个主进程模块 + 渲染桥 + 包一层 UI 错误；不换引擎 |
| 回归？ | 日志失败不得打断录制/导出（写盘失败只降级） |
| 用户真需要？ | 要，否则卡顿类问题无法运营 |
| 会困惑吗？ | 默认不改操作；可选「打开日志文件夹」 |
| 奇怪影响？ | 注意 Portable 路径可写、不要把日志打进只读安装目录 |

闸门可通过。实施时应控制在低风险增量（先骨架，再挂 UI 错误，再补金路径事件）。

## 2. 不采用什么

| 不做 | 原因 |
|------|------|
| 默认按天滚动的 `main.log`（electron-log 默认） | 违反「一次启动一份、别让智能体翻长文件」 |
| Sentry / 遥测上报 | 内网培训机、隐私、G4 |
| OpenTelemetry 全栈 | 无后端、无指标平台，过重 |
| 把所有 `console.log` 原样灌进文件且不分级 | 文件仍会爆；PERF 调试噪声要降级或默认关掉 |
| 为了日志改录→停→编→导步骤 | 原则 7 |

可采用 `electron-log` 当写文件后端，但**必须自定义文件名**：每次 `app.whenReady` 开新文件，而不是库默认的按日追加。更小的做法：自写 ~100 行 `sessionLogger`（`createWriteStream` + JSONL），零新依赖，更贴尺子。

**推荐：自写会话日志模块**（不新增依赖）。Windows-only 范围内足够。

## 3. 文件契约（智能体友好）

### 3.1 目录与文件名

```
<userData>/logs/recordly-YYYYMMDD-HHmmss-pid<pid>.log
```

- `userData` 已有（开发态 `Recordly-dev`，见 `appPaths.ts`）；Portable 若以后改 `userData`，日志跟着走。
- 文件名同时带墙钟和 pid，两次连开也不会撞车。
- 同目录放一份 `latest.log` **或** `latest.json` 指针（只含绝对路径 + 启动时间），方便「打开最新一次」而不复制整份内容。

启动头（文件第一行，固定字段）必须能单独回答：

- `appVersion`、`electron`、`os.release`
- `userData`、`recordingsDir`、本次 `logPath`
- `isPackaged`、命令行（脱敏）
- 启动 `sessionId`（UUID，后面每行带上）

### 3.2 一行一事：JSONL

每一行一个 JSON 对象，UTF-8，便于 Read 后按 `ts` / `level` / `event` 滤。禁止打成无限宽的 pretty JSON 数组（中途崩溃会坏文件）。

建议字段：

```json
{
  "ts": "2026-09-06T10:11:12.345+08:00",
  "level": "info",
  "scope": "recording",
  "event": "capture.start",
  "sessionId": "...",
  "corr": { "recordingId": "...", "exportId": "..." },
  "msg": "native windows capture started",
  "data": { "backend": "wgc", "sourceKind": "window" }
}
```

`level`：`debug` | `info` | `warn` | `error`。  
默认写入 `info+`；`PERF:*` 与逐帧日志默认不写，除非环境变量 `RECORDLY_LOG_DEBUG=1`。

单文件软上限：例如 8 MiB 或 2 万行后停止追加并打一行 `event=log.truncated`（仍不另开第二文件，避免一次启动两份对不上）。超大原因应是误开 debug，而不是正常金路径。

保留：启动时删除超过 **20** 份的旧 `recordly-*.log`（按文件名时间排序）。不删成片旁边的 `*.recording-diagnostics.json`（那是另一主题的证据，跟录像走）。

## 4. 谁写、怎么写

### 4.1 主进程（真源）

`electron/sessionLog.ts`（名称可调）：

1. `app.whenReady` 最早创建文件、写启动头。
2. 包一层 `log.info/warn/error`。
3. **挂钩** `console.warn` / `console.error`（以及可选 `console.log`→debug），保证存量 `console.error` 在未改完调用点前已经入档。
4. `process.on("uncaughtException")` / `unhandledRejection`：先写盘再按现有策略决定是否退出。
5. `app.on("render-process-gone")`、`child-process-gone`：error 级。
6. 退出时 `end` 流，写 `event=app.exit`。

写盘失败：只尝试打一次 stderr，**绝不**因日志打断录制。

### 4.2 渲染进程

preload 暴露：

```ts
electronAPI.log.write({ level, scope, event, msg, data })
```

实现：IPC 丢给主进程同一条流（主进程校验 level/字段长度，防止渲染进程灌爆）。

为少改业务文件：

1. **错误 UI 收口**（优先）：  
   - 包 `toast.error` 的薄封装 `notifyError`：先 `log.write(level=error, event=ui.toast)` 再 toast。  
   - `alert` 金路径 7 处改为同一封装（Windows 上至少覆盖「开始录制失败 / 未选源 / 音频权限」）。  
   - `project.setError` 时写 `event=ui.page-error`。  
   - 主进程 `dialog.showMessageBox` 在 `type` 为 warning/error 时先 `log.warn/error`。
2. 存量 `console.error`：主进程若再监听 `webContents` 的 `console-message`，打包后也能收；注意去重（同一条不要 toast + console + ipc 写三遍）。约定：**UI 错误只走 notifyError**；`console-message` 仅收 `error` 级别且带去重窗口。

### 4.3 金路径生命周期（运营真正要用的）

这些必须是**一等事件**，不能只靠偶然的 console：

| event | 何时 |
|-------|------|
| `app.start` | 启动头 |
| `recording.select-source` | 选定源（种类、是否窗口） |
| `recording.start` / `recording.start-failed` | 开始；失败带错误码与用户可见文案 |
| `recording.stop` / `recording.finalize-failed` | 停止、合成失败 |
| `capture.backend` | WGC / FFmpeg / 回退原因 |
| `cursor.monitor-start` / `cursor.monitor-failed` | 对上「鼠标没跟上」 |
| `mux.start` / `mux.complete` / `mux.error` | 与现有 diagnostics 相位对齐 |
| `editor.open` / `editor.load-failed` | 进编辑器 |
| `export.start` / `export.complete` / `export.failed` | 导出 |
| `captions.generate-failed` | 字幕 |
| `ui.toast` / `ui.alert` / `ui.dialog` / `ui.page-error` | 所有用户可见错误 |
| `app.exit` | 正常退出 |

`corr.recordingId`：一次录制从 start 到 mux 共用；导出用 `exportId`。智能体按 corr 滤，不必读导出噪声。

现有 `writeRecordingDiagnosticsSnapshot` **保留**（成片旁证据）。会话日志只记相位摘要 + 路径，不把 12KB `processOutput` 再抄一遍。

## 5. 资源消耗（一等能力，对上 `R20260906-12`）

用户点名：日志里必须能看出**相关资源消耗**。没有数字就无法解释「为什么整机卡住」。  
这不是第二期点缀，**和金路径生命周期一起做**（可与 §7 第 1–3 步同一批，但资源快照必须出现）。

### 5.1 何时写

| 时机 | event | 间隔 |
|------|-------|------|
| 启动头 | `app.start` 内带一份基线 | 一次 |
| 相位切换 | `resource.snapshot`（`phase` = recording / mux / editor / export / captions / idle） | 立刻 |
| 录 / mux / 导出 / 字幕进行中 | 同上 | **每 5s** |
| 空闲 | 同上 | **每 30s**（用来证明「没在录也高」） |
| 退出 | `app.exit` 带末次快照 | 一次 |

写失败降级，不打断录制。采样器只在主进程：`setTimeout` 漂移补偿即可，不要新依赖、不要性能平台。

### 5.2 每条快照最少字段

用 Electron/Node 现成 API，不装监控探针：

```json
{
  "event": "resource.snapshot",
  "phase": "recording",
  "data": {
    "mem": {
      "appRssMb": 0,
      "appHeapUsedMb": 0,
      "systemFreeMb": 0,
      "systemTotalMb": 0
    },
    "cpu": {
      "appPercent": null,
      "systemLoad1": null
    },
    "processes": [
      { "type": "Browser", "pid": 1, "cpu": 0, "memMb": 0 },
      { "name": "wgc-capture.exe", "pid": 2, "memMb": 0 }
    ],
    "capture": {
      "backend": "wgc",
      "width": 1920,
      "height": 1080,
      "fps": 60,
      "bitrateBps": 18000000
    }
  }
}
```

| 来源 | 用途 |
|------|------|
| `process.memoryUsage()` | 主进程 RSS / heap |
| `os.totalmem()` / `os.freemem()` | 整机内存是否见底 |
| `app.getAppMetrics()` | Chromium 各 type（Browser / GPU / Tab）CPU、内存 |
| 已知子进程 pid（wgc / cursor-monitor / ffmpeg / whisper） | 对上「哪个 exe 在吃」 |
| 当前相位上下文 | 宽高、fps、码率、导出后端（有就写，没有写 null） |

不做：默认每秒打、不跑 `nvidia-smi` 循环、不上 OpenTelemetry。  
可选（有则写，没有跳过）：启动头用一次 WMI/`os.cpus().length` 记下逻辑核数、总内存；GPU 名能廉价拿到再写。

### 5.3 卡顿 / 鼠标仍要的业务字段

事件里继续写：

- 采集后端、源类型、目标路径
- 光标 helper 是否起来、失败原因
- mux 前后探测时长（已有函数，抄摘要即可）
- 导出路径（浏览器预览 vs 原生 GPU）

再往后（仍属本主题，另开执行条）：`capture.health`（dropped frames）、光标采样间隙超阈 `cursor.gap`。没有这些，`R20260906-09` 仍要靠人眼；有了资源快照至少能分开「机器打满」和「导出失败」。

## 6. 人怎么拿到文件

设置页或帮助菜单加一项「打开日志文件夹」（`shell.openPath(logsDir)`），不进金路径默认点击流。  
手册（`R20260906-01`）在「开始做」且改了入口后再补一句：出问题把 `logs` 里**最新那一份**发给支持/智能体。

## 7. 建议实施顺序（等「开始做」）

1. 主进程会话文件 + 挂钩 console.error/warn + 崩溃事件 + 保留 20 份。  
2. preload IPC + `notifyError` 收口 toast/alert/setError/dialog。  
3. 金路径生命周期事件（录/停/mux/导）。  
4. **资源快照**（§5：相位切换 + 5s/30s；`getAppMetrics` + 子进程）。  
5. 测试：启动产生新文件、错误弹框有对应 JSONL、录制中出现 `resource.snapshot`、第二次启动不追加第一份。  
6. 使用指南补「如何交日志」。

单步都应远小于 500 行。不把 PERF 全量搬进文件。

## 8. 对工作流

默认不改变培训师操作。新增的只是后台文件 + 可选打开文件夹。  
与 `R20260906-09` 的关系：本方案是**排障前提**，不是卡顿修复本身。  
与 `R20260906-12` 的关系：资源快照写在本主题；**降默认采集档 / 限核**写在 12，不要把优化改回本夹当「只加日志」。
