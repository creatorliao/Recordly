# P03-得失分析_字幕链路复盘与VOC

## 一、分析背景

### 1.1 场景还原摘要

- **背景**：用户要对一条 53.3MB / 720×1280 / 314.047s 竖屏口播 MP4 完成「识别字幕 → 优化字幕 → 烧录字幕」，并要求用全部 5 个模板各出一版做效果对比。
- **主要过程**：转写 163 条字幕（命中缓存 0.56s）→ 10 处 ASR 误识定点纠正 → 发现源片**自带中英双语硬字幕**（y=976..1086）与 B 站台标（x=348..690）→ 5 个版本迭代出遮罩底片 → 烧录 5 个模板 → 生成对比图。
- **关键结果**：5 个成片**全部 8/8 通过校验**；优化后时间轴**四项硬门全绿**；字面金钱成本为 **0**（全程本机离线）。过程侧代价：遮罩渲染经 5 版、字幕烧录经 2 轮完整重跑、字幕带与台标坐标各量偏 2 次。

### 1.2 分析目标

- **重点分析**：为什么一次「设备就绪、模型已装、CLI 全在」的顺利任务，仍然付出大量探索开销？以及硬字幕/台标处理为何能做到，可复用边界在哪。
- **期望获得**：一条不含试错分支的确定性路径，和一份可回写 `subtitle-burn-master` 的需求。

## 二、做得好的（Keep）

### 2.1 关键成功要素

| 成功要素 | 具体表现 | 重要程度 |
|:---|:---|:---|
| **主动做源片洁净度检查** | 烧录前跑 `check-source`，检出「疑似自带硬字幕（high 置信）」并抽帧目视确认，推翻了「ROO 只是字幕错字」的需求前提 | **高** |
| **局部模糊替代色块** | 台标处理从 `drawbox@0.85` 半透明色块改为 `crop`+`boxblur`+`overlay`，消除字影与方形痕 | **高** |
| **时间门控遮罩** | 用 `overlay=…:enable='not(between(t,0.5,5.0)+…)'` 让台标模糊在英文内容条出现的 4 个窗口内自动关闭 | **高** |
| **基线副本 + 硬校验** | 先复制 `红杉_baseline.srt`，改完用 `verify` 证明时间轴未动（四项硬门全绿，`textChangedCueCount=10`） | **高** |
| **逐条校验替换唯一性** | 每处纠错先查命中数，`==1` 才替换；跨条匹配失败后立即缩小匹配串 | 中 |
| **plan 预判 + 并行烧录** | 5 模板先批量 `plan` 校验版面，再并行 `run`；并额外发现「文档声明 `max_lines=2` 但实渲 3–4 行」 | 中 |
| **环境与模型零安装** | 三 CLI 全在 `~/.local/bin`，`large-v3-turbo-q5_0` 已装，规避了懒装与大文件下载 | 中 |

### 2.2 可复用经验

**经验1：源片前置洁净度三件套**

- **做法**：`subtitle-burn check-source` 拿候选条带 → 全片梯度扫描（`fps=2` + `numpy` 纵向梯度 `>60` 且该行强梯度像素 `>90`）拿精确极值 → `ffmpeg -ss` 抽帧目视确认。三步顺序不能颠倒。
- **效果**：本次量出旧字幕 y=976..1086（p1=976，稳定收敛）、台标 x=348..690。**避免了「两层字幕叠加」这类 ffmpeg 不报错的隐性事故**。
- **适用条件**：任何「往已有视频上烧字幕」的任务。
- **不适用场景**：源片本身是干净的、或允许直接换素材时（此时检查是冗余）。

**经验2：画面缺陷的「局部模糊 + 时间门控」组合**

- **做法**：`split` 出两路 → 对目标区域 `crop` 后 `boxblur` → `overlay` 回原位；若该区域与动态画面元素冲突，用 `enable='not(between(t,…)+…)'` 做时间门控。
- **效果**：台标在正常时段完全读不出，且内容条出现时文字完整保留。
- **适用条件**：固定位置的台标/水印/角标；背景有纹理时尤其优于纯色块。
- **不适用场景**：目标沿画面移动（固定 crop 跟不上）；目标与必须保留的内容**空间重叠**（本次英文内容条右端 x≈450 与台标左端 x=348 真实重叠，只能二选一）。

**经验3：改动类操作先立基线、后用机器验证**

- **做法**：编辑前 `Copy-Item` 一份 baseline；编辑后跑 `verify <baseline> <new> --json`，要求四项硬门全绿并核对 `textChangedCueCount` 与自己的编辑数一致。
- **效果**：把「我没动时间线」从口头承诺变成可复核报告。本次正是靠它抓出 BOM 丢失。
- **适用条件**：任何「只允许改一部分、其余必须不动」的编辑任务。
- **不适用场景**：整体重写类任务，无「保持不变」的部分。

### 2.3 最佳实践提炼

**成功公式**：

> 可交付的成片 = 前置洁净度检查 × 精确区域测量 × 门控式画面处理 × 时间轴可验证 × 版面预判

**操作流程**：

1. **前置探测合并成一次**：环境 + 规格 + 洁净度 + 台标，一次拿全。本次把洁净度检查留到烧录前，代价是后面 5 轮返工。
2. **区域靠扫不靠看**：坐标用全片扫描或放大读刻度得到，不靠目测估算。本次目测错了四次。
3. **画面层一次做到位再往下走**：遮罩定稿前不烧字幕。本次先烧了字幕，才发现内容条被切坏，导致遮罩重做后字幕必须重烧。
4. **改文字必留证**：baseline 加 verify，`textChangedCueCount` 必须等于自己的编辑数。
5. **烧录前先 plan**：批量 plan 能提前暴露字号、行数、与遮罩带的冲突。
6. **多模板并行**：用 `hstack` 拼同一时间点的横向对比，一轮就能看出全部差异。

## 三、做得不好的（Improve）

### 3.1 问题识别

| 问题 | 具体表现 | 影响程度 |
|:---|:---|:---|
| **前置检查缺位** | `ffprobe` 只看了规格，未同时做 `check-source`；直到准备烧录才发现源片自带硬字幕 | **高** |
| **坐标靠目测而非测量** | 字幕带量偏 2 次（只量单行，未考虑单双行浮动）；台标量偏 2 次（估算 x≈548，实测 x=348） | **高** |
| **画面层未定型就烧字幕** | 先烧字幕 → 发现内容条被切坏 → 遮罩重做 → 字幕重烧，2 轮完整重跑 | **高** |
| **遮罩方案试错偏多** | 5 个版本：色块→模糊、范围错、`boxblur` 色度半径被拒、切坏内容条、加时间门控 | 中 |
| **写盘编码细节踩坑** | 用 `UTF8Encoding($false)` 写盘丢掉 BOM，`verify` 直接判红 | 中 |
| **可视化验证的交互轮次偏多** | 同一区域反复抽帧目视（含裁切窗口起太高只截到一行） | 中 |
| **「更省钱」目标未对齐现实** | 本次 API 成本本就是 0，字面无可省空间；真实可省的是算力时间与人工轮次 | 中 |

### 3.2 根因分析

**问题1：前置检查缺位**

- **表面原因**：探测源片时只跑了 `ffprobe`，`check-source` 是烧录前才顺手做的。
- **深层原因**：把「源片是否干净」当成了**烧录阶段的细节**，而不是**任务的输入前提**。实际上它决定整条路径的形态——源片自带硬字幕，就要多一个画面层，而画面层的存在会反过来约束字幕位置与模板选择。这个信息必须在最前面拿到。
- **问题类型**：执行问题。
- **分析依据**：`check-source` 输出 `existing_subtitles: true` / `confidence: high`，且用户最初的对策（「水印只在字幕文字里，不动画面」）被这条检查直接推翻。据 [P02 §2.3]。

**问题2：坐标靠目测**

- **表面原因**：抽帧放大后靠读图估坐标。
- **深层原因**：低估了硬字幕的**位置浮动**——单行与双行时字幕块位置不同（实测顶部 976 vs 1000），只量一个时间点必然偏。台标则是估了左边界却没验证。**逐帧扫描一次就能拿全，成本比两次目视还低。**
- **问题类型**：执行问题。
- **分析依据**：全片 628 帧扫描得 p1=976、中位底 1068、p99=1085，而目视两次分别得出「y≈955 起」与「y=1000..1110」。据 [P02 §2.4]。

**问题3：画面层未定型就烧字幕**

- **表面原因**：遮罩看起来「达标」后就往下走，把字幕烧了。
- **深层原因**：**验收样本只覆盖了正常时段，没覆盖冲突时段。** 台标遮罩在 30s/120s 都正常，但英文内容条只出现在 4 个窗口，第一次烧完字幕抽到 3.5s 那张帧才暴露。缺的是「按要素出现窗口去验收」，不是缺检查。
- **问题类型**：执行问题。
- **分析依据**：`final_3.jpg` 显示 `Building Moats Across the Merchan…` 被切断；修复方式是加 `enable` 时间门控。据 [P02 §2.5]。

### 3.3 关键影响因素

| 排序 | 因素 | 影响方向 | 可控程度 |
|:---|:---|:---|:---|
| 1 | 是否在任务最前面做源片洁净度检查 | 负向（缺位时引发后续全部返工） | **高** |
| 2 | 区域坐标的获取方式（扫描 vs 目测） | 负向 | **高** |
| 3 | 画面层与文字层的先后顺序 | 负向（顺序错则必须重跑） | **高** |
| 4 | 是否使用 baseline + verify | 正向（本次抓出 BOM 问题） | 高 |
| 5 | 多模板是否并行 | 正向 | 高 |
| 6 | 源片语速（342.5 字/分） | 负向（不可控，导致 19 条提示） | 低 |
| 7 | 英文内容条与台标的空间重叠 | 负向（物理冲突，只能二选一） | 低 |

## 四、深度分析

### 4.1 五层阶梯分析

**分析议题**：为什么一次环境完备的顺利任务，仍要付出约 8 项返工？

| 层级 | 分析内容 |
|:---|:---|
| **第一层：现象** | 遮罩渲染 5 版、字幕烧录 2 轮重跑、坐标量偏 4 次、写盘编码 1 次、跨条替换 1 次 |
| **第二层：直接原因** | 源片自带硬字幕与台标这一事实发现得太晚；区域坐标没有一次测准；遮罩未定型就向下游推进 |
| **第三层：关联因素** | 单个 CLI 都只声明自己的职责边界（`check-source` 只在 burn 技能里，转写技能不管画面），没有任何一个入口提示「你应该先检查源片」 |
| **第四层：关键因素** | **缺少一个任务级的前置检查闸门**。三个技能各自正确，但链路没有共同的「输入体检」环节，导致本该在 t=0 暴露的信息在 t=中段才暴露 |
| **第五层：隐藏假设** | 隐含假设「源片是干净的、可直接叠加字幕」。这个假设在多数素材上成立，所以平时不检查也不会出事——**直到遇到一条自有硬字幕的素材，代价一次性结清** |

### 4.2 关键假设识别

| 假设 | 当时是否成立 | 现在是否成立 | 启示 |
|:---|:---:|:---:|:---|
| 「源片无硬字幕，可直接烧录」 | ❌ 不成立 | ❌ 不成立 | 供应链素材（B 站、抖音、剪映导出）常自带硬字幕，必须前置检测 |
| 「ROO 水印是 ASR 错字，只在字幕文字里」 | ❌ 不成立（用户初始假设） | ❌ 不成立 | 实测为画面台标。**需求前提也需要实测校验** |
| 「目测足够定坐标」 | ❌ 不成立 | ❌ 不成立 | 硬字幕单双行位置浮动，台标边界易估偏 |
| 「遮罩一次就能做对」 | ❌ 不成立 | ➖ | 色块、范围、半径、内容条冲突，四类问题要逐个排除 |
| 「API 成本是可变成本，可以更省」 | ➖ | ❌ 不成立 | 本链全离线，金钱成本固定为 0；优化应指向算力时间与人工轮次 |
| 「同一素材重跑转写要 17 分钟」 | ❌ 不成立 | ❌ 不成立 | 缓存命中后 0.56s。缓存是这条链路最大的时间红利 |

### 4.3 适用边界

- **适用场景**：往**已有视频**上叠加字幕、水印处理、角标清除等「在不改变原内容前提下做局部修改」的任务。
- **不适用场景**：
  - 源片本身干净（前置检查是冗余开销）；
  - 需要移动式水印跟踪（固定 crop 跟不上）；
  - 目标区域与必须保留的内容物理重叠（本次台标 x=348 与内容条文字右端 x≈450 重叠，只能二选一）。
- **前提条件**：本机有 `ffmpeg`（含 `ass` 滤镜）、`numpy`（扫描脚本）、以及可用的真 Python（本次发现 `WindowsApps` 下的 `python.exe` 是占位符，需用 `AppData\Local\Programs\Python\Python312\python.exe`）。

## 五、行动建议

### 5.1 保持的做法

- [ ] 烧录前必做 `check-source`，并抽帧目视确认（detector 只给「疑似」）
- [ ] 改文字前复制 baseline，改完跑 `verify` 并核对 `textChangedCueCount`
- [ ] 画面层（遮罩）定型并验收**通过之后**再烧字幕
- [ ] 多模板批量先 `plan`、再并行 `run`
- [ ] 区域坐标一律用扫描或放大读数获取，禁止目测

### 5.2 改进的做法

| 改进项 | 原做法 | 新做法 | 预期效果 |
|:---|:---|:---|:---|
| 前置检查 | `ffprobe` 看规格；`check-source` 留到烧录前 | 探测阶段一次跑完：环境 + 规格 + `check-source` + 台标候选 | 消除问题1、问题3；省 2 轮完整重跑 |
| 区域测量 | 抽帧目视估坐标 | 全片梯度扫描拿极值 + 放大读刻度拿边界 | 消除问题2；省 4 次量偏 |
| 遮罩验收 | 只抽正常时段（30s/120s） | 按**要素出现窗口**验收：正常时段 + 冲突时段各抽一张 | 在烧字幕前暴露内容条冲突 |
| 遮罩实现 | 色块 → 反复试范围与半径 | 直接采用「局部 `boxblur` + `enable` 时间门控」，色度半径固定 `2` | 遮罩从 5 版降到 1–2 版 |
| 写盘编码 | 按需自行决定编码 | 沿用源文件的编码/BOM/换行；写入后先自查 BOM | 避免 `verify` 因编码判红 |
| 文本替换 | 直接写匹配串 | 每次替换先断言命中数 `==1`，跨条情况单独处理 | 避免跨条替换静默失败 |
| 目标表述 | 「更快、更省钱」 | 改为「更快、更少人工轮次、更少重复算力」 | 目标与现实对齐（本次金钱成本为 0） |

### 5.3 待验证的假设

| 假设 | 验证方法 | 验证标准 |
|:---|:---|:---|
| 把前置检查做成技能内置闸门后，同类任务返工降到 ≤1 次 | 下一条自带硬字幕的素材全程走新路径 | 遮罩渲染 ≤2 版、无完整重跑 |
| 梯度扫描法对「浅色字幕 / 无描边字幕 / 半透明字幕」同样有效 | 取 3 条不同类型自带字幕的素材跑扫描 | 极值稳定（p1 与中位数接近），目视复核一致 |
| 台标检测可用「时间持久性」自动区分台标与动态内容条 | 实现后跑本片，检查能否自动排除内容条窗口 | 台标区域稳定检出，内容条窗口被自动排除 |
| 内容条与台标空间重叠时，模糊台标是否优于让台标露出 | 两种处理各出一版，对比观看 | 主观判断「哪种更像正常成片」 |

## 六、关键洞察

> **洞察1**：本次 8 项返工里有 7 项可由**一个前置检查闸门**消除。问题不在于某个 CLI 做得不好，而在于链路缺少共同的「输入体检」——三个技能各自正确，却在衔接处漏掉了源片本身的状态。

> **洞察2**：`max_lines=2` 这类声明与实际不符，是横向对比才暴露的。多模板并行不只是省时间，它让「文档说的」与「实际渲染的」之间的差距变得可见。

> **洞察3**：「更省钱」在本链路上是空目标——全程离线，金钱成本恒为 0。真正可优化的是**算力时间**（遮罩 5 版、字幕 2 轮重跑）和**人工确认轮次**（>10 次抽帧往返）。把目标改成可度量的东西，改进才有方向。
