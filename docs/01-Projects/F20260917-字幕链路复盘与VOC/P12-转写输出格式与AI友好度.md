# P12 · 转写输出格式与 AI 友好度（口播录屏 → 文字）

> 本文档为 `F20260917-字幕链路复盘与VOC` 的补充产出（P12）。
> 回答两个问题：**① 识别结果只有 SRT 吗？还有哪些格式？② 哪些对 AI 更友好？**
> 所有结论均含**本机实测**（whisper.cpp v1.8.4 / v1.9.2，Windows x64，i7-9700 + GTX 750）。
> 与 `P07-字幕格式全景.md` 的分工：**P07 讲字幕"给人/给播放器"的格式**（SRT/ASS/VTT/LRC/TTML/PGS，软字幕 vs 硬字幕）；**P12 讲转写"产物本身"的格式与 AI 可消费性**。

---

## 一、结论先行（30 秒版）

1. **不是只有 SRT。** 光引擎（whisper.cpp）一次就能吐 **8 种**产物：`txt / vtt / srt / lrc / csv / wts / json / json(full)`；工具层（subgen）另有 4 种；App 内部还持有一份**带词级时间戳的内存模型**。
2. **对 AI 最友好的是 `-ojf` 的完整 JSON，而 SRT 只是它的降级子集。** 那份 JSON 里有 SRT 完全没有的东西：**词级时间戳**、**每个词的置信度 `p`**、token id。
3. **但这份"富矿"有一个致命前置条件**：whisper.cpp **≤ v1.8.4 对中日韩 token 的文本是有损的**——我实测 30 秒中文里 **141 个 token 有 38 个是 `�`**（U+FFFD），拼出来的中文是 `这是一段用于��音��别����的��音。`。**同样的模型与音频，换 v1.9.2 引擎 → 0 个 `�`，拼接结果与段文本逐字一致。**
4. **所以「中文想要 AI 友好产物」= 必须升级引擎到 v1.9.2 及以上**；不升级，中文就只能停在 SRT（段级）这一层。英文不受影响。
5. **音画同步的锚点是词级时间戳，不是段级时间码。** 段级 SRT 只能整段对齐；词级能用三种形态表达：内联 VTT（`<00:00:00.140>`）、结构化 JSONL、带时间码的 Markdown。
6. **给 AI 读最佳形态是「带时间码的 Markdown 文稿」，不是 SRT。** 我写了一个转换脚本并实测跑通（`assets/whisper-json-to-ai.ps1`），一次产出三种形态。

## 二、Q1：格式多样性 —— 有三层，不是一层

「识别结果有什么格式」这个问题之所以容易答错，是因为链路上有**三个不同的层**，每层能给的格式不一样。

```text
第 3 层  App（Recordly）   →  内存里的 cues[{text, startMs, endMs, words[]}]，用于渲染与控制
                              ▲ 只在应用内，不落地成文件
第 2 层  工具（subgen 等） →  srt / vtt / txt / json           ← 你日常用的这一层
                              ▲ 二次加工：响度归一化、静音重分段、繁简、标点
第 1 层  引擎（whisper.cpp）→  txt / vtt / srt / lrc / csv / wts / json / json-full
                              ▲ 原始能力上限在这里
```

**关键认知**：**上游能给什么，决定了下游的上限**。第 1 层有词级 JSON，第 2、3 层才有机会用它；第 1 层拿不到（中文在 v1.8.4 拿不到），下游再怎么写也补不回来。

### 2.1 第 1 层：whisper.cpp 引擎原生的 8 种（本机实测，英文 30 秒素材）

一次运行同时带上所有输出开关即可全部产出（实测命令见附录）：

| 开关 | 文件 | 里面有什么 | 实测大小 | AI 友好度 |
|:--|:--|:--|--:|:--|
| `-otxt` | `.txt` | 纯文本，一行一段，**无时间** | 0.4 KB | ★☆☆☆☆ |
| `-ovtt` | `.vtt` | WEBVTT，**段级**时间码（`00:00:00.000`） | 0.7 KB | ★★☆☆☆ |
| `-osrt` | `.srt` | SubRip，**段级**时间码（`00:00:00,000`） | 0.8 KB | ★★☆☆☆ |
| `-olrc` | `.lrc` | `[00:00.00]文字`，**只有行首时间、没有结束时间** | 0.5 KB | ★☆☆☆☆ |
| `-ocsv` | `.csv` | `start,end,text`，**毫秒整数** | 0.5 KB | ★★★☆☆ |
| `-owts` | `.wts` | **卡拉OK生成脚本**（shell，靠 ffmpeg+drawtext 渲染） | 0 KB ⚠️ | ★☆☆☆☆ |
| `-oj` | `.json` | 段级 JSON（含 model/params/systeminfo 元数据） | — | ★★★☆☆ |
| **`-ojf`** | `.json` | **完整 JSON：段 + 词级 tokens + 置信度** | 22.2 KB | **★★★★★** |

**三条实测发现**：

- ⚠️ **`-owts` 在 Windows 上开箱即用不了**：默认字体路径写死为 macOS 的 `/System/Library/Fonts/Supplemental/Courier New Bold.ttf`，在 Windows 上直接产出**空文件**并警告 `font not found ... please specify a monospace font with -fp`。要用必须显式传 `-fp`。<br>【实测·本机】`fmt_en.wts` = 0 字节。
- ⚠️ **段级边界很差**：SRT/VTT/TXT 实测第一条是 `This is a benchmark recording for the Speech Recognition` / `model.` —— **句子被从中间劈开**。这正是 Recordly 和 subgen 都要自己做"静音重分段"的原因（见 P02）。
- ✅ **`-ocsv` 是被低估的一种**：`start,end,text` 三列、毫秒整数，Excel / pandas / AI 都极好吃，而且比 SRT 少一层解析。

### 2.2 第 3 层：Recordly App 内部其实已经持有了词级数据

App 的类型定义（`electron/ipc/types.ts:173-186`）：

```ts
type CaptionWordPayload = { text: string; startMs: number; endMs: number; leadingSpace?: boolean };
type CaptionCuePayload  = { id: string; startMs: number; endMs: number; text: string; words?: CaptionWordPayload[] };
```

**也就是说：App 内存里本来就有词级时间戳**（`words[]`），它是靠 `-ojf` 的 JSON 解析来的（`electron/ipc/captions/parser.ts:19-74`）。

但——**解析器只取了 3 个字段**：

| JSON 里有的 | 含义 | App 是否保留 |
|:--|:--|:--:|
| `tokens[].text` | 词文本 | ✅ |
| `tokens[].offsets.from / .to` | 词级起止（**毫秒**） | ✅ |
| `tokens[].p` | **该词的置信度（0–1）** | ❌ **丢弃** |
| `tokens[].id` | 词表 id | ❌ 丢弃 |
| `tokens[].t_dtw` | DTW 对齐时间 | ❌ 丢弃 |
| 顶层 `systeminfo` / `model` / `params` | 可复现性元数据 | ❌ 丢弃（只写进临时文件后删除） |

> **一句话**：**信息不是没有，是被丢在了从 JSON 到内存的那一步**。而对 AI 来说，`p`（置信度）恰恰是最值钱的字段之一——它等于引擎自己告诉你"这个词我不确定"。

### 2.3 三层格式对照总表

| 能力 | whisper.cpp 引擎 | subgen（你的日常工具） | Recordly App |
|:--|:--|:--|:--|
| 纯文本 | `-otxt` ✅ | `txt` ✅ | ❌ |
| 段级字幕 | `srt` / `vtt` / `lrc` / `csv` ✅ | `srt` / `vtt` ✅ | ✅（字幕轨，可烧录/渲染） |
| **词级时间戳** | `-ojf` JSON ✅ | `json` ✅（**中文在旧引擎下会被自动降级**，见 §三.3） | 内存里有 `words[]` ✅ / 落地为文件 ❌ |
| **词级置信度** | `-ojf` 的 `p` ✅ | — 技能文档未提及 | ❌ 丢弃 |
| 卡拉OK脚本 | `-owts`（Windows 需 `-fp`）⚠️ | ❌（**D11 明确"只留 JSON 词级数据供后期生成"**） | ❌（但自己有 5 套字幕动画模板） |
| 说话人标记 | `--diarize`（**依赖立体声双声道**） | — | ❌ |
| 段落/章节结构 | ❌ | ❌ | ❌ |

> **交叉印证**：`subtitle-generate-master` 自己的文档已经记录了同一件事——
> `D10`：「whisper.cpp v1.8.4 的 `-ojf` 对中日韩 token 的文本是有损的（每个 CJK token 常写成 `�`，只有 `segment.text` 正确）。所以中文拿不到可用的词级文本。」
> `D06`：`运行时太旧不支持 -ojf` 会**自动降级**，仍出 SRT 但失去词级时间戳。
> `D11`：逐字卡拉OK「本期不做，**只留 JSON 词级数据供后期生成**」。
> → 即：**工具层早就把"词级 JSON"当作清水源在设计**，缺的只是引擎那一环。

## 三、Q2：AI 友好度 —— 按"AI 要干什么"来选，而不是按"哪个格式高级"

### 3.1 先立判据：什么才算"对 AI 友好"

不是"格式越新越好"，而是看**四条**：

| 判据 | 为什么 | SRT 满足吗 |
|:--|:--|:--:|
| **① 结构化**（字段可寻址） | AI/程序要能只取"第 3 段的时间"而不用正则抠 | ❌（纯文本，靠位置解析） |
| **② 时间精度到词** | 音画同步、重排、二次剪辑都靠它 | ❌（只有段级） |
| **③ 带置信度/元数据** | AI 才知道"哪句该复核"，而不是盲目信任 | ❌ |
| **④ 稳定可复现**（含模型/参数留痕） | 换模型/参数后能判断产物是否可比 | ❌ |

**SRT 四条只勉强满足第①条的"人能看懂"**，所以——**"只用 SRT"不是保守，是把上游 90% 的信息扔掉了。**

### 3.2 四种 AI 用途 → 对应产物（这是本文档最该被记住的一张表）

| 你要 AI 干什么 | 最佳产物 | 为什么 | 不要用什么 |
|:--|:--|:--|:--|
| **理解全文 / 总结 / 改写成文章** | **带时间码的 Markdown**（`.ai.md`） | LLM 读 Markdown 最省 token；段落结构 + `[00:01:23]` 锚点，引用时可回溯 | 别喂 JSON（token 爆炸）、别喂 SRT（无段落结构） |
| **音画精确同步 / 重排 / 再剪辑** | **词级 JSONL**（`.words.jsonl`）或**词级内联 VTT**（`.word.vtt`） | 每个词有 `startMs/endMs`，重排后时间戳不会错位 | SRT 段级时间做不到词级对齐 |
| **纠错 / 校对 / 挑出可疑词** | **词级 JSONL（用 `p` 字段）** + 低置信度清单 | `p` 是引擎自评的"我不确定"信号 | 人眼通读全文（慢且会漏） |
| **喂给下游字幕工具 / 烧录** | SRT（人看）/ ASS（带样式） | 生态兼容性最好 | — |

### 3.3 决定性实测：`-ojf` 的中文词级产物，v1.8.4 是坏的，v1.9.2 是好的

这一条直接决定"中文能不能吃上 AI 友好产物"，我用同一段 30 秒中文、同一个 `ggml-small` 模型、只换引擎版本，做了对照：

| 引擎版本 | token 总数 | 含 `�`(U+FFFD) 的 token | 段内 token 拼接 vs `segment.text` | 第 1 段拼接结果 |
|:--|--:|--:|:--:|:--|
| **v1.8.4**（随包版本） | 141 | **38（27%）** | ❌ 不一致 | `这是一段用于��音��别����的��音。` |
| **v1.9.2** | 122 | **0** | ✅ **逐字一致** | `这是一段用于语音识别测试的录音。` |

前 8 个有效 token 的对照（文本 / 起止 ms / 置信度）：

```text
v1.8.4 : '这是' | '一' | '段' | '用' | '于' | '�'(1330→1480) | '�'(1480→1550) | '音'
         注意时间轴也被拉长：'段' 占 670→890 ms

v1.9.2 : '这是' 140→270 | '一' 270→380 | '段' 400→520 | '用' 530→660
         '于' 660→790 | '语' 790→1190 | '音' 1190→1320 | '识' 1320→1720
         每个汉字一个 token，文本完整、时间规整
```

**结论**：
- **中文在 v1.8.4 上拿不到可用的词级时间戳**——不是"精度差一点"，是**文本本身就是乱码**，时间轴也不可靠。
- **升级到 v1.9.2 后，中文的词级时间戳完全可用**（逐字一致 + 每字一个 token）。
- 这解释了 `subgen` 里那道「**完整性闸门**」（`D10` 原文：词流拼出来的文字必须与 `segment.text` 一致，否则放弃该段词级时间），也解释了为什么"中文主力走段骨架路径"。**那道闸门在 v1.9.2 下会通过。**

> **英文不受影响**：v1.8.4 的英文 `-ojf` token 文本正常（实测 206 秒英文产出 138 KB 完整 JSON，词级可用）。

### 3.4 被低估的字段：`tokens[].p`（词级置信度）实测效果

我从 v1.9.2 的中文 JSON 里把所有 `p < 0.9` 的词拉了出来（30 秒素材，共 23 个）。**它确实标中了真正的错字**：

| 词 | p | 实际对错 |
|:--|--:|:--|
| **`缅`** | **0.734** | ❌ **错字**（应为"面"，"方便后面做断句"） |
| `这是` | 0.663 | ✅ 正确 |
| `断` | 0.438 | ✅ 正确 |
| `?`（半角问号） | 0.501 | ✅ 正确 |
| `请` | 0.448 | ✅ 正确 |
| `。`（句号） | 0.630 | ✅ 正确 |

**诚实的结论**：`p` **不是判决，是"复核队列"**——
- ✅ 它能**捞出错字**（`缅` p=0.734 在列）；
- ⚠️ 但**假阳性不少**（`这是`/`断`/`请` 都正确却低分），尤其是**标点符号普遍低分**（标点本来就难预测）。
- 实用做法：**按 `p` 升序人工过一遍前 20%**，而不是"低于 0.9 全都要改"。

> 这个字段在 Recordly 的 `parser.ts` 里被丢掉了；`subgen` 是否暴露也未见文档。**用起来是零成本的**（JSON 里本来就有），只要解析时不丢。

### 3.5 音画同步：为什么词级时间戳是唯一可靠的锚

| 产物 | 时间精度 | 重排/改字后会不会错位 | 适合 |
|:--|:--|:--|:--|
| SRT / VTT（段级） | 段 | ⚠️ **会**。改了断句就得手工重算时间 | 人看、发布 |
| `.word.vtt`（词级内联） | **词** | ✅ 不会。每个词自带时间，重排只是重排顺序 | 播放器逐词高亮、网页字幕 |
| `.words.jsonl`（词级结构化） | **词** | ✅ 不会。程序可精确按词重排 | AI 处理、自动化流水线 |
| `.ai.md`（带时间码文稿） | 段（可加词级标记） | —（不是给机器对齐用的） | **喂给 LLM** |

> ⚠️ **一个必须知道的坑**：whisper.cpp **原生 `-ovtt` 不输出词级内联时间戳**（源码 `output_vtt()` 只写 `segment.text` 与段级时间，见 `cli.cpp:467-487`）。词级内联 VTT **必须自己从 `-ojf` 的 JSON 生成**——这就是我写下面那个脚本的原因。

## 四、参考实现：`whisper-json-to-ai.ps1`（已实测跑通）

> 位置：`F20260917-字幕链路复盘与VOC\assets\whisper-json-to-ai.ps1`
> 作用：把 `-ojf` 的 JSON 一次转成三种 AI 友好产物。**自包含，无外部依赖，Windows 原生 PowerShell。**

### 用法

```powershell
# 1) 先转写，务必带 -ojf（且引擎 ≥ v1.9.2 才有中文词级）
whisper-cli -m ggml-large-v3-turbo-q5_0.bin -f 口播.wav -l zh -np -t 8 -ojf -of out

# 2) 转成 AI 友好三件套
pwsh -File .\assets\whisper-json-to-ai.ps1 -JsonPath out.json
```

### 产出

| 文件 | 形态 | 用途 |
|:--|:--|:--|
| `out.ai.md` | 带 `### [00:00:00 → 00:00:04]` 段锚点 + `**[词]**` 低置信度标记 + 校对清单表 | **喂给 LLM 理解全文** |
| `out.words.jsonl` | 每段一行 JSON：`{startMs,endMs,text,words[{text,startMs,endMs,p}]}` | **程序/AI 精确对齐处理** |
| `out.word.vtt` | 词级内联时间戳 VTT | **播放器逐词高亮 / 音画同步** |

### 实测产物样本（`.ai.md`，v1.9.2 中文真实输出）

```markdown
# 转写文稿（AI 友好）

> 来源：`cjk_v192.json`｜模型：`small`｜语言：`zh`｜段数：7
> 词级低置信度阈值 p < 0.9，标记为 **[?]**。

## 时间码文稿

### [00:00:00 → 00:00:04]

**[这是]**一段用于语音**[识]**别测试的录音**[。]**

### [00:00:12 → 00:00:18]

并且给出每个词出现的时间点**[,]****[方]**便**[后]****[缅]****[做]****[断]****[句]**和排**[版]**。
```

> 注：上面 `[缅]` 被标出——**正是那个错字**；`p` 信号在这一句里指向了正确的位置。

### 脚本的自检能力（实测）

脚本会做**完整性闸门**，与 `subgen` 同款判据：

| 输入 | 实测输出 |
|:--|:--|
| v1.9.2 中文 JSON | `完整性告警: 0`，段数 7，词数 113，低置信度词 23 |
| v1.8.4 中文 JSON | ⚠️ `有 5/7 段的词级文本与段文本不一致（含 U+FFFD「�」）` |

**这条告警本身就是判据**：看到它就说明**引擎该升级了**。

## 五、选型速查（口播录屏场景）

| 你的目的 | 产物 | 怎么来 |
|:--|:--|:--|
| **让 AI 读懂整篇内容** | `.ai.md`（带时间码的 Markdown） | `-ojf` → 本脚本 |
| **让 AI 做音画对齐 / 重排 / 二次剪辑** | `.words.jsonl` 或 `.word.vtt` | `-ojf` → 本脚本 |
| **挑出可能错的词去校对** | `.words.jsonl` 里按 `p` 升序 | `-ojf` → 本脚本（附低置信度清单） |
| 人工改字、交给剪辑软件 | SRT | `-osrt` 或 subgen 默认 |
| 网页 / 在线课程播放 | VTT（段级够用；要逐词高亮用 `.word.vtt`） | `-ovtt` / `.word.vtt` |
| 数据分析 / 表格 | CSV | `-ocsv` |
| 要样式、要烧进画面 | ASS | `subtitle-burn build`（见 P07/P08） |
| 素材归档 / 可复现 | **保留 `-ojf` 的 JSON** | `-ojf`（里面含 `model`/`params`/`systeminfo`，等于自带的实验记录） |

> **一句话**：**SRT 是"给人看的终点"，`-ojf` 的 JSON 才是"给 AI 用的起点"**。两者不冲突——同一份转写，同时留 SRT（发布）与 JSON（AI / 可复现）。

## 六、坑与边界（都是实测撞到的）

| # | 坑 | 实测证据 | 规避 |
|:--|:--|:--|:--|
| K1 | **v1.8.4 中文词级 token 是 `�`** | 141 token 中 38 个 U+FFFD；拼接 `这是一段用于��音��别…` | **升级引擎到 v1.9.2+**；或中文只当段级用 |
| K2 | **`-ovtt` 没有词级内联时间戳** | 源码 `output_vtt()` 只写段级 | 自己从 `-ojf` 生成 |
| K3 | **`-owts` 在 Windows 产空文件** | 实测 0 字节 + `font not found`（默认字体是 macOS 路径） | 传 `-fp <字体>`；或用本脚本的 `.word.vtt` 替代 |
| K4 | **whisper 自带断句很差** | 实测首条被劈成 `...for the Speech Recognition` / `model.` | 保留 Recordly / subgen 的静音重分段 |
| K5 | **`-ojf` 的 JSON 里 `transcription` 是顶层键，不在 `result` 里** | 实测结构：`{systeminfo, model, params, result{language}, transcription[]}` | 解析时别找错层（直觉上会以为在 `result` 下） |
| K6 | **`offsets` 是毫秒整数**，`timestamps` 是字符串 | 实测 `"offsets":{"from":4160}` vs `"timestamps":{"from":"00:00:04,160"}` | 用 `offsets`，别解析字符串 |
| K7 | **`p` 有假阳性** | `这是`(0.663)、`断`(0.438) 都正确 | 当"复核队列"用，别当"错误判决" |
| K8 | **`-ojf` 体积是 SRT 的 ~28 倍** | 30 秒素材：JSON 22.2 KB vs SRT 0.8 KB | 归档可压缩；但换来的是词级+置信度 |
| K9 | 中文标点：**turbo 模型几乎不吐句末标点** | 见 P13 实测表 | 靠 `subtitle-optimize-master` 补标点，或人工 |

$j.transcription.tokens | Where-Object { $_.text -notmatch '^\[' -and $_.p -lt 0.9 } |

## 附录 B：JSON 完整结构（实测，v1.9.2）

```json
{
  "systeminfo": "WHISPER : COREML = 0 | OPENVINO = 0 | CPU : SSE3 = 1 | ... | AVX2 = 1 | F16C = 1 | FMA = 1 | OPENMP = 1 | REPACK = 1 | ",
  "model": { "type": "small", "multilingual": true, "vocab": 51865,
             "audio": { "ctx": 1500, "state": 768, "head": 12, "layer": 12 },
             "text":  { "ctx": 448,  "state": 768, "head": 12, "layer": 12 },
             "mels": 80, "ftype": 1 },
  "params": { "model": "<模型绝对路径>", "language": "en", "translate": false },
  "result": { "language": "en" },
  "transcription": [
    {
      "timestamps": { "from": "00:00:00,000", "to": "00:00:04,160" },
      "offsets":    { "from": 0, "to": 4160 },
      "text": " This is a benchmark recording for the Speech Recognition",
      "tokens": [
        { "text": "[_BEG_]", "timestamps": {"from":"00:00:00,000","to":"00:00:00,000"},
          "offsets": {"from":0,"to":0}, "id": 50364, "p": 0.971789, "t_dtw": -1 },
        { "text": " This", "timestamps": {"from":"00:00:00,110","to":"00:00:00,340"},
          "offsets": {"from":110,"to":340}, "id": 639, "p": 0.902006, "t_dtw": -1 }
      ]
    }
  ]
}
```

**读法**：
- `model.type` / `params.language` / `systeminfo` = **自带的实验记录**（换模型/参数后可对比）
- `transcription[].offsets` = 段级毫秒
- `transcription[].tokens[]` = **词级**；`text` 为 `[...]` 的是特殊 token（`[_BEG_]` 等），分析时要过滤
- `p` = 词级置信度；`t_dtw` = DTW 时间（本机实测恒为 `-1`）
