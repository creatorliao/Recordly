# 剪映字幕动画模板的机制与可移植性分析

> 本文档为 `F20260917-字幕链路复盘与VOC` 的补充产出。
> 回答三个问题：① 剪映怎么表达字幕动画？② 能不能抽出来复用到别处？③ 我们能不能自己做同款？
> 所有结论基于本机实测（本机装有剪映 **11.4.2.14459**，含 11 个真实草稿）。

---

## 结论先看（TL;DR）

| 问题 | 结论 | 依据 |
|:---|:---|:---|
| 剪映怎么表达动画？ | 工程侧是 **H5（HTML/CSS/JS）** 定义 + 草稿里存 **effect ID 引用** | 本机 `Resources\image_h5_text_template_publish` 为 37 个 HTML/CSS 文件 |
| 能抽取剪映模板复用吗？ | **不能**，三条路都堵 | ① 草稿加密 ② 模板资源是 ID+服务端资源 ③ 渲染靠剪映原生引擎 |
| 能自己做同款吗？ | **能**，且已验证 | 逐字弹入/位移/淡入/矩形擦出在 libass 全部跑通 |
| 建议 | 自建 ASS 模板库，不追求抽取 | 见 §四 |

## 一、剪映是怎么表达字幕动画的

### 1.1 工程文件层：草稿目录结构

本机实测草稿路径（Windows 剪映）：

```text
C:\Users\creator\AppData\Local\JianyingPro\User Data\Projects\com.lveditor.draft\<草稿名>\
```

本机共 **11 个草稿**，每个草稿目录内的文件：

| 文件 | 作用 | 本机实测 |
|:---|:---|:---|
| `draft_content.json` | **工程主体**（轨道、素材、动画引用） | **已加密**，见下 |
| `draft_meta_info.json` | 元数据（名称、封面、导入素材登记） | **已加密** |
| `draft_agency_config.json` | 动画库/代理配置缓存 | **明文 JSON**（仅 154 字节的功能开关） |
| `assets/` | 导入的素材副本 | 未逐一验证 |

### 1.2 关键发现：草稿主体是加密的

```text
文件: 9月16日\draft_content.json  (0.87 MB)
头 16 字节 hex: 38 69 44 39 6b 61 52 63 47 31 44 38 55 42 39 6d
头 40 字节文本: 8iD9kaRcG1D8UB9mpnv4355d4B/QFqOUk6AJ4UwV...
```

**不是 JSON**——尝试 `json.load` 报 `Extra data: line 1 column 2 (char 1)`。内容是一段 Base64 样式的密文。

抽查的 **8 个草稿全部同构**（都是密文），说明这是该版本的统一做法，不是个别草稿异常。

> **这条直接决定了「从剪映工程里抽模板」的可行性**：抽不了。除非先解决解密，而解密属逆向工程范畴，且会随剪映版本变化而失效。

### 1.3 渲染层：模板是 H5，不是关键帧数据

本机 `Apps\11.4.2.14459\Resources\` 下与文字/动画相关的资源：

| 目录 | 文件数 | 推测作用 |
|:---|:---|:---|
| `image_h5_smart_text` | 164 | 智能字幕（H5 渲染） |
| `image_h5_smart_text_old` | 157 | 旧版 |
| **`image_h5_text_template_publish`** | **37** | **文字模板（H5 发布页）** |
| `image_h5_sticker_publish` | 36 | 贴纸模板 |
| `Font` | 15 | 字体资源 |
| `aigc_text_template` | 6 | AIGC 文字模板 |
| `template_sticker` | 5 | 模板贴纸 |

`image_h5_text_template_publish` 的实际文件清单：

```text
nestedRoutes.json                      1 KB
publish-text-template.html             2 KB
publish-subtitle-template.html         2 KB
publish-text-template-collection.html  2 KB
publish-text-template-retouch.html     2 KB
*.css  (750.82a24079.css 达 200 KB)
```

**这说明**：剪映的文字模板是用 **HTML + CSS + JavaScript** 表达的——动画就是 CSS animation / transition / JS 时间轴。这解释了剪映的动画为什么表现力这么强：**它本质上是在跑一个网页渲染器**，能力上限是浏览器的能力上限。

### 1.4 草稿里的动画引用（依据公开社区整理的 schema）

> ⚠️ **举证说明**：因本机草稿已加密，无法直接读取其动画字段。以下结构来自开源社区对 CapCut/剪映草稿格式的整理（[capcut-cli 的 draft-schema 文档](https://github.com/renezander030/capcut-cli/blob/master/docs/draft-schema/00-overview.md)），属**未经本机验证的二手资料**，此处仅用于解释机制，不作为落地依据。

草稿的 `materials` 中有一类 **`material_animations`**，是图像/文字的入场出场动画条目；文字段落里则以类似 `animations` / `extra_material_refs` 的字段引用它。整体设计：

```jsonc
{
  "tracks":   [ { "type": "text", "segments": [ { "material_id": "...", "animations": [...] } ] } ],
  "materials": {
    "texts": [...],                  // 文字内容与样式
    "material_animations": [...]     // 动画条目
  }
}
```

**关键机制**：`tracks` 与 `materials` 是**扁平解耦**的——段落不内联素材，而是用 `material_id` 引用。动画同理，是**一条带 ID 的条目**，而非可读的关键帧曲线。

**这意味着**：即使能把草稿解密，拿到的也只是**动画 ID**（形如某个 effect 标识），真正的动画曲线在剪映的渲染引擎/服务端资源里。**ID 本身不是可移植的数据。**

### 1.5 三层总结：剪映的动画表达链路

```text
用户在 UI 选模板
   ↓
草稿里写一个动画 ID 引用        （加密，且只是 ID）
   ↓
剪映原生渲染引擎按 ID 取实现      （CSS/JS 或原生着色器，非公开）
   ↓
导出成片
```

**对比 ASS 的表达链路**：

```text
模板里写样式 + 每条字幕写覆盖指令   （纯文本，完全可读可改）
   ↓
libass 按指令逐帧渲染              （开源实现，行为可预测）
   ↓
烧录或软字幕
```

**本质差异**：剪映是**「ID + 闭源实现」**，ASS 是**「自包含指令 + 开源实现」**。这个差异就是「能不能抽取复用」的答案。

## 二、能不能从剪映抽取模板复用到别的项目

### 三条路径逐一评估

| 路径 | 做法 | 可行性 | 原因 |
|:---|:---|:---:|:---|
| **A. 从工程文件抽** | 解密 `draft_content.json` → 提取动画定义 | ❌ 不可行 | 文件加密；且即便解密也只得到动画 **ID**，拿不到实现 |
| **B. 从资源目录抽** | 从 `Resources\` 找模板定义文件 | ❌ 不可行 | 是 H5 发布页（配 UI 用），非独立可复用资产；模板内容本身在服务端 |
| **C. 用导出成品反推** | 用剪映导出带动画的成片 → 图像分析反推关键帧 | ⚠️ 理论可行、成本极高 | 需要逐帧分析 + 重建；只能得到「近似」，且每次换模板都要重做 |

### 为什么「换一个软件用同一个模板」在原理上就很难

剪映的模板效果依赖三样东西，**没有一样是可移植的数据**：

1. **渲染引擎**：CSS 动画/着色器的具体行为（缓动曲线、抗锯齿、混合模式）
2. **字体资源**：模板指定的字体（剪映自带字体，别的环境未必有，且授权可能不允许外带）
3. **服务端资源**：部分模板效果从云端下发

**结论**：**不能抽取**。任何声称「一键把剪映模板导出到剪映以外」的方案，实际做的是「**照着重做一遍**」，不是「导出」。

### 那有没有折中方案

有，但不是「抽取」，而是**用剪映当参考、用 ASS 重实现**：

```text
剪映里选好模板 → 导出 3-5 秒样片 → 逐帧看动画参数（时长/错峰/缓动/位移量）
              → 按参数在 ASS 里重写等效效果
```

这条路的价值在于**把剪映当规格说明书**，而不是当素材源。本报告 §三 就是按这个方法验证 ASS 的能力边界。

## 三、我们能不能自己做「剪映同款」——能力基线（全部实测）

用 `libass`（ffmpeg 的 `ass` 滤镜）实测了 7 种动画，结论如下。

### 3.1 可行清单

| 效果 | 实现手法 | 实测结果 |
|:---|:---|:---|
| **逐字弹入** | 一句拆 N 条事件，各自 `\an5\pos(x,y)` + `\fscx0\fscy0\t(0,320,...)`，起始错峰 45ms | ✅ **通过**。0.45s 部分字、0.9s 全出现 |
| **逐字上移** | 每字 `\move(x,y+30,x,y,0,300)` | ✅ 通过（y 580→520 实测位移） |
| **逐字错峰淡入** | 每字 `\t(0,400,\alpha&H00&)` | ✅ 通过 |
| **整行缩放弹入** | `\fscx40\fscy40\t(0,300,...)` + 过冲回落（多段 `\t`） | ✅ 通过 |
| **移动 + 淡入组合** | `\move(...)\fad(400,0)` | ✅ 通过（位置与透明度同时变化） |
| **矩形遮罩擦出** | `\clip(x0,y0,x0,y1)\t(0,d,\clip(...x1...))` | ⚠️ 可行但**纵向高度必须给足**，否则会把字切掉（我第一次就切了字） |
| **逐字扫光（卡拉OK）** | `\kf<厘秒>` | ✅ 通过（已有模板 `karaoke-glow` 在用） |

### 3.2 不可行清单（别浪费时间）

| 想做的 | 为什么不行 |
|:---|:---|
| 任意缓动曲线（bezier / spring / elastic） | `\t` 只有一条幂曲线（`accel` 参数），过冲只能用多段 `\t` 链近似 |
| 抖动 / 震动 | `\t(\pos(...))` 在 libass 里**静默无效**（源码里 `pos` 分支忽略插值因子） |
| 非矩形遮罩动画 | `\t` 只能动画**矩形** `\clip`；矢量 `\clip` 不能动画 |
| 贴纸 / 粒子 / emoji 素材 | ASS 没有图片事件，只有字形与 `\p1` 矢量绘制 |
| 渐变色 / 混合模式 / 动态模糊 | ASS 标签里没有这些 |
| 文字沿路径运动 | 无此标签 |
| 真正的物理弹跳 | 只有幂曲线，做不出真实弹簧 |

### 3.3 关键工程结论：**ASS 做逐字动画必须「拆事件」**

这是和剪映最大的实现差异，也是最容易低估的工作量。

**剪映**：一个文字对象 + 一个「逐字」动画选项，引擎自动逐字处理。
**ASS**：**必须把一句字幕预先拆成 N 条独立 `Dialogue` 事件**，每条只管一个字。

以「第二段是结果」（6 字）为例：

```ass
Dialogue: 1,0:00:09.52,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(210,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}第
Dialogue: 1,0:00:09.56,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(270,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}二
Dialogue: 1,0:00:09.61,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(330,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}段
Dialogue: 1,0:00:09.65,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(390,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}是
Dialogue: 1,0:00:09.70,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(450,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}结
Dialogue: 1,0:00:09.74,0:00:11.02,PopChar,,0,0,0,,{\an5\pos(510,600)\fscx0\fscy0\t(0,320,\fscx100\fscy100)}果
```

**坐标算法**（可直接套用）：

```text
字步长   = 字号 + 字距          （58 + 2 = 60）
总宽     = 字步长 × 字数        （60 × 6 = 360）
首字中心 = (画面宽 - 总宽) / 2 + 字步长/2   （(720-360)/2 + 30 = 210）
第 i 字中心 x = 首字中心 + i × 字步长
错峰       = 45ms（可调；短句 30–60ms 都自然）
单位动画   = 320ms
```

**已知代价**（实测）：
1. **字幕条数会膨胀**：163 条字幕若全做逐字动画，事件数从 163 涨到约 1800 条
2. **字体度量与实际字宽有细微差异**，长句可能出现字距不匀
3. **标点跟着前一个字一起弹出**，无法单独控制
4. **必须在生成阶段预先拆字**，无法动态计算（这是与剪映最大的体验差距）

**已产出可用模板**：`assets/templates/capcut-style_逐字弹入.ass`（含坐标算法注释与限制说明，已渲染验证）。

## 四、建议与落地路径

### 4.1 建议结论

| 事项 | 建议 |
|:---|:---|
| 抽取剪映模板 | **放弃**。原理上不通，别投入 |
| 拿剪映当参考 | **推荐**。导出样片 → 读参数 → ASS 重实现 |
| 自建 ASS 模板库 | **推荐**。先做 3–4 个高频效果，已验证可行 |
| 超出 ASS 能力的效果 | **混合方案**：文字走 ASS，表达不了的那层预渲染成 PNG/透明序列，在同一 ffmpeg filtergraph 里 `overlay` |

### 4.2 优先自建哪几个模板

按「剪映使用频率 × ASS 可行性」排序：

| 优先级 | 模板 | 理由 |
|:---|:---|:---|
| 1 | **逐字弹入** | 短视频最高频；已实现验证 |
| 2 | 逐字错峰淡入 | 比弹入克制，长视频友好；实现同构，成本低 |
| 3 | 整行缩放弹入 | 已有 `punch-pop` 接近，微调即可 |
| 4 | 矩形擦出 | 标题感强；注意纵向高度给足 |
| — | 逐字扫光 | 已有 `karaoke-glow` |
| ❌ | 抖动、粒子、渐变、贴纸 | ASS 做不到，需混合方案 |

### 4.3 要不要做成 CLI 能力

`subtitle-burn` 目前是「一条字幕 = 一条 ASS 事件」。要做逐字模板，需要新增一个**拆字器**：

```text
输入：SRT + 模板名（如 perchar-pop）
处理：按坐标算法把每条字幕拆成 N 条带 \pos 的事件
输出：ASS
```

这是**纯文本变换**，不涉及渲染，实现成本低、风险小。建议作为 `subtitle-burn` 的新能力（见 §六 VOC）。

## 五、回到根本：为什么两者做不出完全一样的效果

| 维度 | 剪映 | ASS / libass |
|:---|:---|:---|
| 表现形式 | H5（CSS/JS）+ 原生着色器 | 文本标签（覆盖指令） |
| 动画模型 | 关键帧 + 任意缓动 | 单段幂曲线 + 多段近似 |
| 逐字处理 | 引擎自动 | **必须预先拆事件** |
| 素材支持 | 图片/贴纸/粒子/视频 | 仅字形与矢量绘制 |
| 可移植性 | **不可移植**（ID + 闭源引擎） | **完全可移植**（自包含文本） |
| 可编辑性 | 依赖剪映 | 任何文本编辑器 |
| 依赖 | 剪映客户端 | 任何带 libass 的播放器/ffmpeg |

**一句话概括**：剪映换来的是**表现力**，付出的是**可移植性**；ASS 换来的是**可移植性与可编程性**，付出的是**表现力上限**。二者不是替代关系。

对本次任务（批量、自动化、可脚本化的字幕烧录），ASS 是正确选择——因为它的每一条效果都能被脚本生成和复用。

## 六、VOC 建议（回写 subtitle-burn-master）

| # | 建议 | 优先级 | 说明 |
|:---|:---|:---|:---|
| 1 | 增加**逐字模板**能力（拆字器 + 逐字弹入/错峰淡入） | **高** | 当前只能整行动画；逐字是剪映用户最习惯的效果，且实现是纯文本变换，成本低 |
| 2 | 模板文档补充「逐字类效果需拆事件」的说明与坐标算法 | 高 | 用户自行实现时最容易卡在坐标换算 |
| 3 | 提供 `--char-stagger` / `--char-anim` 参数 | 中 | 免去手写 ASS |
| 4 | 文档明确 ASS 的能力边界清单（哪些剪映效果做不到） | 中 | 避免用户按剪映预期提出做不到的需求 |
