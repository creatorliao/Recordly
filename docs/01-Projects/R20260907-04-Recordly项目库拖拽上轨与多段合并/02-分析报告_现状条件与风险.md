# 02 · 分析报告：现状条件与风险

## 结论

当前 Recordly 已有单工程、单主视频片段的编辑与导出链路，时间轴具备 clip 的拖拽、分割、删除、撤销基础。项目库目前承担「打开工程」语义，不能直接改成素材箱，否则会破坏单段用户的金路径。

## 源码事实

- `EditorShell` 将当前工程状态、预览、时间轴和导出串在同一工程上下文中。
- 时间轴项通过 `TimelineWrapper` 统一处理拖拽、缩放、重叠校验和取消回滚。
- 工程持久化已经保存 clip、音频、字幕、标注等区域，但现有主视频来源仍以当前工程媒体为中心。
- 项目库入口调用打开工程动作；点击工程格子不能静默变成「加入当前时间轴」。
- Windows portable 构建已存在独立脚本 `scripts/build-win-portable.mjs`，目录产物不应提交到 Git。

## 实现条件

第一期应先抽象「素材引用」和「时间轴 clip」的关系，再接 UI。每个素材引用至少需要来源路径、媒体元数据、可选讲解声/光标遥测关联；时间轴只保存引用和 clip 范围，不复制或 concat 源文件。

## 主要风险

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 项目格子语义被改写 | 老用户找不到打开工程 | 项目层与素材层分离 |
| 多段音画关联不完整 | 段间串声、光标错位 | clip 使用源时间基准并做切点测试 |
| 不同分辨率直接拉伸 | 画面变形 | 使用当前工程画布，较小画面信箱 |
| 导出只覆盖第一段 | UI 看似成功但结果错误 | 增加两段导出集成验证 |
| 未保存工程被隐式切换 | 用户编辑丢失 | 打开工程仍走未保存确认 |

## 判断

这是高价值、高风险的时间轴和导出变更，不应在需求代决未确认前施工。当前可先收口视觉系统、类型错误和验证基线。
