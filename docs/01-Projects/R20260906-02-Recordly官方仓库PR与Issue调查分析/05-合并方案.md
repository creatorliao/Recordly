# 05 · 合并方案（具体执行步骤）

> ⚠️ 过程稿。含「向上游 `gh pr merge` / 关闭他人 PR」。**本地只在 `dev-creator` 移植；执行以 [`12`](12-综合完善方案.md) 为准。**

> 目标：按 [`04-功能优先级.md`](04-功能优先级.md) 的 P0→P1 顺序，把 PR 安全、分批地合并进 `main`，每批跑通冒烟，不留回归。
> 执行前先看每个 PR 的合并状态：`DIRTY`=需 rebase、`UNSTABLE`=CI 失败、`UNKNOWN`=旧 PR 需重新验证。

---

## 〇、每个 PR 合并前：必过六问（逐 PR 应用，无一例外）

| # | 问 | 不过则 |
|---|----|--------|
| ① | 服务哪个目标(G1–G4)？ | 落不进 → 拒 |
| ② | 是否不过度设计（≤500 行、聚焦）？ | 超 → 审慎/拆小 |
| ③ | 有无回归风险（录/停/编/导）？ | 有 → 加验证 |
| ④ | 用户视角·**有必要吗**？ | 炫技 → 拒 |
| ⑤ | 用户视角·**会带来困惑吗**？ | 困惑 → 重设计 |
| ⑥ | 用户视角·**会有奇怪影响吗**？ | 有 → 拒/改 |

> **每个 PR 都必须过这六问，无一例外。** 六问全过才进下面的合并批次。

## 〇、前置准备（一次性）

```bash

gh repo view webadderallorg/Recordly --json viewerPermission

# 2. 拉最新 main，作为合基
git fetch origin && git checkout main && git pull origin main

# 3. 批量看目标 PR 状态
for n in 875 803 797 845 730 785 825 796 855 712 777 823 874 865 733 774 732 719 710 790; do
  gh pr view $n --repo webadderallorg/Recordly --json number,title,mergeStateStatus,reviewDecision --jq '"#\(.number) \(.title) [\(.mergeStateStatus)]"'
done
```

## 八、每批合并的统一验收清单（冒烟测试）

每次合完一批，跑这一套，任一失败即回滚该批：

1. ✅ 启动应用，选窗口，开始录制（倒计时正常）
2. ✅ 录制中点击被录软件，能正常交互
3. ✅ 停止录制，自动进入编辑器
4. ✅ 加一个修剪（T）→ 应用自动缩放 → 生成字幕
5. ✅ 保存项目 → 重新打开
6. ✅ 导出 MP4，文件能播放、有声音
7. ✅ 若本批含**功能增强且改变了操作方式**：已更新对应使用手册，并在手册/速查卡中标注「变更提示」告知用户调整操作行为

## 九、风险预案

| 风险 | 预案 |
|------|------|
| 社区 PR `DIRTY`（冲突） | `gh pr checkout` 后手动 `git rebase origin/main`，解决冲突后 push 回 PR 分支 |
| 社区 PR `UNSTABLE`（CI 失败） | 先看 `gh pr checks <n>`，若是无关 lint 波动则 rebase 重跑；若是真失败则不合并 |
| 合并后回归 | 用 `git revert` 回滚该 PR，重新评估 |
| 作者长期不响应 | 超过 2 周不响应，可自行 cherry-pick 其提交并署名，或关闭 |
