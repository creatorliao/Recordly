# 06 · 目标贡献核对（确保每个合并都对目标有用）

> 六问仍有效。P0 映射表里的 macOS/Linux PR **不执行**。队列见 [`12`](12-综合完善方案.md)。

> 目的：给「合并」上一道闸——**每个 PR 合并前，必须证明它对我们的目标有贡献**，否则不放行。
> 用一句话约束所有合并决策：**服务培训师录课，不服务炫技。**

---

## 一、目标再定义（可衡量的口径）

| 编号 | 目标 | 可衡量的落点 |
|------|------|-------------|
| **G1** | 完整路径可用 | 「启动录制 → 停止 → 编辑 → 导出」全程无阻断 |
| **G2** | 减轻剪辑工作量 | 录完到导出，人工操作 ≤ 15 分钟（修剪/缩放/字幕一次过） |
| **G3** | 字幕 / 配音 | 能一键生成字幕、能录到讲解声/加配音 |
| **G4** | 功能完善、体验良好、**不过度设计** | 功能少而稳 > 功能多而险；改动 >500 行进入高审慎 |

> 任何合并决策，先落到 G1–G4 里；**落不进任何一个，就不合。**

---

## 二、每个 PR 合并前必须回答的问题（六问）

**目标三问**：

1. **它服务哪个目标？** → 必须明确指出 G1/G2/G3/G4 中的至少一个。
2. **它是否「不过度设计」？** → 改动规模、范围是否聚焦，是否动核心链路。
3. **它有无回归风险？** → 是否影响「录、停、编、导」任一步。

**用户视角三问**（新增功能尤其必答）：

4. **有必要吗？** → 用户真的需要，还是「炫技」？培训师录课用得上吗？
5. **会带来困惑吗？** → 新增入口/选项/开关，会不会让老用户找不到原来的操作？
6. **会有奇怪影响吗？** → 有无意外副作用、干扰现有操作、改变默认行为？

**六问全过 → 合；任一不过 → 拒绝、重设计或要求拆分。**

---

## 三、贡献核对清单（合并闸门，逐项打勾）

```
□ 1. 明确对应 G1/G2/G3/G4 中的哪一个（写出来）
□ 2. 改动规模可接受（≤500 行直接过；500–2000 需审；>2000 基本拒）
□ 3. 不触碰无关模块（聚焦单一功能/修复）
□ 4. 不破坏「录 → 停 → 编 → 导」任一步（冒烟通过）
□ 5. 非 Slop（疑似 AI 生成低质代码 → 重写）
□ 6. 非重复（同一主题已有 PR 则只合一个）
```

**6 项全勾，才允许合并。**

## 五、合并决策流程图（一句话版）

```
PR 进来
  ├─ 落进 G1？→ 是 → 优先合（保命）
  ├─ 落进 G2/G3？→ 是 → 应合（提效/字幕）
  ├─ 落进 G4？→ 是 → 低风险合（体验/中文）
  ├─ 落不进任何目标？→ 否 → 关闭
  └─ 违背 G4（巨型/Slop/重复）→ 否 → 拒绝
```

---

## 六、长效机制（让「目标贡献」成为习惯）

1. **每个 PR 的合并说明里，写一句「为何合」**：例 `merge #803: 服务 G1，录制中点击穿透`。
2. **每季度回看一次**：已合 PR 是否真的带来了 G1–G4 的改善（用录课冒烟耗时做度量）。
3. **对社区 PR 的拒绝/关闭，统一用三问结果回复**，让贡献者明白「不是你的代码不好，是不服务当前目标」。

---

## 七、给执行者的一句话

> 合并前自问：**「合了这个，培训师录软件操作会更容易吗？」** 答不出「是」，就不合。
> 这就是「确保目标贡献」的全部。
