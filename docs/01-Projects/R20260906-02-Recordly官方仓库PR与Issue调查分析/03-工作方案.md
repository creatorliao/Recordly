# 03 · PR 分类汇总与工作方案

> ⚠️ 过程稿。阶段一仍含 macOS。**执行以 [`12-综合完善方案.md`](12-综合完善方案.md) 为准。**

> 核心原则（再次钉死，一切据此判断）：
> 1. **目标**：培训师，录软件操作，走通「启动录制 → 停止 → 编辑 → 导出视频」完整路径
> 2. **诉求**：减轻剪辑工作量 · 字幕/配音
> 3. **底线**：功能完善、体验良好，**不过度设计**（宁可少而稳，不要大而危）

---

## 一、PR 分类汇总（一表看清）

以 100 个 open PR 为基数，按「对你的价值」重新归类：

| 类别 | 数量 | 一句话定性 |
|------|------|-----------|
| **A. 核心路径可靠性**（点得动/有声音/存得了/导出顺） | ~15 | 必须合，否则录不了课 |
| **B. 教学提效**（按键叠加/区域录制/裁剪/降噪） | ~8 | 应合，直接省剪辑时间 |
| **C. 字幕配音**（字幕运行时/降噪/SenseVoice） | ~3 | 你的点名诉求 |
| **D. 中文与文档** | ~5 | 零风险，顺手合 |
| **E. 平台修复（非主平台）** | ~15 | Linux/macOS 细分，按目标平台取舍 |
| **F. 冷门/增强**（headless/自动化/GIF/新语言） | ~15 | 可选，不伤核心 |
| **G. 过度设计/高风险**（巨型 Slop） | ~12 | 坚决不碰 |
| **H. 重复/可关闭** | ~10 | 合并其一，其余关闭 |

> 详细逐条分级见 [`02-PR分级建议.md`](02-PR分级建议.md)。

## 二、工作方案（四阶段）

### 阶段一：保命（目标：完整路径先跑通）

**做什么**：合并 A 类「点得动 + 有声音 + 存得了」的 P0 PR。

**具体清单与顺序**：

| 顺序 | PR | 动作 | 验收标准 |
|------|----|------|---------|
| 1 | #875 | 合 | macOS 选窗口录制，焦点不丢、目标软件可操作 |
| 2 | #803 | 合 | 录制时点得到被录软件的按钮 |
| 3 | #797 / #845 / #730 | 三选一/选一干净方案 | HUD 不再吞点击、不挡屏幕 |
| 4 | #785 | 合 | Windows 麦克风全程不断 |
| 5 | #825 | 合 | macOS 麦克风保留，字幕能从音频生成 |
| 6 | #796 | 合 | Windows/Linux 能保存/打开项目 |
| 7 | #712 | 合 | 自动字幕生成流程可靠 |
| 8 | #855 | 合 | VFR 录制下编辑器不冻结 |
| 9 | #777 | 合 | 麦克风降噪可选 |
| 10 | #823 + #874（或 #865） | 合 | 中文标签正确、文档不再误导 |

**风险管控**：
- 合并前帮对方 **rebase 到最新 main + 重跑 CI**（这些 PR 大多 `DIRTY`/`UNSTABLE`）。
- #803/#797/#845/#730 同属 HUD 点击穿透，**合并时会出现冲突**，先定一个「主方案」，其余关闭并感谢。
- 每合一个，跑一遍「录 → 停 → 编 → 导」冒烟测试。

### 阶段二：提效（目标：剪辑量降下来）

**做什么**：合并 B 类「教学向 + 省剪辑」的 P1 PR。

| 顺序 | PR | 动作 | 为什么 |
|------|----|------|--------|
| 1 | #733 | 合 | 按键叠加，教软件操作时展示快捷键，教学价值最高 |
| 2 | #774 | 合 | 区域录制，只录目标软件区域 |
| 3 | #732 | 合 | 拖拽裁剪 + 宽高比锁定 |
| 4 | #719 | 合 | 录制目标高亮 |
| 5 | #710 | 合 | 补九语种漏字（中文体验） |
| 6 | #790 | 合 | 选源后自动开始录制 |

**验收标准**：录一节 10 分钟软件操作课，从录完到导出 ≤ 15 分钟（修剪 + 自动缩放 + 字幕 + 导出）。

### 阶段三：按需（目标：不主动扩张）

**做什么**：F 类冷门增强 + E 类非主平台修复，**按实际需求触发，不主动合并**。

| 触发条件 | 才合 |
|----------|------|
| 有脚本/批量出片需求 | #864 headless CLI、#817 自动化 API |
| 露脸讲解且在意美观 | #835 摄像头虚化 |
| 大量导出 GIF | #598、#520、#655 |
| 明确要支持 Linux 用户 | #863/#876、#808/#786/#768/#767/#705 等 Linux 修复 |
| 明确要支持某新语言 | #691/#664/#734/#316 |

**做什么**：处理 G 类巨型 Slop PR 和 H 类重复 PR。

| 对象 | 处理 |
|------|------|
| #794（+25k 行 GPU 导出） | ❌ 拒绝，理由：动导出核心、标 Slop、风险极高 |

**给社区的措辞建议**（关闭时）：
> "Thanks for the contribution! This is a great direction, but the scope is larger than we can review safely right now. Could you split it into smaller, focused PRs? We'd love to review a narrowed version."

## 四、长期维护原则（写给未来的每一次 PR 评审）

1. **先问「对培训师录课有没有用」**，再问「改动大不大」——两者都过才合。
2. **改动 >500 行自动进入高审慎模式**，>2000 行基本拒绝，除非能拆小。
3. **带 Slop 标签的一律重写**，不接受原样合并。
4. **同一主题多个 PR 只合一个**，其余关闭并引导协作。
5. **每合一个 P0/P1，必须跑「录→停→编→导」冒烟**，保证不引入回归。
