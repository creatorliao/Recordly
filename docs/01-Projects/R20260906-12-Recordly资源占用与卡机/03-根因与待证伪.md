# 03 · 根因与待证伪

> 分两类：**源码已经能定的设计根因**，和 **必须真机 + 资源日志才能钉死的**。后者禁止假装已经量过。

## 1. 已能定的根本原因（设计，不是猜测）

### R1 · 采集默认按「最高档」而不是「培训够用」

目标 4K、60fps、十几到几十 Mbps，写死在业务常量里，没有「本机是 1080p 办公本就降档」。  
**这是整机卡、磁盘忙、GPU 编码排队的主因候选。** 落 G1/G4。

### R2 · 进程栈默认全开，没有让路

Electron 多进程 + WGC 编码 + 光标 hook/遥测 + HUD，录的时候同时转。  
整机核数少或核显时，采集跟不上 → 成片卡、光标采样间隙变大（对上 09），同时前台被录软件也卡。

### R3 · 编辑 / 导出默认继续按源画质合成

预览 60fps GPU 合成；导出默认 `source`。录完进 Studio 若源是 4K60，预览和导出会再吃一轮。  
用户说「用这个工具」——不一定只发生在按红钮那几分钟。

### R4 · 重活不互斥、字幕不限核

Whisper 可打满 CPU；与导出/预览没有队列。培训师若「一边生成字幕一边拖时间轴」，整机假死符合这条。

### R5 · 看不见消耗，所以无法运营

不是卡的物理原因，但是**查不下去的原因**。没有 `resource.snapshot`，R1–R4 哪个在你这台机器上占主因，无法证伪。

## 2. 还要继续调查（未证伪）

| 编号 | 问题 | 怎么证 |
|------|------|--------|
| U1 | 卡在录、停后 mux、进编辑器、导出，还是字幕 | 会话日志相位 + 同时刻资源快照 |
| U2 | 你的屏是 1080 还是 4K；实际编码分辨率是多少 | `recording.start` 写下宽高/fps/码率 |
| U3 | 走的是 WGC 还是浏览器 `getDisplayMedia` | `capture.backend` |
| U4 | 编码器是硬编还是软编（软编会吃光 CPU） | helper 日志 / Media Foundation 失败回退（**当前没落盘**） |
| U5 | 磁盘是否被高码率写满（机械盘 / 杀毒扫描） | 快照里写 `disk` 粗指标或 mux 耗时异常 |
| U6 | 编辑器空闲是否仍 60fps 空转 | 真机看 GPU；日志可记 ticker started |
| U7 | 是否同时开了字幕 + 导出 + 预览 | 金路径事件是否重叠 |
| U8 | 核显 vs 独显、内存是否 8G 级 | 启动头写 GPU 名、总内存（可从系统信息拿，不做驱动探测全家桶） |

U 项没齐之前，**不把某一条优化当唯一解药**，但 R1–R4 已经够定方向：先可观测，再把默认档降到培训够用。

## 3. 与 09 的关系

- 整机打满 → 采集丢帧、光标 33ms 采样漂移 → 成片卡、鼠标跟不上。  
- 09 仍可能另有时钟/合成 bug；**先用资源日志分开「机器忙」和「算法错」**，再决定 09 动不动合成代码。
