# 02 · 调查分析：占用大户与默认策略

> 依据：2026-09-06 仓库源码。结论以文件为准。  
> **全库没有** `process.memoryUsage` / `app.getAppMetrics` / `getProcessMemoryInfo`：磁盘上目前写不出 CPU/内存账。

## 1. 总判断

Recordly 默认按「能录到的最高画质」设计，不是按「培训机还能同时讲课」设计。

Windows 金路径上，一次录制至少叠这些：

| 进程 / 线程 | 做什么 | 默认有多猛 |
|-------------|--------|------------|
| Electron 主进程 + 渲染 + GPU + 网络 | 壳、HUD、设置、IPC | Chromium 本身就不轻 |
| `wgc-capture.exe` | WGC 采屏 + Media Foundation 编码 | **硬编码 `fps: 60`** |
| `cursor-monitor.exe` | 低级鼠标钩 + 每 10ms 泵消息 | 轻，但整机忙时会拖采样 |
| 主进程光标遥测 | 每 **33ms** 采一点（约 30Hz） | 中等；忙时会漂，对上 09 |
| 窗口模式：每 250ms 刷 bounds | `startWindowBoundsCapture` | 轻 |
| 停录后 FFmpeg | mux 音视频 | 短时尖峰 |
| 编辑器 Pixi | 预览 ticker **`maxFPS = 60`**，默认开缩放运动模糊 0.35 | GPU 持续转 |
| 导出 | 默认质量 **`source`**（跟源分辨率走） | 4K 源可到约 45 Mbps 档 |
| Whisper `ggml-small` | 字幕；**没有限制线程数** | 容易打满所有核 |

这些可以叠在同一台机器上（例如编辑器还开着又去导、或导的同时点字幕）。源码里**没有**「重活互斥」或「按机器降档」。

## 2. 采集：默认 4K / 60fps / 高码率

浏览器回退路径（`src/hooks/useScreenRecorder.ts`）：

- `TARGET_WIDTH/HEIGHT = 3840×2160`，`TARGET_FRAME_RATE = 60`
- `getDisplayMedia` 的 `ideal/max` 就是这两项；锁不住时才退到「当前能拿到的」
- 码率：4K **45 Mbps**，QHD **28 Mbps**，其余 **18 Mbps**
- 60fps 再乘 **1.7** → 4K60 约 **76.5 Mbps**

Windows 原生 WGC（`electron/ipc/register/recording.ts` + `mf_encoder.cpp`）：

- 启动配置写死 `fps: 60`，没有按显示器刷新率或机器能力降
- 码率档与上面同量级（4K 45 / QHD 28 / 基线 18），60fps 乘 **1.35** → 4K60 约 **60.8 Mbps**
- 分辨率跟被录显示器/窗口走：4K 屏就是 4K 编码

培训课多数是 1080p 窗口 + 30fps 就够。当前默认等于按直播/演示片规格压磁盘和 GPU。

## 3. 同时开着的窗口

`electron/windows.ts`：编辑器窗口 + 全屏 HUD overlay（录的时候还在）+ 可选倒计时窗。  
录的时候 Chromium 至少两块 WebContents 活着，再加原生采集进程。没有「开录就停掉编辑器 GPU ticker」这类让路。

## 4. 编辑器预览

`VideoPlayback.tsx`：`app.ticker.maxFPS = 60`。  
默认 `DEFAULT_ZOOM_MOTION_BLUR = 0.35`（开着）。预览是 WebGL/WebGPU 合成（光标弹簧、点击特效、缩放），不是「只播一个 `<video>`」。  
停在时间轴上是否仍 60fps 空转，要真机对 ticker 是否 `stop`；源码里暂停路径会 `ticker.stop()`，播放路径会再 `start()`。**空闲时是否完全歇着，还要验。**

## 5. 导出默认「源画质」

`projectPersistence.ts`：未指定时 `exportQuality` → **`source`**；`mp4FrameRate` 默认 **30**。  
`exportBitrate.ts`：source + 4K → **45 Mbps** 档。  
导出若走浏览器逐帧（`modernFrameRenderer` / WebCodecs）会再吃一轮 GPU+内存；原生 GPU 导出走 FFmpeg/CUDA，会和桌面抢同一块卡。

## 6. 字幕

`generate.ts`：whisper-cli **没有 `-t` 线程上限**。whisper.cpp 常见行为是尽量用满核。  
small 模型相对 medium 已经小，但「打满 CPU」仍足以让整机假死几分钟。

## 7. 日志侧缺口（为何「不知道为什么」）

`R20260906-11/03` 已证：没有会话日志。本主题再补一条：

- 连一次资源快照都没有，无法回答「卡在录、编、导、还是字幕」
- 成片旁 `*.recording-diagnostics.json` 只有 mux/探测，没有 CPU/内存/子进程

所以「继续调查」的下一块必须靠 **11 的资源事件**，不能再靠猜。
