## 2. 同一块预览里谁画什么

`VideoPlayback` 从上到下三层：

```
底：resolvedWallpaper（CSS url / data URL / 纯色）     ← 线 A
中：Pixi 把隐藏 <video> 贴成精灵，ticker 跟帧         ← 线 C
上：字幕 overlay / 摄像头泡 / 光标                      ← 线 B 只往 overlay 填字
```

停预览（`suspendRendering`）只停中层：ticker.stop、`<video>` pause。  
底层壁纸继续在，所以上层空转时你会觉得「只剩背景在闪」。

线 A 的 `wallpaper` 是路径（如 `/wallpapers/xxx.jpg`），解析一次出 data URL 并缓存。依赖是 `[wallpaper]`，换图才再解析，**不会每帧重读图**。  
线 B 生成字幕不改 `videoPath`、不 `remountPreview`，不拆视频纹理。

所以：**读图修好不会导致播不了；字幕修好也不会自己拆预览。** 能拆预览的只有 C 的 `preview-yield`。

## 3. 真交叉点（有，但窄）

### 3.1 P2 把 B 的「生成中」接到了 C 的停预览

`captions.ts` 一开始 `setSessionLogPhase("captions")`，结束或失败再回 `editor`。  
P2 把 `captions` 算进让路：**识别时预览停，避免 Whisper 和 60fps 合成抢核。**

这是故意的互斥，不是 bug：

- 没点「生成字幕」→ 相位不是 `captions` → 不影响回放  
- 你截图开的是背景面板，不是字幕面板 → **这次闪屏与 B 无关**  
- 导出时点生成会被拒（`export` 相位互斥）→ B 与导出也不抢

本轮 C 的修复：**让路只留 `export` / `captions`。**  
B 仍然：生成那几秒预览静止，完了继续播。不要为了「字幕已正常」把 captions 让路也拆掉，否则识别时整机又容易卡（对上本夹 R4）。

### 3.2 A 与 C 没有共享开关

壁纸 IPC / data URL **不写会话相位，不发 `preview-yield`。**  
C 停 ticker 也 **不重新 resolve 壁纸**。  
两条路不相交。A 修好之后，C 一坏，症状会更「像只有背景」——因为背景终于画出来了。

### 3.3 停录时序：mux 与「立刻能播」对着干（C 自己的矛盾）

`useScreenRecorder`：mux 后台跑，好让编辑器马上播主视频。  
P2 却在 `mux` 相位停预览。  
这是闪屏主因，见 `10` R1。与 A、B 无数据依赖。

## 4. 综合判断（会不会有了 A/B 就没了回放）

| 组合 | 互斥？ | 怎么共存 |
|------|--------|----------|
| A 读图 + 回放 | 否 | 背景层 / 视频层分开。保持 A，只修 C |
| B 字幕生成 + 回放 | **短时互斥** | 默认能播；点生成才停预览；完了恢复。老路径不变 |
| B 字幕 + 导出 | **真互斥** | 导出中拒绝生成。已落地，保持 |
| A 读图 + B 字幕 | 否 | 各走 IPC：壁纸 data URL vs Whisper 文件 |
| C 让路 + 刚停录回放 | **曾误互斥** | 已收回 `recording`/`mux` 让路 |

没有「修了字幕/读图就必须牺牲回放」。  
也没有「回放一修，图和字幕会再裂」——本轮不动 `assetPath` / Whisper 查找。

代决：保持现状分层，不再为「看起来像一回事」去改 A/B 的代码。

## 5. 你怎么验这三件事没互相踩

一次启动、同一个工程即可，不必拆三次：

1. 进 Studio：背景 → 图片，格子有图；预览铺得上选中的图（A）  
2. 立刻点播放：画面跟时间轴走、有声、不闪（C）  
3. 再点生成字幕：生成那几秒预览可以停；完成后字幕上时间轴，再点播放仍正常（B + C 短时互斥）  
4. 不要在导出中途点生成（应提示等一下）
