# 分析报告：录制 → 结构化存储 → 模型理解 → 回放

> 调查日：2026-09-06。本夹仍处调查研究，不改产品代码。  
> 读者：RPA 专家，目标是做 **Windows / macOS 的 AI+RPA**（录一次，自动化回放，配套大模型理解）。  
> 本报告只论证你提出的三条路径，并回答：可行吗、合理吗、有没有同类开源。

相关底稿：[`02`](02-调查_Recordly现有实现.md)（Recordly 记了什么）、[`03`](03-调查_开源项目与线上方案.md)（仓库清单）、[`04`](04-方案_可选路径与决策建议.md)（底座选型）。

## 0. 被论证的路径（原设想）

```text
① 操作记录   专门工具记下轨迹：点了哪些「DOM」、坐标在哪、（隐含）键鼠
② 数据存储   写入结构化文档
③ 模型分析   大模型读档，理解操作逻辑与步骤，并据此复现
```

产品能力要求：录制、解析、复现；**录制一次，自动化回放**；模型负责理解。

先给判断，再展开证据。

| 问题 | 判断 |
|------|------|
| (a) 可行吗 | **可行**，但必须把「DOM」改成「分层定位器」，并把模型从「每次回放都推理」挪到「编译 / 漂移修复」 |
| (b) 合理吗 | **作为 AI+RPA 主路径合理**；若③变成每步看屏再点，则合理变成 Computer-Use，不再是 RPA |
| (c) 有类似开源吗 | **有，且已形成明确品类**：最同构的是 OpenAdapt；网页侧有 Stagehand / Midscene；传统开源 RPA 有录放但弱在「模型编译」 |

## 1. 这条路径在产业里叫什么

你写的不是新发明。2025–2026 开源与厂商已经把它拆成两种产品，名字不同、金路径不同：

| 品类 | 金路径 | 健康回放要不要模型 | 代表 |
|------|--------|--------------------|------|
| **演示编译 / AI+RPA** | 录轨迹 → 结构化证据 → **编译成程序** → 确定性回放 | **不要** | OpenAdapt；Stagehand 的 cache/self-heal（网页） |
| **Computer-Use 智能体** | 目标描述 → 每步截图 → 模型规划点击 | **要** | UI-TARS、Claude Computer Use、Agent-S |

[OpenAdapt 自己的对照表](https://openadapt.ai/compare) 把这一点写死了：

- 传统 RPA：选择器 + 流程图，回放确定，修选择器靠人。
- Computer-Use：新任务每次重规划。
- 演示编译：录一次，编成可检查的程序；界面漂了先用证据重解析，再可选让模型提修复，过不了就停。

你要的「录制一次，自动化回放」+「配套大模型理解」，在产业定义上应落在**第一类**。  
若把③理解成「每次回放都让模型重新理解」，你做出来的是第二类，和 RPA 专家要的交付物（可回归、可验收、可算成本）冲突。

**论证结论：路径方向对；③的默认语义必须改成「编译时理解 + 漂移时修复」，不能是「回放时理解」。**

## 2. (a) 是否可行

### 2.1 可行的充分条件

三条都做成，且回放稳定，需要同时满足：

1. **记录不是只有坐标**  
   至少：时间、键鼠、前台窗口（进程/标题/边界）、点击瞬间截图、当时能拿到的结构树（DOM 或 UIA 或 AX）。  
   只有 `cx/cy`（Recordly 那种）→ 模型能看片复述，**不能**编出可维护机器人。证据见 [`02`](02-调查_Recordly现有实现.md)。

2. **「DOM」改成定位器阶梯，而不是一种树**  

   | 表面 | 结构真源 | 桌面是否还有「DOM」 |
   |------|----------|---------------------|
   | 浏览器 / 开了 CDP 的 Electron | Chromium DOM | 有，和网页 RPA 同构 |
   | 标准 Win32 / WPF / 部分 Qt | UI Automation 树 | 无 DOM，有等价树 |
   | macOS AppKit | Accessibility (AX) | 同上 |
   | 自绘（微信 4.x、企微 4.x DirectUI） | 经常空树 | 无；只能图像/OCR/热键 |

   字面「记录操作了哪些 DOM」在 Windows/Mac **全桌面**上不可行；在 Electron/网页上可行。  
   工程上可行的说法是：**记录当时最强的定位器 + 全部弱证据**（坐标、图、OCR 字）。

3. **存储必须是「步骤」，不是 30Hz 点列**  
   模型吃的应是：`stepId / action / targetCandidates[] / beforeShot / afterShot / typedText / window`。  
   原始钩子流可以留作附录，分析阶段先压缩。

4. **复现走执行器，不走「模型手搓鼠标」**  
   编译产物指向：Playwright（DOM）、FlaUI/pywinauto（UIA）、AX API、Sikuli/OCR。  
   模型输出的是**带定位器的步骤表 + 成功判据**，不是像素级模仿。

5. **有成功判据**  
   「看起来点过了」不够。RPA 要：文本变了、窗出来了、文件在了、或独立读库。OpenAdapt 用实验说明：只看屏幕验收，90 次注入错误里会放行 54 次；加一条屏外核对可降到 9/90。

这五条都满足时：**路径可行**。缺 1 或 2，③会变成看片幻觉；缺 4 或 5，产品是助手不是机器人。

### 2.2 不可行的几种误解

| 误解 | 为什么断 |
|------|----------|
| 全桌面都有 DOM | 微信/企微自绘已把 UIA 打断，更没有 HTML |
| 坐标 + 大模型 = 稳定回放 | 分辨率、DPI、窗位置、主题一变就废；模型补救成本高 |
| 录完直接把 JSON 扔给模型去「操作电脑」 | 那是 Computer-Use，每次都推理，难验收 |
| 用 Recordly 的 `*.cursor.json` 当 archive | 缺键盘、缺窗、缺结构，见 `02` |

### 2.3 Windows / Mac 可行性差一档

| | Windows | macOS |
|--|---------|-------|
| 钩子 | `WH_MOUSE_LL` / uiohook，工程成熟 | 辅助功能权限；钩子启动不当会卡主线程（Recordly 因此在 macOS 跳过 uiohook） |
| 结构树 | UIA3（FlaUI / pywinauto） | AX API，覆盖面看应用是否暴露 |
| Electron | 两边都是 CDP，对称 | 同左 |
| 权限与分发 | 管理员/DPI 感知 | 辅助功能 + 屏幕录制授权，用户必须点一次系统设置 |
| 自绘客户端 | 同样难 | 同样难 |

跨端**可行**，但是「一套录制器、两套结构后端、一套编译 IR」。不要幻想一份 DOM 日志通吃。

## 3. (b) 是否合理

### 3.1 对 RPA 专家为什么合理

你要的不是「会用电脑的聊天机器人」，而是：

- 人做一遍（示教）；
- 机器以后自己做（机器人）；
- 模型帮忙读懂示教、绑定位器、界面变了再修。

这正好补上传统开源 RPA 的短板：

| 传统开源 RPA（TagUI、OpenRPA、RPA-Python） | 你的设想补的那一层 |
|--------------------------------------------|-------------------|
| 人写 flow / 选图 / 录较脆的选择器 | 模型从结构化轨迹**归纳步骤与意图** |
| 回放确定，这点要对 | 保持：健康路径不调模型 |
| 界面一变就要人改 | 模型参与**修复编译产物**，不是现场乱点 |

所以：**①②完全合理；③合理当且仅当它是编译器/分析器，不是执行器。**

合理的闭环应写成四步，而不是三步：

```text
① 记录   多层证据（结构 + 坐标 + 图 + 窗 + 键盘文本）
② 存储   原始轨迹 + 压缩后的步骤文档（IR）
③ 理解   模型：去噪、合并、命名意图、绑定定位器、写出成功判据
④ 回放   执行器跑 IR；失败则停或触发③再编译，而不是边跑边猜
```

少第④、把③兼执行，路径就会从「合理的 AI+RPA」滑向「每次都贵、每次都飘的智能体」。

### 3.2 和「只坐标 / 只 DOM / 只视觉」比，为什么这条更合理

| 只做一种记录 | 问题 |
|--------------|------|
| 只坐标 | 便宜、全平台，回放脆；模型也救不了窗一挪 |
| 只 DOM | Electron/网页完美，微信/企微交白卷 |
| 只视觉（每步 VLM） | 覆盖自绘，成本高、难回归、难合规审计 |
| **结构优先 + 视觉锚 + 坐标垫底**（你的路径补全后） | 有树用树，没树用图，坐标只当最后一档 |

这是 RPA 里经典的 **selector 阶梯**，只是多了一个「模型来写/修阶梯」的编译步。合理。

### 3.3 不合理的膨胀

- 第一期就承诺微信 + 企微 + 任意 Electron + 双系统同等品质。  
- 模型既理解又实时操控，还没有停机条件。  
- 把培训向录屏器（Recordly）和 RPA 录制器做成同一个进程。

这些会让一条合理路径在实施上变得不合理。

## 4. (c) 有没有类似的开源项目

按「和你三条路径的同构程度」排，不是按星数排。

### 4.1 同构最高：录 → 结构化证据 → 编译 → 确定性回放

| 项目 | 许可 / 星（约） | 同构点 | 缺口 |
|------|-----------------|--------|------|
| [OpenAdapt](https://github.com/OpenAdaptAI/OpenAdapt) + [openadapt-flow](https://github.com/OpenAdaptAI/openadapt-flow) + [openadapt-capture](https://github.com/OpenAdaptAI/openadapt-capture) | MIT / 主仓 ~1.7k，引擎仍 Beta | **几乎就是你的路径**：录真实点击键入；编译成本地程序；健康回放零模型；Win UIA / Mac AX / 浏览器 / RDP | 对微信/企微自绘未担保；要资格认证；中文 IME 需自验 |
| 定位器阶梯（官方文档） | 每步保留裁剪模板、OCR、几何；回放按档解析 | 即「DOM/控件 + 坐标 + 图」同时存 | — |

这是目前开源里**唯一把「示教编译成可验证程序」写成产品合同**的桌面+网页栈。  
对「AI+RPA、录一次回放」应作为第一对照物，而不是 UI-TARS。

### 4.2 同构在网页、逻辑可搬到桌面 IR

| 项目 | 许可 / 星（约） | 同构点 |
|------|-----------------|--------|
| [Stagehand](https://github.com/browserbase/stagehand) | MIT / ~2.4 万 | 自然语言 + Playwright 代码；可缓存，健康路径少推理；变了再让 AI 修 |
| [Midscene](https://github.com/web-infra-dev/midscene) | MIT / ~1.5 万 | 截图/视觉理解网页 UI（含 canvas）；偏测试智能体 |
| 你已有的网页 rpa-agent 录制 | 私有/本机 | 已经是 ①②③④ 在 **DOM 表面**上的实现 |

桌面要抄的是它们的 **IR 与「先缓存后自愈」**，不是把浏览器 SDK 硬套到微信上。

### 4.3 传统开源 RPA：有录放，弱在「模型理解」

| 项目 | 许可 / 星（约） | 有①②④吗 | 有③吗 |
|------|-----------------|-----------|--------|
| [TagUI](https://github.com/aisingapore/TagUI) | Apache-2.0 / ~6.3k | 有。flow 可读；支持 DOM 标识、**png 找图**、**(x,y)**，Win/Mac/Linux | 弱。人写或插件录；AI 只是可另接 |
| [OpenRPA](https://github.com/open-rpa/openrpa) | MPL-2.0 / ~3.1k | 有。企业级编排、Windows 桌面强 | 弱。经典选择器 RPA |
| [RPA-Python](https://github.com/tebelorg/RPA-Python) | Apache-2.0 / ~5.5k | 有。Python 调键鼠/视觉 | 无编译器 |
| pywinauto / FlaUI / FlaUI-MCP | BSD / MIT | **只有④**（执行）+ 可快照树 | 无录制编译 |

它们证明：**「结构化步骤文档 + 回放」在开源 RPA 里早就合理**。  
你要加的是 TagUI 没有做成产品的那一层——**从示教轨迹自动写出/修好 flow**。

### 4.4 看起来像、其实是另一条路

| 项目 | 为什么不像你的路径 |
|------|-------------------|
| UI-TARS Desktop、Agent-S、UFO、OmniParser | 强在「看懂屏幕」；弱在「编成可回归机器人」。适合当③的感知插件 |
| wxauto / pywechat / wx_work_auto | 应用专用 API，不是通用录制器 |
| Recordly | 成片遥测，不是 RPA archive |

### 4.5 一句话对照

```text
你的设想     =  传统 RPA 的录放（TagUI/OpenRPA）
              + 示教编译与模型修定位器（OpenAdapt / Stagehand）
              + 无树时的视觉档（OmniParser / Sikuli / TagUI 找图）

还不是       =  每步都让 UI-TARS 玩电脑
```

## 5. 建议写进产品规格的「正确版本」

给后续方案（确认后）直接用的合同句，避免三条路径在落地时走样：

1. **记录**：专门录制器同时写四类证据——结构命中（DOM 或 UIA 或 AX，允许空）、坐标、点击帧、窗口身份；键盘记「提交后的文本」而非每个扫描码。  
2. **存储**：原始 JSONL + 压缩后的步骤 IR（给模型、也给人审）。  
3. **理解**：大模型只在编译、人工修订、回放失败后的修复这三处出场。  
4. **回放**：执行器跑 IR；健康路径零模型；失败停机并带步骤号，禁止盲点。  
5. **范围**：Win/Mac 一套 IR，两套结构后端；Electron 复用网页录制；自绘客户端单独资格认证。

## 6. 总答复（给拍板用）

**(a) 可行。** 零件都在：钩子、UIA/AX/CDP、找图、模型。不可行的是「全桌面都当 DOM」和「只存坐标就让模型复现」。

**(b) 合理。** 这是当前开源与厂商共同收敛的 **AI+RPA** 形态，比纯智能体更符合「录一次、自动化回放」。合理性取决于模型待在编译侧。

**(c) 有类似项目。** 桌面+网页最同构：**OpenAdapt 家族**。网页侧 **Stagehand / Midscene / 你已有的 rpa-agent**。传统开源 RPA **TagUI / OpenRPA** 证明录放合理，但缺模型编译。Computer-Use 仓库当感知，不当母体。
