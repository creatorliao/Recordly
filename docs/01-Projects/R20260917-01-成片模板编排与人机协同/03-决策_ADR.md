## ADR-01 · 工具形态：独立 CLI + 伴生 Skill

### 背景

用户提出两种可能：「相对独立的工具」或「Recordly 给我提供相关的 API 或 CLI」。

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 调 Recordly 的对外 API | ❌ **不存在**。全仓无 WebSocket、无 express、无 CLI（`package.json` 无 `bin`）、IPC 不可外部达（`contextIsolation: true`）。两个 HTTP 服务：`mediaServer` 仅 `GET /video?path=` 且鉴权是**进程内路径白名单**、端口随机（`mediaServer.ts:85-91`）；`rendererServer` 只服务静态 `dist/`。**这条路是死的。** |
| B. 改 Recordly 源码，内置面板 | ⚠️ 可行性有，但代价高：AGPL 仓、要跟上游 `git pull`、跨平台构建链（原生 helper）、每次上游变更都要维护 |
| C. 独立 CLI + 伴生 Skill，通过文件与环境变量协作 | ✅ 与家族现有三个工具（`rlex`/`rlz`/`rld`）同构；零 Recordly 源码耦合；可测、可脚本化 |
| D. Electron 扩展（`registerRenderHook`） | ⚠️ 扩展 API 存在，但**拿不到字幕数据**：扩展设置只支持标量字段（`EXTENSIONS.md:208`），字幕条是数组 |
| E. 记录式 GUI 宏（自动点界面） | ❌ 脆弱、不可测、无法无人值守 |

### 决策

**选 C。** 独立 Python CLI + 伴生 Skill，复用 `RECORDLY_SMOKE_EXPORT*` 公开契约与 `.recordly` 文件格式。

### 理由

1. **A 不是"不选"，是"没有"** —— 这是本轮调研最硬的结论，见 `04` §7。
2. 家族已有三次同样的落地（`recordly-export` / `recordly-zoom` / `recordly-deliver`），模式被验证过。
3. C 让工具**离线可测**：编排层是纯文本变换，不需要 Recordly 在场（对比 `rlz` 就是"纯离线、不需要运行体"）。
4. D 看似诱人（能在预览与导出里都画），但**字幕条数据进不了扩展**，等于要另起一套字幕数据源，反而更复杂。

### 后果

- ✅ 工具可在无 Recordly 的机器上完成"编排 + 校验"，只在最后一步需要运行体
- ✅ 不碰 AGPL 源码，许可清爽
- ⚠️ 必须自己处理与 Recordly 的数据契约演进（`.recordly` 版本变化）
- ⚠️ 无法改变 Recordly 的渲染行为（字体、水平位置）—— 转入 ADR-05

### 前提

`RECORDLY_SMOKE_EXPORT*` 与 `.recordly` 字段名继续作为公开契约存在（`recordly-export-master/AGENTS.md:77-84` 已认可）。

## ADR-02 · 命名与边界

### 背景

家族命名：`recordly-export`(`rlex`) / `recordly-zoom`(`rlz`) / `recordly-deliver`(`rld`)。
新工具需要一个不冲突、能自解释的名字，并划清与 `rlex` 的边界。

### 选项

| 候选 | 问题 |
|:---|:---|
| `recordly-caption-master`(`rlc`) | "caption" 太窄 —— 本工具还要处理内容文档进画面 |
| `recordly-template-master`(`rlt`) | 只覆盖了模板，没覆盖"人机协同"与"项目化" |
| `recordly-project-master`(`rlp`) | 与 `rlex` 的"离线编排项目"职责重叠，易混 |
| **`recordly-compose-master`(`rlc`)** | ✅ 覆盖"编排/合成"，与 `rlex` 的"导出"区分明确 |

### 决策

**仓名 `recordly-compose-master`，CLI `recordly-compose`，别名 `rlc`。**

### 与 `rlex` 的边界（重要）

| | `rlex`（recordly-export） | `rlc`（recordly-compose，本工具） |
|:---|:---|:---|
| 出发点 | **录屏** | **已有 MP4 + 文档** |
| 核心能力 | 样式预设 + 离线编排 + **无头导出** | **模板编排 + 人机协同 + 项目化** |
| 字幕 | 明确声明"不碰字幕内容" | **以字幕/模板为核心** |
| 与对方的关系 | —— | **调用 `rlex export run` 出片，不自研渲染** |

> **一句话**：`rlex` 管"从录屏到成片的样式"，`rlc` 管"从既有素材到成片的模板与协同"。
> **`rlc` 不重复实现导出** —— 这是不变量。

### 后果

- `rlc` 的 `export` 子命令是 `rlex` 的**薄封装**（构造调用、回读报告），不是新渲染器
- `rlc` 依赖 `rlex` 已安装；缺失时给明确修复指令（家族惯例：懒装/自愈）

## ADR-03 · 事实源：纯文本副本 vs `.recordly`

### 背景

**【已读源码确认】** `.recordly` 的往返是**双向有损**的（`04` §2.5.3）：

- 5 组字段**完全不读输入**：`fontFamily`、`zoomSmoothness`、`cursorMotionBlur`、`exportPipelineModel`、`zoomMotionBlurTuning.*`
- 9 个光标运动字段会**塌缩**到 `focused` 预设（人一动自由滑块 `cursorSize` 就触发）
- GUI 保存发出的是**固定字段清单**（`useProjectSnapshotModel.ts:74-140`），清单外的字段保存一次即消失
- 未知键一律丢弃（归一化返回全新对象字面量，枚举约 60 个键）

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 以 `.recordly` 为唯一事实源 | ❌ 人保存一次就丢字段；且数组字段 CLI 灌不进（`04` §2.4） |
| B. 自己另起一套 JSON 格式，出片时再转 | ❌ 与 Recordly 生态脱节，且无法把人的 GUI 改动读回来 |
| **C. 项目内保纯文本权威副本，`.recordly` 每次由工具再生** | ✅ 人机都好读写；人改 GUI 后 `pull` 回文本；再生时重新写入工具拥有的字段 |

### 决策

**选 C。** 项目结构：

```
<项目目录>/
  compose.toml            # 项目清单：素材、模板名、输出设置
  captions.srt            # D1 字幕文稿（权威副本）
  style.toml              # D3 样式参数（权威副本）
  media/                  # D2 内容文档转出的画面素材
  vendor/                 # 原样携带的 Recordly 侧车（.cursor.json 等）
  build/                  # 再生区（可整目录删除后重建）
    <name>.recordly       # ← 交给 Recordly 的制品
    <name>.mp4
    <name>.mp4.report.json
    review/               # 试穿产物
  .compose/
    state.json            # 交接锁、留痕、上次 pull 的指纹
```

### 理由

1. `captions.srt` / `style.toml` 是**人最快、AI 最好接**的格式（需求 P-3）
2. `build/` 可整体删除重建 —— 这让 `apply` 天然幂等（验收 A-6）
3. 人的 GUI 改动通过 `pull` 抽取回文本，**不依赖 `.recordly` 作为长期存储**
4. 再生时由工具写入它拥有的字段，天然规避了"清单外字段消失"

### 后果

- ⚠️ 必须自己维护"文本 ↔ `.recordly`"的字段映射表，并随 Recordly 版本演进
- ✅ `fontFamily` 的丢失**不影响** `style.toml` 的存储（只是渲染时无效）—— 见 ADR-05
- ⚠️ `pull` 必须是**显式动作**，且要报差异（验收 A-4）

### 前提

`.recordly` 的 `version: 2` 结构在 Recordly 1.4.x 期间稳定。

## ADR-04 · 并发与交接协议（应对 1 秒自动保存）

### 背景

**【已读源码确认】** 这是本轮最危险的发现（`04` §2.5.2）：

- `PROJECT_AUTOSAVE_DELAY_MS = 1_000`，只要 dirty 且已有路径，**1 秒后静默覆盖文件**（`useProjectSaveActions.ts:7, :176-191`）
- 全仓**无文件监听、无 mtime 冲突检测**（`grep fs.watch|chokidar|watchFile|FSWatcher` → 0 命中）
- GUI 不感知磁盘变化；AI 写盘会被人的下一次编辑静默冲掉（last-writer-wins）
- 无锁、无"文件已变更"提示

**如果我们什么都不做：AI 在人生成的会话期间写 `.recordly`，改动会无声消失。**

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 依赖文件 mtime 判断 | ⚠️ 可检测部分冲突，但 GUI 不检查 mtime，所以仍会覆盖；只能保护 AI 自己 |
| B. 用 `.bak` 做恢复 | ⚠️ `writeProjectFileAtomically` 已留 `.bak`（`atomicSave.ts:88-105`），可兜底但救不回"谁该赢" |
| C. 只读副本：给 GUI 一份 `build/<name>.recordly`，人改这份 | ✅ 简单，但 `pull` 仍可能与人并发 |
| **D. 显式交接锁 + 单向通行** | ✅ 最稳：同一时刻只有一方有权写 |

### 决策

**选 D，并叠加 C。** 具体规则：

| # | 规则 |
|:--:|:---|
| R1 | 工具写 `.recordly` **前**必须确认锁状态；锁被占（人有活跃会话）则拒绝写，并提示 |
| R2 | `rlc open` 时工具**先写制品、再落锁**，并把锁信息写进 `.compose/state.json`（时间、制品指纹、PID）；同时把制品放进 Recordly 的项目目录以便一次点击打开（见 ADR-10） |
| R3 | 人改完，必须显式执行 `pull`（或 `handoff-back`）。`pull` 成功后**释放锁** |
| **R4** | **（硬要求，`[修-9]`）** `pull` **必须**校验制品指纹：与落锁时不一致 → 人改过，走差异流程；一致 → 提示"没有检测到改动"。**指纹不符时不得静默覆盖，必须报差异** |
| R5 | 锁存在但超时（可配，默认 12h）→ 视为陈旧锁，警告后可 `--force` 接管 |
| R6 | 任何情况下，写盘前**先备份**到 `.compose/backup/<时间戳>.recordly`（在 Recordly 自带 `.bak` 之上再加一层） |

### 理由

1. **R1/R3 是唯一能真正避免 last-writer-wins 的办法** —— 因为 GUI 侧不可改、不可通知
2. 落锁时必须记**制品指纹**，否则无法区分"人改过"与"人没动"
3. **锁必须是文件而非内存态**（工具是短命进程，每次调用都是新进程）

### 后果

- ⚠️ 引入一个必须被遵守的协议；工具要提供 `status` 明确显示锁状态
- ✅ 人工干预变成**显式、可追溯**的动作（呼应需求 R-5 留痕）
- ⚠️ 人"忘了 pull 就关掉 GUI"是常见路径 → `status` 要能提示"锁未释放，可能有未回收的改动"

### 前提

**⚠️ 经 `08-场景走查.md` P-07 修正后，本 ADR 的前提发生了变化：**

原方案假定"人通过 `rlc open` 打开 Recordly"。但走查确认 **Recordly 无法被外部命令打开一个项目**
（无 CLI/API；`RECORDLY_SMOKE_EXPORT*` 只导出；`DEV_OPEN_RECORDING_INPUT` 打开的是视频；
IPC 仅应用内可达）——**详见新增的 ADR-10。**

因此：

- **人"绕过工具直接打开"不再是异常路径，而是主路径**
- 交接锁从"主要防线"降级为"辅助提示"
- **`pull` 的指纹校验（R4）成为唯一可靠防线**，这就是 R4 被提升为硬要求的原因

> 若上游未来提供 `--open-project <path>` 启动参数（已记入 `07-VOC`），
> 本 ADR 的原始设计（`open` 即落锁 + 布景）可以恢复。

## ADR-05 · `fontFamily` 困局

### 背景

**【已读源码确认 + 实测】** 字体不可控，且**绕不过去**：

- 归一化无条件重置：`projectPersistence.ts:785`（实测：13 字段里唯一被强制改写的）
- CLI 白名单也不含它（`rlex project validate` 报"未知字段"）
- 渲染读的是**归一化之后**的值：`modernFrameRenderer.ts:1638` 的 `settings.fontFamily`
  —— 所以**往文件里塞值没有用**，读回来就是默认值
- 默认字体栈 `'"SF Pro Text", "SF Pro Display", "Helvetica Neue", sans-serif'` **不含 CJK**

**⇒ "自己在工具侧绕过去"这个选项在技术上不存在。**

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 提上游 PR 修 `:785` | ✅ 一行改动；且**标注侧已有字体选择 UI**（`AnnotationSettingsPanel.tsx:227-257`）+ `AnnotationTextStyle.fontFamily`，说明能力现成，字幕侧更像遗漏 |
| B. 接受系统兜底字体 | ✅ 零成本，中文能显示（只是不是"清秀字体"） |
| C. 用 Electron 扩展在 `final` 相位自己画字幕 | ⚠️ 技术上可行（扩展在预览与导出都跑），但**拿不到字幕条数组**（扩展设置只支持标量），要另起数据源；且要关掉原生字幕，等于重写一层 |
| D. 放弃 Recordly 渲染，回到 ffmpeg + libass | ❌ 与 ADR-01/02 冲突，等于放弃本工具的意义 |

### 决策

**短期选 B，同时推进 A（提上游 PR）。明确不选 C 与 D。**

### 理由

1. **A 的成本极低**：单行改动（`fontFamily: rawAutoCaptionSettings.fontFamily || getDefaultCaptionFontFamily()`），
   加上字体栈补 CJK。风险面小，且标注侧有先例。
2. **B 已可用**：本轮实测确认中文字幕在白字无底框样式下渲染正常（`06`§2 抽帧目视），
   只是字体由系统决定。
3. **C 的隐藏成本被低估**：扩展拿不到字幕数据，要自带数据源 + 关闭原生字幕 + 自己实现
   排版/换行/动画，等于把 Recordly 的字幕引擎重写一遍，与本工具"不重造渲染器"的原则冲突。
4. **D 是退路不是方案**：`subtitle-burn` 已在做这件事，本工具的价值在编排与协同。

### 后果

- ✅ B 让工具**今天就能交付**（字体除外）
- ⚠️ 工具必须在 `style.toml` 里**照常保存 `fontFamily`**，并在渲染前**显式警告**
  "该字段本次渲染无效"，而不是静默（呼应需求 R-4）
- ⚠️ `05-待确认清单` 需跟踪 PR 进展

### 前提

上游接受这个 PR，或我们接受长期 B。

## ADR-06 · 模板试穿策略

### 背景

**【实测】** 真渲染的单位成本很高（`06`§4）：

- 一次 `rlex export run` 需要**启动整个 Electron 应用**：日志实测 `ready-to-show` 6.0s / 8.4s
- 导出内还有固定开销：`metadataLoadMs` 1143ms + `rendererInitMs` 808ms ≈ **2s**
- 一次应用启动**只能导出一次**（`useSmokeExportAutomation.ts` 单次驱动，无批量路径）

**⇒ 试穿 5 个模板 ≈ 5 次启动 ≈ 1 分钟纯开销，还没算渲染。**

### 选项

| 选项 | 单次成本 | 保真度 |
|:---|:---|:---|
| A. 全片真渲染每个模板 | 分钟级 | 100% |
| B. **短片段真渲染**（截 3–5s） | ~10–15s（含启动） | 100%（片段内） |
| C. **静态帧近似渲染**（PIL 把字幕样式画到抽帧上） | **毫秒级** | 高（几何与样式按 04 的公式复刻；字体渲染有差异） |
| D. 直接看已有成片对比图 | 0 | 只反映过去 |

### 决策

**两段式：默认 C（快速近似试穿），可选 B（真渲染试穿）。**

| 命令 | 行为 |
|:---|:---|
| `rlc review --fast`（默认） | 抽 **2–3 帧且刻意覆盖最亮/最暗场景** → 每个候选模板在每帧上都画一遍 → **算字幕区对比度并对低对比格打标** → 拼对比图 |
| `rlc review --render` | 每个候选模板渲一个 3–5s 真片段，拼成对比条 |
| `rlc review --compare <a> <b>` | 两个模板同帧并排 |

> **`[修-5]`** 多帧 + 对比度打标是**必须的**，不是锦上添花：
> `P09` 曾因单帧窄裁剪切到浅色墙面，**误判 4 个模板白色文字不可读**。
> 只抽一帧会把这次人工误判变成**自动化误判**，而人会更相信自动结果。

### 理由

1. **C 的几何是可复刻的**：字幕盒宽高、字号缩放、底距、圆角在 `04` §4 与 `06`§5 里都有精确公式，
   `captionStyle.ts` 的系数（`CAPTION_LINE_HEIGHT = 1.32`、padding `x=1.1×fs, y=0.78×fs`）是明文
2. **试穿要的是"选哪个"，不是"验收"** —— 近似足够做决策，且把反馈环从分钟压到毫秒
3. 但必须**明确标注近似**，不能让人误以为那是最终效果；最终判定仍走 B 或整片渲染
4. C 还有一个好处：**不需要 Recordly 在场**，让试穿也能离线做

### 后果

- ⚠️ 要维护一份"样式 → 近似渲染"的复刻实现；Recordly 改版需同步
- ✅ 需求 P-3（试穿单位成本）有了明确答案
- ⚠️ 近似与真实存在差异（尤其字体、字距），文档与输出都要写明

### 前提

试穿用于**筛选**，不用于**验收**。

## ADR-07 · 内容文档进画面的形态

### 背景

**【已读源码确认】** `04` §6.1：

- 标注图片字段 `imageContent` 必须是 **inline `data:` URL**；给文件路径会被渲染器忽略
  （`annotationRenderer.ts:51-58`）
- **全仓无体积校验**（`grep file\.size|MAX_.*SIZE|sizeLimit` → 无命中）
- base64 膨胀 ~33%；10 页 1080p PNG ≈ **40 MB JSON**，Recordly 整体读入内存
- `style` / `figureData` 是**无校验的整对象展开**（`projectPersistence.ts:655-667`）

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 原样内联页图 | ❌ 项目文件爆炸；无上限意味着无保护 |
| **B. 内联但强制限幅**（缩页 + JPEG + 页数上限） | ✅ 单次渲染、零额外通道；代价是清晰度 |
| C. 画面外合成：Recordly 出片后再用 ffmpeg 叠文档 | ✅ 画质最好、项目不膨胀；代价是多一遍编码 |
| D. 只用文档的文字（转成文本标注），不用图 | ✅ 最轻；但丢失版式（报告类文档通常版式就是信息） |

### 决策

**默认 B，超限自动降级到 C，并允许 `--mode` 显式指定。**

| 模式 | 触发 | 做法 |
|:---|:---|:---|
| `inline`（默认） | 单页压缩后 < 阈值（默认 800 KB）且总页数 ≤ 上限（默认 12） | 缩到目标宽度 → JPEG q80 → base64 → 图片标注 |
| `overlay`（自动降级） | 超阈值 | 页图存 `media/`，出片后用 ffmpeg 叠加（`rlc` 自有步骤） |
| `text` | `--mode text` | 只抽文本 → 文本标注 |

### 理由

1. **B 是默认因为它是单遍渲染** —— 与"一次出片"的目标一致
2. **必须有上限**，因为 Recordly 侧没有 —— 保护要由工具承担
3. **C 是必需的逃生门**：PDF 报告常有十几页且要求可读，压到 800KB 就糊了
4. `overlay` 模式正好复用已有能力：家族里 `mp4-tools` / `ffmpeg` 都在，且 `subtitle-burn` 已验证过
   "先出片再叠内容"这条路

### 后果

- ⚠️ 两种模式的成片**质量与耗时都不同**，必须在报告里写清用了哪种
- ⚠️ `overlay` 模式引入第二遍编码 → 需要考虑是否重编码（可 `-c:v copy` 不行，因为要叠加）
- ✅ 项目文件体积可控

### 前提

内容文档以 **PDF** 为主；DOCX/PPTX **本地无法光栅化**（无 LibreOffice），
须走 `documents2md`/`pptx-creator` 或先转 PDF（`04` §6.2）。

> ⚠️ **`[修-16]` 依赖选型已按许可证修正**（见 `01-需求` §11.5）：
> 本机现成可用的 `fitz`（PyMuPDF）是 **AGPL-3.0**，并入 MIT 仓构成**许可证冲突**；
> 改用 **pypdfium2**（BSD-3-Clause / Apache-2.0）。
> **教训**：取材时"能跑通"不等于"可以用"—— 先查许可证，再查能力。
> 若坚持用 `fitz`，只能二选一：整体改 AGPL-3.0，或改为独立进程调用（T-2）。

## ADR-08 · 跨机迁移

### 背景

**【已读源码确认】** `04` §2.5.3：`videoPath`、`webcam.sourcePath`、`audioRegions[].audioPath`
都是**绝对路径**，全仓无重写逻辑；视频缺失时 `resolveProjectMediaSources`
**直接拒绝加载**（`Project video file not found: <path>`）。
且**光标轨迹不在项目里**（在 `<video>.cursor.json` 侧车）。
另有一处平台差异：缺 `borderRadius` 时 macOS 默认 8、其他平台 0（`projectPersistence.ts:86-93`）。

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 忽略（假定单机） | ❌ 用户明确要"项目可复用"，且跨机是自然需求 |
| **B. 清单内存相对路径 + `relocate` 命令 + 启动自检** | ✅ 明确、可测 |

### 决策

**选 B。**

| # | 措施 |
|:--:|:---|
| 1 | **素材默认「引用」不拷贝** `[修-1]`：`compose.toml` 记绝对路径；`init --embed` 才拷进 `media/` 并转为相对路径。理由：S01 的输入常是 50 MB 级 MP4，无声拷贝既慢又占盘，且"相对路径"只在 embed/relocate 之后才真正成立 |
| 1b | `vendor/` 与 `media/` 内的文件**一律相对项目目录**（这两处是我们自己写入的，可控） |
| 2 | `vendor/` 原样携带 Recordly 侧车（`.cursor.json`、`.recordly-session.json`），否则缩放/点击效果无法复现 |
| 3 | 提供 `rlc relocate --video <新路径> --in-place` 重定位外部素材 |
| 4 | 每次 `apply` 前做**自检**：所有引用路径存在？`fontFamily` 是否被要求但不可用？侧车是否齐全？ |
| 5 | 报告里记录 `borderRadius` 等**平台相关默认值**，避免跨平台静默差异 |

### 理由

1. 绝对路径是 Recordly 的设计，我们改不了；**只能在生成侧用相对路径 + 显式重定位**
2. 侧车携带是必须的 —— 否则"换个机器打开，缩放和点击效果全没了"且没有任何提示
3. 自检把失败提前到编排阶段（秒级），而不是等到渲染时（分钟级）

### 后果

- ⚠️ `apply` 时要把相对路径解析成绝对路径写进 `.recordly`（因为 Recordly 要绝对路径）
- ✅ 项目目录变成**可整体拷贝的最小单元**

## ADR-10 · 「打开 GUI」只能做到"准备 + 一次点击"

> 本条由 `08-场景走查.md` 的 **P-07（方案级缺口）** 触发新增。
> 它**削弱**了原方案对 S3（精修面）的承诺，因此必须单独立案。

### 背景

需求 C-3 与 S3-1～S3-5 要求：人进 Recordly 时应该是**布景好的**、打开即就位。
原 ADR-04 假定 `rlc open --review` 能"启动 Recordly 并打开这份制品"。

**【已读源码确认】** 走查逐条排查后确认：**这件事在当前 Recordly 上做不到。**

| 手段 | 能否让 Recordly 打开指定项目 |
|:---|:---|
| `RECORDLY_SMOKE_EXPORT*`（18 个环境变量） | ❌ 只触发**导出**，跑完 `window.close()`，不接受交互 |
| `RECORDLY_DEV_OPEN_RECORDING_INPUT` | ❌ 打开的是**视频/录制**，不是 `.recordly` 项目 |
| `open-project-file-at-path` IPC | ❌ **仅应用内可达**（`contextIsolation: true`，preload 只注入应用窗口） |
| 命令行参数 | ❌ 全仓无 argv 解析；`second-instance` 只做窗口聚焦（`main.ts:886`） |
| `mediaServer` / `rendererServer` | ❌ 只读、随机端口、路径白名单，无控制能力 |
| 系统文件关联双击 | ⚠️ 可行但**我们无法布景**，且各平台行为不一 |

**⇒ S3-3「打开即定位字幕区」同样不可达**（面板激活状态是应用内部状态，无外部入口）。

### 选项

| 选项 | 评价 |
|:---|:---|
| A. 改 Recordly 源码加启动参数 | ❌ 违反 ADR-01/ADR-09；且要跟上游 |
| B. 自动化点界面（模拟点击/键鼠） | ❌ 违反 ADR-01 选项 E：脆弱、不可测、不可无人值守 |
| **C. 退化为"准备 + 指引"** | ✅ 零上游依赖，今天可用 |
| D. 请求上游加 `--open-project <path>` | ✅ 正解，但**不由我们控制时间** |

### 决策

**选 C 立即落地，同时把 D 作为上游请求记入 `07-VOC`。**

`rlc open` 的实际动作：

| # | 动作 |
|:--:|:---|
| 1 | 先 `apply`，确保制品最新 |
| 2 | **把制品复制/链接进 Recordly 的项目目录**（`get-projects-directory` 对应位置）—— 这样它会出现在项目浏览器 / 最近项目里 |
| 3 | 在 `style.toml` 顶部写好「本次要调什么」（人打开就能看到意图，而不是自己去猜） |
| 4 | 落锁 + 记制品指纹（ADR-04 R2） |
| 5 | 打印明确指引：**「在 Recordly 里打开 `<项目名>`，调完保存，回来跑 `rlc pull`」** |
| 6 | **不谎称能自动打开，也不假装已定位到字幕区** |

### 理由

1. **诚实优先**：能力边界必须写进工具的输出，而不是让人以为"怎么没反应"
2. **第 2 步实际价值很高**：把"去文件系统里找"降为"在最近项目里点一下"，
   这是当前唯一不依赖上游的实质改善
3. **第 3 步补偿了 S3-3 的缺失**：既然不能自动定位面板，就把"要调什么"前置成文字，
   人的注意力成本从"找"变成"读"

### 后果

- ⚠️ 需求 §5.3 的 **S3-2 / S3-3 从"要求"降级为"上游请求"**（已回写 `01-需求`）
- ⚠️ **人绕过工具直接打开成为主路径** → 交接锁降级为提示，`pull` 指纹校验升为硬要求（ADR-04）
- ⚠️ `rlc open` 不再是"安全入口"，工具不应假设锁一定生效
- ✅ 不影响 S0/S1/S2/S4 四个面 —— **它们本来就不需要 Recordly GUI**

### 前提

Recordly 项目目录可由 `get-projects-directory` 定位（【已读源码确认】IPC 存在）。
若上游提供 `--open-project`，本 ADR 可升级回全自动布景。
