## B. 验证项（方案依赖但尚未实测）

### Q5 中文 whisper 输出是否真的并成 1 词/条

| 项 | 内容 |
|:---|:---|
| **问题** | `06`§5 的成本估算**取决于**这个前提：中文落在 489 次 `measureText`/帧（便宜档）。依据是 `parser.ts:44-70` 的"无空白就并词"逻辑【已读源码确认】，但**未实测** |
| **为什么没测** | 本机无 Windows whisper 运行时（只有 `darwin-arm64` 的 `whisper-cli`），也无 `ggml-*.bin` 模型 |
| **风险** | 若实际按字/词分开，布局成本**跳约 9 倍**（10.1s → 85.9s / 314s 片） |
| **怎么验** | 用 `subgen` 或 Recordly GUI 对一段中文生成字幕，看 `.recordly` 里 `autoCaptions[0].words` 的数组长度 |

### Q6 长视频的真实性能曲线

| 项 | 内容 |
|:---|:---|
| **问题** | `06`§5.5 的 O(时长²) 外推（30 分钟 ≈ 5.5 分钟布局开销）是**算术推算，不是实测** |
| **待确认** | 30 分钟素材上 `renderFrameMs` 的实际数值；以及 ASR 的真实耗时（`02` §7.4 按 RTF 3.363 外推 ≈101 分钟） |
| **怎么验** | 跑一次 30 分钟素材，读 `<out>.mp4.report.json` 的 `renderFrameMs` |

### Q7 `review --fast` 近似渲染的保真度

| 项 | 内容 |
|:---|:---|
| **问题** | ADR-06 的默认试穿是**近似**（PIL 按公式复刻），未验证与真实渲染差多少 |
| **待确认** | 同一模板同一帧，近似图 vs 真渲染抽帧的像素差异；尤其**字距与换行**（两者文本引擎不同） |
| **怎么验** | 拿 `clean-bar-white` 做同帧对比图 |

### Q8 `overlay` 模式的画质与耗时

| 项 | 内容 |
|:---|:---|
| **问题** | ADR-07 的降级路径是"出片后 ffmpeg 叠加"，引入第二遍编码 |
| **待确认** | 需要重编码（`-c:v copy` 无法叠加）→ 画质损失多少？耗时增加多少？ |
| **怎么验** | 实现后对比 inline 与 overlay 两种成片的 VMAF/体积/耗时 |

### Q9 一次应用启动能否导出多个项目

| 项 | 内容 |
|:---|:---|
| **问题** | `useSmokeExportAutomation.ts` 看起来只驱动**一次**导出。若确认，试穿 `--render` 的 N 个模板要付 N 次启动成本（`02` §7.3） |
| **待确认** | 是否有未发现的批量路径？能否在不改 Recordly 的前提下复用同一进程？ |
| **影响** | ADR-06 的成本模型 |

### Q10 `fontFamily` 被重置后，**实际**用什么字体

| 项 | 内容 |
|:---|:---|
| **问题** | 默认栈全是拉丁字体 → 中文走系统兜底。但**具体兜底成哪个字体**未知（Chromium 在 Windows 上通常是微软雅黑，未验证） |
| **影响** | 决定"接受系统兜底"这条退路的实际观感（ADR-05 选 B 的可行性） |
| **怎么验** | 渲染一张含中文的帧，用字体识别或与已知字体渲染图逐像素比对 |
