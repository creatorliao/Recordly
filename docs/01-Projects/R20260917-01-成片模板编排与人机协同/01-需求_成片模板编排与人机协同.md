# 01 · 需求：成片模板编排与人机协同

> 本文是 R20260917-01 的需求 SSOT。上游来源：用户在本轮对话中的两次口述需求
> （第一次提出"MP4 + 文档 → 导入 Recordly → 手工选调模板 → 导出"，第二次补充
> "AI 全自动 + 人随时插队 + 不要框定在原来的窗口上 + 不要太偏人工"）。
> 原话摘录见 §1.2，逐字保真，未改写。

---

## 1. 背景与来源

### 1.1 为什么要做

我们已经有两条字幕链路（见 `F20260917-字幕链路复盘与VOC`）：

| 链路 | 能力 | 缺口 |
|:---|:---|:---|
| `subtitle-generate` → `subtitle-optimize` → `subtitle-burn` | 任意 MP4 + SRT → 硬字幕成片；5 个 ASS 模板；纯命令行 | 模板上限受 libass 限制；无法所见即所得 |
| Recordly 内置字幕（v1.4.0-beta.1） | 本地转写 + 4 个动画 + GUI 调参 + 预设 | 字体不可控、水平位置不存在、文本无法从命令行灌入 |

`recordly-export`（`rlex`）已经打通"**编排 `.recordly` 项目 + 无头导出**"，但它从**录屏**出发，且明确声明"本技能不碰字幕内容"。

**所以现在缺的是一条"以模板为轴、以人机协同为骨架"的编排层。** 本文就是给它立需求。

### 1.2 用户原话（逐字保真）

> **第一次口述**
> 「假设我已经有了一个 MP4 和一些文档，然后我在 recordly 里面导入进去，手工选择调整模板，然后他帮我导出，在这个方向上是否可以实现？希望这是一个相对独立的工具，或者 Recordly 给我提供相关的 API 或 CLI 来实现同等的功能。」

> **第二次口述（补充，本次新增）**
> 「我希望实现的目标是 AI 可以全自动跑完，但是呢，人有些时候进去调整一下字幕，调整一下参数，这样就会有对应的项目。」
> 「可以有更灵活的人机协同模式，不一定要框定在原来的窗口上面。如果原来的窗口要展示出来，我希望它是更漂亮的、更合适的，更符合我们现有的工作流。我们现在都已经人机协同了，原来那种方式太偏向于人工了。」

### 1.3 从原话里提炼出的三条硬约束

| # | 约束 | 出处 |
|:--:|:---|:---|
| **C-1** | **AI 全自动是默认路径。** 人工是可选的例外，不是必经步骤。 | 「AI 可以全自动跑完」 |
| **C-2** | **人工干预后必须能交回 AI 继续跑**，且产出物是一个可复用的「项目」。 | 「人有些时候进去调整一下…然后再交给 AI 继续跑，这样就会有对应的项目」 |
| **C-3** | **人工干预的界面不被限定为 Recordly 原窗口。** 若使用原窗口，它必须是"布景过的"、漂亮的、贴合工作流的。 | 「不一定要框定在原来的窗口上面」「太偏向于人工了」 |

### 1.4 建设方式的变化（第三轮补充，2026-09-17）

> **用户原话（逐字保真）**
> 「我继续补充，就是我们以往要学习多个工具的时候，学习成本太高了条件也不太具备，因为每一个工具有自己的成本：学习成本和真真正正的费用成本。但是，如果我们现在 AI 编程能力已经足够强了之后，我们可以从开源社区按照合法合规的方式，从仓库中抽取对应的某一部分代码，整合到我们自己的项目里面。我们按需取材、按需构建，然后人机协同把它串起来，形成新的工作流程。这是我们跟以往不一样的地方。」

提炼成第四条硬约束：

| # | 约束 | 说明 |
|:--:|:---|:---|
| **C-4** | **按需取材、按需构建。** 不再"学会整个工具再用它"，而是从开源仓**合法合规地抽取需要的部分**，整合进自己的项目，再由人机协同串成新工作流。 | 前提是「**合法合规**」四个字 —— 见 §11 |

**这条改变了本方案的方法论底座**，因此单独立章（§11）：
它既解释了为什么本方案敢"自己造一个工具"（而不是去学 `rlex`+`rlz`+`subtitle-burn` 三套），
也给出了**取材时必须守的许可证围栏**。

## 2. 问题界定

### 2.1 一句话问题陈述

> 给一段已有 MP4 和若干文档，**让 AI 无人值守地产出一版带模板化字幕的成片**；
> 并在人想插手时，提供一个**代价极低、不绑定 Recordly 窗口**的干预面，
> 人改完能**无损地交回 AI 继续**，最终沉淀成一个可反复打开、可批量复用的**项目**。

### 2.2 三个必须回答的问题

| 问题 | 本文档的答案位置 |
|:---|:---|
| 这件事技术上能不能做？ | `02-方案_技术选型与架构.md` + `06-机制验证报告.md`（含实测） |
| 人机协同的"面"到底有几个、各自代价多大？ | §5（本文核心） |
| 会不会有坑、坑在哪？ | `05-待确认清单.md` + `08-场景走查.md` |

### 2.3 判定标准（做成什么样算好）

1. **无人值守可跑通**：一条命令，从 `MP4 + SRT` 出到成片，中途零交互。
2. **人的干预可被 AI 接住**：人改完存盘后，AI 不需要重新理解上下文就能继续，且**人的改动不丢**。
3. **默认不进 GUI**：全流程里，打开 Recordly 编辑器是**可选**动作而非必经动作。
4. **项目可复用**：同一个项目的模板/参数能一键套到第二个 MP4 上。

## 3. 目标与非目标

### 3.1 目标（In scope）

| # | 目标 |
|:--:|:---|
| G-1 | 从**任意已有 MP4**（非 Recordly 录制）建立项目 |
| G-2 | 消化三类文档：**字幕文稿**、**内容文档**、**配置文档**（见 §4） |
| G-3 | 提供**模板库**：命名模板 = 一组字幕/画面样式；可列出、可预览、可套用 |
| G-4 | 提供**模板试穿**：一次看到多个候选模板在同一素材上的真实效果 |
| G-5 | 提供**多个人工干预面**，按代价递增，各自可独立使用（见 §5） |
| G-6 | 提供**双向同步**：`apply`（配置/文稿 → 项目）与 `pull`（项目 → 配置/文稿），带冲突检测 |
| G-7 | 驱动**导出**并回读报告（复用 `rlex`，不自研渲染器） |
| G-8 | 全流程**可脚本化、可无人值守**，且每步都可单独重跑（幂等） |
| G-9 | 项目**可跨机迁移**（无绝对路径硬依赖，或提供重定位命令） |

### 3.2 非目标（Out of scope —— 明确不做）

| # | 不做 | 理由 |
|:--:|:---|:---|
| N-1 | **不自研渲染器** | Recordly 已有渲染管线；自研等于重造且永远追不上 |
| N-2 | **不修改 Recordly 源码**（本方案内） | 减少与上游 AGPL 仓的耦合；`fontFamily` 那一处列为"建议上游修"的单点。<br>⚠️ **注意区分**：「不修改」≠「不借鉴」—— 我们仍然**大量取材于 Recordly 的公开接口契约**（`version:2`、字段名、环境变量名、报告命名），这是 §11.3 的 **T-1**，允许且鼓励 |
| N-3 | **不做视频剪辑**（剪切/转场/多轨） | 那是 Recordly 编辑器本体与 `mp4-tools` 的地盘 |
| N-4 | **不替代 `subtitle-burn`** | 两条链路分工并存（见 §7） |
| N-5 | **不做逐字动画**（本期） | 需要 Recordly 侧先合并预览/导出双路径，成本高，列为路线项 |
| N-6 | **不引入云服务** | 全本地、零 API 成本，与现有链路一致 |

## 4. 三类输入文档（用户明确三类都要）

用户在澄清中三类全选。三类的处理路径完全不同，必须在需求层就分开。

| 类型 | 典型文件 | 它变成什么 | 落点 |
|:---|:---|:---|:---|
| **D1 字幕文稿** | `.srt` / `.vtt` / `.txt` 逐字稿 | 项目的**字幕条**（`autoCaptions[]`） | 项目内 `captions.srt` |
| **D2 内容文档** | `.pdf` / `.docx` / `.md` 报告 | 画面上的**素材**（图片/标注/分页） | 项目内 `media/` + 标注区 |
| **D3 配置文档** | `.toml` / `.yaml` / `.json` | **模板与参数**（样式、位置、模板名） | 项目内 `style.toml` / `template.toml` |

**统一原则：项目内一律以"人和 AI 都好读好写"的格式存一份权威副本**，`.recordly` 是**产物**而不是唯一事实源。这条是 C-2（人工改完交回 AI）能成立的前提——因为 `.recordly` 里的字幕是数组、CLI 灌不进去（见 `04-借鉴`），而 SRT/TOML 人改起来毫无门槛。

### 4.1 D1 的导入必须处理的三件事（走查修正 `[修-2/3/4]`）

| # | 问题 | 要求 |
|:--:|:---|:---|
| 1 | **编码** | 必须嗅探 **UTF-8 BOM / UTF-8 / GBK / UTF-16**；输出统一 **UTF-8 无 BOM**，并**报告检测结果**。依据：`P05`/`P06` 已因 BOM 丢失去过一次校验（`04` §2.4 同源问题） |
| 2 | **双语行** | 双语 SRT（一行中文一行英文）会被 Recordly 当成**两行**并触发分页 → 出现"中文一页、英文一页"。默认**剥离非主语言行**（按 CJK 占比判定），`--keep-bilingual` 可关，并报告剥离行数 |
| 3 | **时间码越界** | Recordly **不校验**字幕是否超出视频时长（`04` §2.2）。`verify` 必须检查并在越界时给出**具体条目号** |

依据见 `08-场景走查.md` 的 P-02 / P-03 / P-04。

## 5. 人机协同模型（本文核心）

### 5.1 定位转变：从"人去用工具"到"人做例外处理"

用户原话点破了问题：「原来那种方式太偏向于人工了」。

**旧形态**：流程设计成"AI 做一半 → 请人去 Recordly 里操作 → AI 再接着做"。人在系统里扮演**操作员**，承担的是工具的复杂度。

**新形态**：AI 扮演**主驾驶**，人是**例外处理者（exception handler）**。人只做机器判断不了或不该替人决定的事——通常是"哪个好看""这句话是不是听错了"。系统要主动**把决策压缩到最小**。

由此推出四条设计原则：

| # | 原则 | 反例（要避免的） |
|:--:|:---|:---|
| **P-1** | **默认不打扰。** 只有置信度低或触及偏好的地方才请人。 | 每做一步都弹一个"请确认" |
| **P-2** | **一次只问一个决定。** 把"调字幕+调参数+选模板"拆成三个可选时刻，而不是一个大表单。 | 打开一个满屏控件的面板让人自己找 |
| **P-3** | **能用文本就不用 GUI。** 文本面人最快、AI 最好接。GUI 是最后手段。 | 为了改一个错字要求人开编辑器 |
| **P-4** | **干预必须留痕且可回放。** 人改了什么要记下来，AI 才能理解"为什么变了"。 | 人改完存盘，AI 只看得到结果、看不到意图 |

### 5.2 五个协同面（按"人的代价"递增）

**关键结论：人机协同不需要被框在 Recordly 窗口里。** 下面 S0–S4 五个面共用同一个项目，人可以只用其中任意一个。

| 面 | 名称 | 人在哪个界面 | 人做什么 | 单次代价 | 谁提供 |
|:--:|:---|:---|:---|:---:|:---|
| **S0** | 无人面 | 无 | 什么都不做 | **0** | 本工具（默认路径） |
| **S1** | 文本面 | 任意文本编辑器 / AI 对话 | 改 SRT 错字、改 TOML 参数 | **秒级** | 本工具（项目内的纯文本副本） |
| **S2** | 试穿面 | 本地评审包（图片/短片 + 一张清单） | 从候选模板里点一个；看改动清单点头 | **十秒级** | 本工具（`review` 命令产出） |
| **S3** | 精修面 | Recordly 编辑器（**可选**） | 拖动位置、改字号、逐条改字幕 | **分钟级** | Recordly 本体（已有） |
| **S4** | 交付面 | 体检报告 | 看"能不能发"的结论 | **秒级** | `recordly-deliver`（`rld`，已有） |

**排序即推荐顺序**：能停在 S0 就停在 S0；要插手先走 S1；S1 不够再 S2；S2 还不足以表达才进 S3。

### 5.3 S3（精修面）的"布景化"要求

用户说：「如果原来的窗口要展示出来，我希望它是更漂亮的、更合适的，更符合我们现有的工作流。」

S3 是最贵的一个面，因此要求它**只在该出现的时候出现，且以布景好的形态出现**：

| # | 要求 | 现状 |
|:--:|:---|:---|
| S3-1 | **不是必经步骤** | ✅ 可做（S0/S1/S2 已覆盖多数情况） |
| S3-2 | **打开即就位**（项目/视频/字幕/模板预置好，不用找） | ⚠️ **降级**：只能做到"在 Recordly 的最近项目里一次点击"，见下 |
| S3-3 | **只暴露要调的**（打开时定位到字幕区） | ❌ **当前不可达** → 转为**上游请求**（`07-VOC`） |
| S3-4 | **改完一键交回** | ✅ 可做（`rlc pull`） |
| S3-5 | **背景/光标/缩放已定稿**，人只处理字幕 | ✅ 可做（这些字段本来就是工具写入的） |

> ⚠️ **S3-2 / S3-3 的降级来自 `08-场景走查.md` 的 P-07/P-08（方案级缺口）。**
>
> 走查确认：**Recordly 没有任何外部手段可以"打开一个指定项目"**，也没有办法
> 控制打开后面板落在哪一区（`04` §7、`03-决策_ADR.md` ADR-10）。
>
> **修正后的诚实承诺**：
> - 工具把项目**准备到位并放进 Recordly 的项目库** → 人**一次点击**就能打开（不再是"去文件系统找"）
> - 工具把"本次要调什么"**写在 `style.toml` 顶部**，补偿"不能自动定位面板"
> - **不承诺**自动打开、不承诺自动定位
>
> 这仍然满足本需求的底线 C-3（**不把协同框定在 Recordly 窗口上**），
> 但 S3 是一个**"半自动面"**，不是"布景好的自动面"。此降级已同步到 `02-方案` §6.2 与 ADR-10。

> 补充：**S0/S1/S2/S4 四个面完全不受此影响** —— 它们本来就不需要打开 Recordly GUI。

### 5.4 协同的闭环：项目是唯一交接物

```
        ┌──────────────────────────────────────────────┐
        │            项目（唯一事实源）                 │
        │  captions.srt / style.toml / media/ / *.recordly │
        └──────────────────────────────────────────────┘
             ▲          ▲            ▲            ▲
     apply   │   pull   │      pull  │     pull   │
             │          │            │            │
        ┌────┴───┐ ┌────┴────┐ ┌─────┴─────┐ ┌────┴────┐
        │  S0 AI │ │ S1 文本 │ │ S2 试穿  │ │ S3 GUI  │
        │ 全自动 │ │  面     │ │   面     │ │  精修   │
        └────────┘ └─────────┘ └───────────┘ └─────────┘
```

- `apply`：把 `captions.srt` + `style.toml` + `template.toml` 合成进 `.recordly`（幂等）
- `pull`：把 `.recordly` 里人改过的内容**反向抽取**回 `captions.srt` / `style.toml`，并**列出差异**
- 任一面的改动，AI 只需读项目里的纯文本副本就能理解，不需要解析 `.recordly`

### 5.5 冲突与安全的硬要求

| # | 要求 |
|:--:|:---|
| R-1 | `pull` 必须**报告差异**（哪些字段变了、从什么变成什么），不能静默覆盖 |
| R-2 | 人正在 Recordly 里编辑时，AI 不得写 `.recordly`（需要锁或显式确认） |
| R-3 | 任何 `apply`/`pull` 写盘前先出计划（dry-run 默认），写盘后留备份 |
| R-4 | 已知会丢失的字段（`fontFamily`）必须**显式警告**，不得静默丢弃 |
| R-5 | 每次人工干预产生一条**留痕记录**（时间、面、改了什么），供 AI 与复盘读取 |

## 6. 场景表（用户可见场景，S01–S12）

> 本表是"用户会真的说出口的话"→ 命令 → 判据。与 `08-场景走查.md` 一一对应。

| 编号 | 用户会说的话 | 期望命令 | 判据 |
|:---|:---|:---|:---|
| **S01** | 「这个片子给我配上字幕出个片，我不管了」 | `init` → `import-captions` → `apply` → `export` | 一条链跑完，零交互，出片 + 报告 |
| **S02** | 「有 `xxx.srt`，用它当字幕」 | `import-captions --srt` | 字幕条数与 SRT 一致；时间码零漂移 |
| **S03** | 「这几个模板都试一下，我看看哪个好看」 | `templates try --all` 或 `review` | 产出多个候选效果 + 一张对比图，人一次看完 |
| **S04** | 「就用第 3 个，以后都按这个来」 | `template use <name>` | 模板名写入 `template.toml`；后续 apply 自动套用 |
| **S05** | 「第 8 条字幕有个错字，我改一下」 | 人改 `captions.srt` → AI `apply` | 只动那一处；时间码与其余条目零改动 |
| **S06** | 「字号太小了，调大一点，往上挪一点」 | 人改 `style.toml` → AI `apply` | 只变字号与底距；其余样式不变 |
| **S07** | 「我要自己拖一下位置」 | `open --review` 打开布景好的 Recordly | 打开即定位字幕区；改完 `pull` 能读回；**不丢字段**（`fontFamily` 除外，需警告） |
| **S08** | 「这份 PDF 报告里有几页要放进画面」 | `import-doc --pdf` → 生成画面素材 → `apply` | 页图进项目 `media/`；画面位置可指定 |
| **S09** | 「AI 先跑，我待会儿再看」 | `init`+`apply`，人稍后 `review`/改文本，再 `export` | 项目状态可中断可续；两次命令之间全部状态落盘 |
| **S10** | 「这个模板套到下一个片子上」 | `template use` + 新 `init --from <project>` | 模板与参数复用；素材路径正确重定位 |
| **S11** | 「30 分钟的录课也这么弄」 | 同上 | 不因时长退化到不可用（见 `02-方案` §7 性能预算） |
| **S12** | 「这条能发了吗？」 | `rld`（`recordly-deliver`） | 出"能不能发"的逐项结论 |

## 7. 与既有链路的分工（不替代，只补位）

| 工具 | 出发点 | 强项 | 与本工具的关系 |
|:---|:---|:---|:---|
| `subtitle-generate`（`subgen`） | 音视频 | 本地转写，零 Key | **上游**：给 S01/S02 产 SRT |
| `subtitle-optimize` | SRT | 改文字不改时间轴 | **上游**：给 S05 之前做体检纠错 |
| `subtitle-burn` | MP4 + SRT | ASS 模板 + ffmpeg 烧录；纯命令行 | **并行**：任意 MP4 + 精细 ASS 模板时仍用它 |
| `recordly-export`（`rlex`） | 录屏 | `.recordly` 编排 + 无头导出 | **下游**：本工具调用它出片，不自研渲染 |
| `recordly-zoom`（`rlz`） | 光标轨迹 | 镜头计划 | **可选上游**：给录屏类素材生成缩放区 |
| `recordly-deliver`（`rld`） | 成片 | 交付体检 | **下游**：S12 / S4 面 |
| **本工具** | **已有 MP4 + 文档** | **模板编排 + 人机协同 + 项目化** | —— |

**一句话边界**：`rlex` 管"从录屏到成片的样式"，本工具管"**从既有素材到成片的模板与协同**"。

## 8. 验收标准

### 8.1 功能验收（每项可机械判定）

| # | 判据 | 判定方式 |
|:--:|:---|:---|
| A-1 | 任意 `h264+aac` 的 MP4 + 合法 SRT，能一条命令出片 | 脚本跑通，退出码 0，产物存在 |
| A-2 | 字幕条数与 SRT 逐条一致，时间码零漂移 | 逐条比对（复用 `subtitle-optimize` 的时间轴校验思路） |
| A-3 | 人的文本改动经 `apply` 后**只改该处** | 改前改后 diff 仅命中目标条目 |
| A-4 | `pull` 能报出人改过的字段差异 | 输出含"字段 → 旧值 → 新值"清单 |
| A-5 | 已知会丢的字段有显式警告 | `fontFamily` 改动时输出 WARN，不静默 |
| A-6 | `apply` 幂等：连跑两次，第二次零变更 | 第二次输出"0 处真实变更" |
| A-7 | 默认 dry-run，写盘需显式确认 | 无 `--out`/`--yes` 时不落盘 |
| A-8 | 项目可跨机迁移 | 换目录后 `relocate` 或相对路径可解析 |
| A-9 | 全流程可无人值守 | 单命令串起：无 stdin 交互 |

### 8.2 协同验收（对应 §5）

| # | 判据 |
|:--:|:---|
| B-1 | 存在一条**完全不需要打开 GUI** 的端到端路径（S0+S1） |
| B-2 | 打开 GUI 是**可选**的，且文档明确写出"什么情况下才需要" |
| B-3 | 进入 S3 时，项目已预置完毕（不做额外准备动作） |
| B-4 | 人在 S1/S2/S3 任一面的改动，AI 都能接住，不需要重跑前序步骤 |
| B-5 | 每次人工干预有留痕记录（时间/面/改了什么） |

### 8.3 性能预算

| # | 判据 | 目标 |
|:--:|:---|:---|
| P-1 | 编排层（不含渲染）开销 | **秒级**（纯文本变换，不应超过 5s） |
| P-2 | 单次渲染耗时 | 不劣于 `rlex` 基线（实测 0.70×–1.59× 实时，见 `06`） |
| P-3 | 模板试穿的单位成本 | 见 `02-方案` §7；若走真实渲染，须明确告知固定开销 |

## 9. 术语

| 术语 | 含义 |
|:---|:---|
| **项目** | 一次成片任务的目录；含 `captions.srt`/`style.toml`/`template.toml`/`media/`/`*.recordly`；是人与 AI 的唯一交接物 |
| **模板** | 一个命名样式集合（字幕样式 + 画面参数），可列出、预览、套用 |
| **试穿** | 把多个候选模板套到同一素材上，产出可比对的效果，供人挑选 |
| **协同面** | 人机交互的具体载体（S0–S4）；不同面代价不同 |
| **apply** | 文本/配置 → `.recordly`（幂等，默认 dry-run） |
| **pull** | `.recordly` → 文本/配置（带差异报告） |
| **留痕** | 人工干预的记录（时间、面、字段、旧值、新值） |
| **按需取材** | 从开源仓合法合规地取用**需要的那一部分**（接口契约 / 外部工具 / 代码片段），而非学习并使用整个工具。见 §11 |
| **T-1 / T-2 / T-3** | 取材的三种方式：接口契约（最安全）/ 外部工具进程调用 / 代码并入（风险最高）。见 §11.3 |
| **许可证传染** | 强著佐权许可（如 AGPL/GPL）要求派生作品沿用同一许可，因此**不能并入 MIT 仓**。见 §11.4 |

## 10. 开放问题

未决项移入 `05-待确认清单.md` 跟踪。其中影响架构的三条先列在此：

1. **`fontFamily` 不可控**：Recordly 在加载时无条件重置该字段（`projectPersistence.ts:785`），且 CLI 白名单不含它。**不修 Recordly 则字体不可控。** 是否提上游 PR？（见 `03-决策_ADR.md` ADR-04）

## 11. 建设方式：按需取材、按需构建（C-4 展开）

### 11.1 战略转变：从"学工具"到"取材 + 自建 + 串联"

| | **以前的做法** | **现在（C-4）** |
|:---|:---|:---|
| 面对一个新需求 | 找一个现成工具，**学会它**，然后用它 | 找到**做这件事的那部分代码/契约**，**取需要的**，整合进自己的项目 |
| 成本结构 | **学习成本** + **费用成本**，且都是**一次性沉没**（每多一个工具就多一份） | **取材成本**（低，AI 读码/抽取）+ **维护成本**（集中在自己一处） |
| 能力边界 | 被工具的能力边界框死（工具不支持就只能等/换） | 边界由**自己能改多少**决定 —— 因为是自己的代码 |
| 组合方式 | 工具间靠"人肉搬运"（导出→导入→再导出） | 人机协同**串成一条流水线**，接口由我们定义 |
| 失败模式 | 工具不合用 → 整个方案推倒 | 某一段不合用 → **换掉那一段** |

**为什么现在才可行**：用户点出的前提是「**AI 编程能力已经足够强**」。
具体到本方案，它体现为这三件事都变便宜了：

1. **读懂陌生仓库** —— 本轮就是实例：在没有文档的情况下，靠读码定位到
   `projectPersistence.ts:785`（字体被重置）、`parser.ts:44-70`（中文并词）、
   `useProjectSaveActions.ts:7`（1 秒自动保存）等关键点。
2. **重写而不是复制** —— 本轮把 `rlex` 的 `.recordly` 契约**独立重实现**，而不是抄它的代码。
3. **快速验证** —— 本轮手写项目 → 真机出片，一次跑通（`06`§2）。

### 11.2 C-4 对本方案的三条推论

| # | 推论 | 在本方案里的体现 |
|:--:|:---|:---|
| **D-1** | **不必重造已经做好的整段** | `rlc` **不做渲染**（ADR-02）；渲染交给 `rlex` + Recordly。这就是"按需"——只取"编排"这一段 |
| **D-2** | **该自己写的就自己写，不迁就现成工具** | 字幕模板层、交接锁、项目结构 —— 现成工具都没有，且它们的边界框不住我们的需求，所以自己写（ADR-03/04） |
| **D-3** | **取材必须合法合规** | **这是 C-4 里唯一的硬门**。见 §11.3–11.5 |

> ⚠️ **D-3 不是客套话。** 本方案原先把 **PyMuPDF (`fitz`)** 列为 PDF 转图的首选，
> 而本轮实测确认它是 **AGPL-3.0**；而家族工具仓（如 `recordly-export-master`）是 **MIT**。
> 把 AGPL 依赖放进 MIT 仓**是许可证冲突**。这个错误正是因为**先看了"能不能用"，后看了"能不能取"**。
> 修正见 §11.5。

### 11.3 三类"取材"与各自的合规边界

**取材不是只有"抄代码"一种。** 按风险从低到高：

| # | 取材方式 | 是什么 | 合规要求 | 本方案实例 |
|:--:|:---|:---|:---|:---|
| **T-1** | **接口契约** | 字段名、环境变量名、文件格式、报告命名 | ✅ **最安全**。事实性接口不受版权保护；但仍应**独立重实现**并注明来源 | `.recordly` 的 `version:2` / `autoCaptionSettings` 字段名 / `RECORDLY_SMOKE_EXPORT*` / `<out>.mp4.report.json` |
| **T-2** | **外部工具/程序** | 以**独立进程**调用别人装好的程序 | ✅ 通常安全（聚合而非派生）。只需遵守其**分发条款**，不把它的代码并进自己仓 | `rlex`、`ffmpeg`、`pandoc`、`Recordly` 本体、`subgen` |
| **T-3** | **代码片段/库** | 把代码**拷进自己仓**，或作为**库依赖** | ⚠️ **风险最高**。取决于对方许可证：宽松(MIT/BSD/Apache)可并入；**强著佐权(AGPL/GPL)会传染** | 见 §11.4 |

**判据一句话**：

> **能走 T-1 就不走 T-3；能走 T-2 就不走 T-3。**
> 只有当"这段逻辑必须由我们持有、且没有宽松许可证的实现"时，才考虑 T-3，
> 且此时**要么接受许可证传染，要么自己重写**。

### 11.4 许可证台账（本轮实测）

> 数据来源：`Recordly/LICENSE.md` 头部、本机 `importlib.metadata`、
> [pypdfium2 PyPI 元数据](https://pypi.org/pypi/pypdfium2/json)。
> **未实测的条目标"待核"，不许当结论用。**

| 组件 | 许可证 | 能并入 MIT 仓？（T-3） | 备注 |
|:---|:---|:---:|:---|
| **Recordly** | **AGPL-3.0** | ❌ **不可并入** | `LICENSE.md` 首行即 AGPL。**但可走 T-1（接口契约）与 T-2（外部运行体）** |
| **PyMuPDF (`fitz`)** | **AGPL-3.0**（双许可，另一支为 Artifex 商业） | ❌ **不可并入**（除非本仓也 AGPL 或购买商业许可） | 实测："Dual Licensed - GNU AFFERO GPL 3.0 or Artifex Commercial License" |
| **pypdfium2** | **BSD-3-Clause, Apache-2.0** | ✅ **可并入** | 实测 PyPI 元数据；底层 PDFium 亦为宽松许可。**推荐作为 PDF 转图的首选** |
| **Pillow** | HPND（宽松，MIT 同类） | ✅ 可并入 | 实测 `importlib.metadata` |
| **python-docx** | MIT | ✅ 可并入 | 实测 |
| **python-pptx** | MIT | ✅ 可并入 | 实测 |
| **Typer** | MIT | ✅ 可并入 | 家族四仓既有依赖，沿用（**【待核】**：未逐字读 LICENSE 文件） |
| **`rlex`（recordly-export-master）** | MIT | ✅ 可并入 | 其 README 明确"本仓未包含 Recordly 源码，仅按公开契约独立重实现" |
| **whisper.cpp** | MIT | ✅ 可并入 | **【待核】** |
| **ffmpeg** | LGPL/GPL（视构建） | ⚠️ **只走 T-2**（独立进程调用），不静态链接 | 家族既有实践 |
| **pandoc** | GPL-2.0+ | ⚠️ **只走 T-2** | 独立进程调用 |

**家族既有围栏（沿用，并上升为通则）** —— 摘自 `recordly-export-master/AGENTS.md:77-84`：

> **可以**复用公开接口契约（`.recordly` 字段名、`RECORDLY_SMOKE_EXPORT*` 环境变量名、
> `<输出>.mp4.report.json` 命名）。
> **不可以**把 Recordly 源码逐段复制进本仓（AGPL 传染）。

### 11.5 ⚠ 对技术选型的直接影响（一处修正）

本方案原先在 `02-方案` §3 把 **PyMuPDF (`fitz`)** 列为"PDF → 逐页 PNG"的首选，
理由是**【实测】本机已装、可用**。但这**只回答了"能不能用"，没回答"能不能取"**。

| 项 | 原方案 | 修正后 |
|:---|:---|:---|
| PDF 转图首选 | PyMuPDF (`fitz`) | **pypdfium2**（BSD-3-Clause / Apache-2.0） |
| 理由 | 本机已装，一步到位 | **许可证与 MIT 仓兼容**；且同为一步到位的 PDF 渲染 |
| 代价 | —— | 本机**未装**（实测 `-- pypdfium2`），需加依赖；API 与 `fitz` 不同，需重写这一层（工作量小） |
| 兜底 | —— | 若坚持用 `fitz`，则**必须**让 `rlc` 整体改为 **AGPL-3.0**，或改为**独立进程**调用外部 PDF 工具（T-2） |

> **这条修正本身就是 C-4 的示范**：取材时**先查许可证，再查能力**。
> 已同步到 `02-方案` §3 与 `03-决策_ADR.md` ADR-07。

### 11.6 取材判据（决策清单）

面对一个"要做的能力"，按顺序问：

| # | 问题 | 若是 | 若否 |
|:--:|:---|:---|:---|
| 1 | 别人已经做成**独立可调用的工具**了吗？ | 走 **T-2**，只调进程、不并代码 | 下一步 |
| 2 | 只需要它的**接口/格式**吗？ | 走 **T-1**，独立重实现并注明来源 | 下一步 |
| 3 | 有一段**宽松许可**的实现可复用吗？ | 走 **T-3**，并**保留其许可证与出处声明** | 下一步 |
| 4 | 只有**强著佐权**实现吗？ | **自己重写**，或**改造本仓许可证**（需明确决策，不可默认） | 自己写 |
| 5 | 自己写要多久？ | 若明显超过"重写一段宽松实现"的成本，回到 3 再找替代 | 自己写 |

**反模式（明确禁止）**：

| # | 反模式 | 为什么 |
|:--:|:---|:---|
| A-1 | 从 AGPL 仓**拷代码**进 MIT 仓 | 许可证传染，且违反家族既有围栏 |
| A-2 | 依赖 AGPL 库而**不自查** | 同上；本方案的 PyMuPDF 就是一例 |
| A-3 | 把"能跑通"当作"可以用" | 漏掉许可证维度（本轮已犯过一次，见 §11.5） |
| A-4 | 为了省事引入**重型依赖**只用一个函数 | 与"按需"相反；应按最小必要取材 |
| A-5 | 抄了代码但**不留出处** | 即使许可证允许，也违反可追溯 |

### 11.7 风险

| # | 风险 | 缓解 |
|:--:|:---|:---|
| 1 | **许可证漂移**：上游改许可（如 PyMuPDF 曾收紧到 AGPL） | `doctor` 增加**依赖许可证自检**，把台账落成机器可查的清单 |
| 2 | **"按需取材"退化为"到处抄"** | 用 §11.6 的判据清单逐条过；每个 T-3 都要留出处声明 |
| 3 | 自建部分**维护成本被低估** | 只自建"必须由我们持有"的那一段（D-2）；其余一律 T-1/T-2 |
| 4 | 与上游**契约漂移**（`.recordly` 升版） | 字段映射表（`02` §6.1）+ `05-待确认清单` 跟踪 Recordly 版本 |
