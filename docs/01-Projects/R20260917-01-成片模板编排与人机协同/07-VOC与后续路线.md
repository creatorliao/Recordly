# 07 · VOC 与后续路线

> 本文记录**用户反馈（VOC）**与**后续路线**。
> 规则（沿用家族约定）：只把需求写在这里；用户原话有「因为」的留下原话，
> **没有说明理由的写「未说明理由」，禁止编造动机。**

---

## 1. 用户原话（逐字保真，不改写）

> **VOC-01｜2026-09-17**
> 「这样的话，我们就可以规划另外一个工具。假设我已经有了一个 MP4 和一些文档，然后我在 recordly 里面导入进去，手工选择调整模板，然后他帮我导出，在这个方向上是否可以实现？希望这是一个相对独立的工具，或者 Recordly 给我提供相关的 API 或 CLI 来实现同等的功能这个部分能不能实现？请你帮我调查研究并文档化，在项目目录的 docs目录下按照规范和要求创建一个主题文件夹，把我的需求、你的调查研究分析结果以及最终的解决方案放进去，至少输出3份文档并且按照场景对这个方案进行走查，确保不会有问题，但是不用马上修改代码」

> **VOC-02｜2026-09-17（补充，同轮内）**
> 「我希望实现的目标是AI可以全自动跑完，但是呢，人有些时候进去调整一下字幕，调整一下参数，」

> **VOC-03｜2026-09-17（补充，同轮内）**
> 「可以有更灵活的人机协同模式，不一定要框定在原来的窗口上面。如果原来的窗口要展示出来，我希望它是更漂亮的、更合适的，更符合我们现有的工作流。我们现在都已经人机协同了，原来那种方式太偏向于人工了。」

> **VOC-04｜2026-09-17（补充，同轮内）**
> 「请你帮我把这些信息收集、整合，完善到刚才的需求里，并完善刚才的解决方案和分析报告。」

> **VOC-05｜2026-09-17（第三轮补充）**
> 「我继续补充，就是我们以往要学习多个工具的时候，学习成本太高了条件也不太具备，因为每一个工具有自己的成本：学习成本和真真正正的费用成本。但是，如果我们现在 AI 编程能力已经足够强了之后，我们可以从开源社区按照合法合规的方式，从仓库中抽取对应的某一部分代码，整合到我们自己的项目里面。我们按需取材、按需构建，然后人机协同把它串起来，形成新的工作流程。这是我们跟以往不一样的地方。」

> **VOC-06｜2026-09-17（同轮指示）**
> 「请帮我把上述内容也添加到刚才那份需求文档里。」

## 3. 对上游的请求（新）

> 以下请求来自本轮调研发现的**能力缺口**，不是用户直接提出的。
> 每条都带证据，便于作为 issue/PR 提交。

### 3.1 致 Recordly（`webadderallorg/Recordly`）

| # | 请求 | 证据 | 价值 |
|:--:|:---|:---|:---|
| **U-01** | 修 `fontFamily` 被强制重置 + 默认字体栈补 CJK | `projectPersistence.ts:785` 无条件 `getDefaultCaptionFontFamily()`；默认栈 `types.ts:450-452` 全是拉丁字体。**实测确认是 13 个字幕字段里唯一被强制的**（`06`§3） | 解锁字幕字体自定义。**改动量：一行 + 一个字体栈** |
| **U-02** | 提供 `--open-project <path>` 启动参数 | 全仓无 argv 解析；`open-project-file-at-path` 仅应用内可达（`04` §7） | 让外部工具能"布景打开"，S3 面从半自动升为全自动（ADR-10） |
| **U-03** | 字幕布局**按时间窗口裁剪**，去掉每帧全量重算 | `modernFrameRenderer.ts:1781` → `buildActiveCaptionLayout` → `flattenCaptionWords(全部 cues)`，且 `isWithinCaptionCoverage` 每帧 `[...cues].sort()`（`04` §5.1） | 把 O(条数×帧数)=O(时长²) 打成 O(帧数)。30 分钟片可省约 5.5 分钟（`06`§5.5） |
| **U-04** | 统一 `enabled` 在两条导出路径的语义 | `captionRenderer.ts:26` 看 `enabled`，`modernFrameRenderer.ts:1617` 不看（`04` §4.2） | 消除"关字幕静默失效"（走查 P-13） |
| **U-05** | 提供"打开时定位到指定面板"的手段 | 面板激活是应用内部状态（`setActiveEffectSection`），无外部入口 | 满足 S3-3 |
| **U-06** | 字幕支持水平位置（X / 对齐） | `AutoCaptionSettings` 无 X 字段；导出硬 `centerX = width/2` | 位置可调 |

> **建议优先级**：U-01（一行，收益最大）→ U-03（长视频刚需）→ U-04（消除静默 bug）→ 其余。

## 4. 后续路线

### 4.1 近期（与 `02-方案` §8 三期对应）

| 期 | 主题 | 关键交付 | 卡在哪 |
|:--:|:---|:---|:---|
| **一期** | 打通链路（MVP） | `init`/`import-captions`/`apply`/`export`/`verify`；项目结构；5 个内置模板 | 无（机制已全部实测验证） |
| **二期** | 人机协同 | 交接锁 + 指纹校验 + 留痕；`pull` 差异报告；`style.toml` + `review --fast`；`relocate` | 无（但 S3 只能到"半自动"，见 ADR-10） |
| **三期** | 内容文档与规模化 | `import-doc --pdf`（inline/overlay/text）+ `[[content.pages]]`；`--from` 继承；`review --render` | Q3（大 JSON 压测） |

### 4.2 中期（依赖上游）

| # | 事项 | 依赖 |
|:--:|:---|:---|
| M-01 | `rlc open` 升级为真正的"布景打开" | U-02 被采纳 |
| M-02 | S3-3「打开即定位字幕区」达成 | U-05 被采纳 |
| M-03 | 字体模板真正生效（清秀中文字体） | U-01 被采纳 |
| M-04 | 长视频不再退化 | U-03 被采纳 |
| M-05 | `rlex` 直接吃 SRT | R-01 被采纳 |

### 4.3 远期（本轮明确不做，见 ADR-09）

| # | 事项 | 为什么不做 / 何时再看 |
|:--:|:---|:---|
| L-01 | 逐字动画（剪映同款） | 需先合并 Recordly 的预览/导出双渲染路径，且会击穿光栅缓存（`04` §4.1）。路径清晰但成本高 |
| L-02 | 字幕水平位置 | 需改 Recordly 源码 → 随 U-06 一起提 |
| L-03 | 批量出片（一套模板 × N 个片子） | 需要先把一期的项目结构稳定下来 |
| L-04 | 与 `subtitle-burn` 的能力合并 | 两条链路目前分工清晰（`01` §7），合并会失去"任意 MP4"的通用性 |
| L-05 | 自研渲染器 | 永不（ADR-09） |
| L-06 | GIF 无头导出 | Recordly 通道写死 `format:"mp4"` |
