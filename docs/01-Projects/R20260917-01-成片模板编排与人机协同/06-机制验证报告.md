## 2. 实验一：手写项目灌字幕 → 真机出片

**这是本轮最关键的一次验证。** 它同时证实了"AI 能写项目"和"字幕真会被渲染"两件事。

### 2.1 素材

| 项 | 值 |
|:---|:---|
| 输入视频 | `recordly-export-master/samples/input/demo-clip.mp4`（591,035 B，960×540，4.02s） |
| 预设 | `course-light` |
| 工作目录 | `D:\code\_scratch\p10-caption-test\`（**仓外**，不污染 Recordly） |

### 2.2 生成项目

```
$ rlex project new --video <demo-clip.mp4> --preset course-light --out t.recordly
[OK] ok 已生成项目：D:\code\_scratch\p10-caption-test\t.recordly
[OK] video-exists: 素材存在：...\demo-clip.mp4
```

### 2.3 手写注入字幕（模拟 AI 编排层）

用 Python 直接改 JSON（因为 CLI **不支持**数组字段，见 §7）：

```python
e["autoCaptions"] = [
    {"id": "c1", "startMs": 200,  "endMs": 2000, "text": "第一句字幕"},
    {"id": "c2", "startMs": 2000, "endMs": 3800, "text": "第二句字幕"},
]
s = e["autoCaptionSettings"]
s["enabled"] = True
s["fontSize"] = 48
s["bottomOffset"] = 10
s["maxRows"] = 1
s["animationStyle"] = "none"
s["textColor"] = "#FFFFFF"
s["backgroundOpacity"] = 0.0        # ← 纯白字、无黑底框
s["fontFamily"] = '"Microsoft YaHei", sans-serif'
```

校验（注意 `fontFamily` 的警告，正是 §3 要确认的那条）：


## 3. 实验二：字段往返保真度（AI → 人 → AI）

### 3.1 方法

直接把 `normalizeProjectEditor` 当纯函数调用，喂一个**所有字幕字段都设成非默认值**的输入，
看哪些活着出来。这正是 Recordly **加载任何项目时必经的那一步**（含无头导出）。

```ts
const out = normalizeProjectEditor({
  autoCaptionSettings: {
    enabled: true, timelineQuickAdd: false, language: "zh",
    fontFamily: '"SimSun", serif',        // ← 故意用非默认值
    fontSize: 48, bottomOffset: 12, maxWidth: 88, maxRows: 3,
    animationStyle: "pop", boxRadius: 3,
    textColor: "#FF0000", inactiveTextColor: "#00FF00", backgroundOpacity: 0.11,
  },
  autoCaptions: [{ id: "c1", startMs: 100, endMs: 900, text: "保留吗",
                   words: [{ text: "保留吗", startMs: 100, endMs: 900, leadingSpace: true }] }],
});
```

### 3.2 原始输出

```
PROBE settings:
  kept    enabled: true -> true
  kept    timelineQuickAdd: false -> false
  kept    language: "zh" -> "zh"
  FORCED  fontFamily: "\"SimSun\", serif" -> "\"SF Pro Text\", \"SF Pro Display\", \"Helvetica Neue\", sans-serif"
  kept    fontSize: 48 -> 48
  kept    bottomOffset: 12 -> 12
  kept    maxWidth: 88 -> 88
  kept    maxRows: 3 -> 3
  kept    animationStyle: "pop" -> "pop"
  kept    boxRadius: 3 -> 3
  kept    textColor: "#FF0000" -> "#FF0000"
  kept    inactiveTextColor: "#00FF00" -> "#00FF00"
  kept    backgroundOpacity: 0.11 -> 0.11
  DROPPED __unknownProbe: "keepme" -> undefined
PROBE cues: count=1 first={"id":"c1","startMs":100,"endMs":900,"text":"保留吗",
  "words":[{"text":"保留吗","startMs":100,"endMs":900,"leadingSpace":true}]}
```

### 3.3 结论

| 结果 | 数量 | 字段 |
|:---|:---:|:---|
| **保留（kept）** | **12** | enabled, timelineQuickAdd, language, fontSize, bottomOffset, maxWidth, maxRows, animationStyle, boxRadius, textColor, inactiveTextColor, backgroundOpacity |
| **被强制（FORCED）** | **1** | **fontFamily** |
| **被丢弃（DROPPED）** | 1（探针字段，属正常卫生） | `__unknownProbe` |
| cue 及其 `words[]` | 完整保留 | —— |

> ### ✅⚠ 结论
> **13 个字幕设置里 12 个能安全往返，唯一被毁的是 `fontFamily`。**
>
> 这是个**好消息**：人机协同的交接机制**今天就有 92% 可用**，
> 拦路的只有一行代码（`projectPersistence.ts:785`）。
>
> ❌ **坏消息**：`fontFamily` 不是"要小心处理"，而是**原理上绕不过去** ——
> 渲染读的是归一化**之后**的值（`modernFrameRenderer.ts:1638`），
> 所以往文件里塞值没有任何用。详见 `03-决策_ADR.md` ADR-05。

> ⚠️ **本实验只覆盖字幕字段。** 全量审计显示还有 4 组字段被强制
> （`zoomSmoothness`、`cursorMotionBlur`、`exportPipelineModel`、`zoomMotionBlurTuning.*`），
> 以及 9 个光标运动字段会**塌缩**到预设。详见 `04` §2.5.3。

## 4. 实验三：导出性能基线

### 4.1 两份真实报告（不是桩，是真跑）

两份都通过 `RECORDLY_SMOKE_EXPORT=1` 拉起 `D:\code\Recordly` 的 dev 运行体完成。
run.log 首行证据：

```

# cwd=D:\code\Recordly
# env RECORDLY_SMOKE_EXPORT=1
[smoke-export] Starting editor smoke export for <项目>
```

| 指标 | 报告 A（`case-01`，含 2 缩放区+背景+内边距） | 报告 B（`SA-real-export`，最简） | 本次（§2，含字幕） |
|:---|:---:|:---:|:---:|
| 帧数 | 516 | 120 | 120 |
| 成片时长 | 17.183 s | 4.000 s | 4.023 s |
| **导出总耗时** | **27,338 ms** | **2,789 ms** | **5,960 ms** |
| **倍速** | **1.59×** | **0.70×** | 1.48× |
| `renderFrameMs` 总计 | 2,831 | 201 | 638 |
| **单帧渲染均耗** | **5.487 ms** | **1.672 ms** | **5.316 ms** |
| `decodeLoopMs` | 23,069 | 1,745 | 3,029 |
| `encodeWaitMs` | 14,635（53%） | 624（22%） | 220 |
| `finalizationMs` | 3,478 | 582 | 747 |
| `metadataLoadMs` | 392 | 371 | **1,143** |
| `rendererInitMs` | 379 | 80 | **808** |
| 渲染后端 / 编码器 | webgpu / `avc1.640033` 硬件 | 同 | 同 |
| `autoCaptions` | `[]` | `[]` | **2 条** |

**固定开销**：`metadataLoad` + `rendererInit` ≈ **0.4–2.0 s**（本次偏高，疑为首次冷启动）。
**应用启动**：日志 `Editor Window: ready-to-show` 实测 **6.0 s / 8.4 s** —— 这部分**不计入**报告。

### 4.2 关键读数

1. **最简项目能跑到 0.70× 实时**（4 秒片 2.8 秒导完）→ 渲染不是瓶颈。
2. **复杂项目 1.59×** → 项目复杂度（缩放/背景/内边距）显著影响耗时。
3. **编码是主要瓶颈**：报告 A 有 53% 的时间在等编码器。
4. **一次应用启动只能导一次**（`useSmokeExportAutomation.ts` 单次驱动）→
   试穿 N 个模板要付 N 次启动成本。**这是 ADR-06 的直接依据。**

### 4.3 ⚠ 一个未解释的矛盾

两次 smoke 导出的日志里 `GPU feature status` 显示：

```
"2d_canvas":"disabled_software", "webgl":"disabled_off", "webgpu":"disabled_off",
"video_encode":"disabled_software", "gpu_compositing":"disabled_software"
```

但报告写的是 `renderBackend: webgpu` + `encoderName: avc1.640033/prefer-hardware/realtime`。

**两者矛盾，原因未查明。** 影响范围：§4 的**绝对数值**可能受此影响。
但 §5 的字幕布局成本是**纯 canvas 2D + JS**，与 GPU 无关，**不受影响**。

## 5. 实验四：字幕布局成本基准

### 5.1 方法

临时 vitest 基准（**跑完已删除**），语料对齐红杉真实 SRT 统计
（163 条 / 平均 11 字 / 最大 28 字 / 仅 2 条含空格），每场景跑 **9,420 帧**（= 314.047s × 30fps）。

测的是 `buildActiveCaptionLayout(...)` —— 即 `modernFrameRenderer` **每帧都调**的那个函数
（`modFrameRenderer.ts:1646-1652`），`measureText` 用计数器包装。

### 5.2 原始输出

```
BENCH text-only-163-cues   cues=163 frames=9420 measureText/frame=489.0  measureText/total=4606380  js_ms_per_frame=0.2297 js_total_ms=2163.5
BENCH word-timed-163x10    cues=163 frames=9420 measureText/frame=4888.4 measureText/total=46049130 js_ms_per_frame=0.6840 js_total_ms=6443.3
```

（vitest 报 `Test timed out in 5000ms` —— 那是默认超时，测量已完成，数据有效。）

### 5.3 中文落在便宜的那一档

**【已读源码确认】** `electron/ipc/captions/parser.ts:44-70` 的分词逻辑是
"**没有空白就往前一个词里拼**"。中文没有词间空格 → 整段并成一个词。

> **⇒ 中文的实际成本是 `text-only` 那一档（489 次/帧），不是 4,888 次/帧。约 9 倍差。**
>
> ⚠️ **推论**：将来若给中文加真正的分词，成本会跳约 9 倍 —— 这条要写进代码注释。

### 5.4 合并计算（对 314s 片）

| 场景 | 单帧 | ×9,421 帧 | 占导出总量 |
|:---|:---:|:---:|:---:|
| **文本型（中文实际）** | 0.230 + 489.0×1.726µs = **1.074 ms** | **≈10.1 s** | **2.0%–4.6%** |
| 词时间戳型 | 0.684 + 4,888.4×1.726µs = **9.122 ms** | ≈85.9 s | 17.2%–39.3% |

（百分比区间 = 按 0.70× 外推 219s ↔ 按 1.59× 外推 500s。**【外推】**）

### 5.5 规模风险（须预警）

成本 ∝ **总条数 × 总帧数 ∝ 时长²**（因为每帧都 `flattenCaptionWords(全部 cues)`，
无时间窗口、无记忆化，见 `04` §5.1）。

**【外推】** 中文口径：

| 片长 | 估算条数 | 字幕布局耗时 |
|:---|:---:|:---:|
| 5 分钟 | ~160 | ≈ 10 s |
| 10 分钟 | ~310 | ≈ 37 s |
| 30 分钟 | ~930 | ≈ 5.5 分钟 |
| 60 分钟 | ~1,860 | ≈ 22 分钟 |

> **工具侧修不了**（在 Recordly 里）。方案是在 `verify` 里给预警 + 记入 VOC（`07`）。

## 7. 实验六：CLI 能力边界

### 7.1 能改（样式标量）

```
$ rlex project patch t.recordly --set editor.autoCaptionSettings.fontSize=44 \
      --set editor.autoCaptionSettings.bottomOffset=8 \
      --set editor.autoCaptionSettings.animationStyle=pop --out t2.recordly
[OK] ok 已写入：3 处真实变更、0 处夹取、0 处未知字段
  editor.autoCaptionSettings.fontSize: 34 -> 44.0
  editor.autoCaptionSettings.bottomOffset: 4 -> 8.0
  editor.autoCaptionSettings.animationStyle: "fade" -> "pop"
```

### 7.2 不能改（数组 / 字体）

```
$ rlex project patch t.recordly --set 'editor.autoCaptions[0].text=hello'
[X] 未知字段 editor.autoCaptions[0].text: 字段不在 .recordly v2 白名单里

$ rlex project patch t.recordly --set 'editor.autoCaptions=[]'
[X] editor.autoCaptions 是数组字段，本版不支持用 --set 赋值

$ rlex project patch t.recordly --set 'editor.autoCaptionSettings.fontFamily=...'
[X] 未知字段 editor.autoCaptionSettings.fontFamily: 不在 .recordly v2 白名单里
```

### 7.3 预设里已带字幕设置

```
$ rlex preset show course-light   → autoCaptionSettings: enabled=true, fontSize=34,
                                     bottomOffset=4, maxRows=2, animationStyle=fade
$ rlex preset show vertical-9x16  → autoCaptionSettings: enabled=true, fontSize=40,
                                     bottomOffset=8, maxRows=2, animationStyle=pop
$ rlex preset show demo-dark / minimal → 不含字幕设置
```

> ### ✅ 结论
> - **样式标量可全自动驱动** → 需求 G-3/G-4 的自动化面成立
> - **字幕文本灌不进去** → 必须由工具**自己写 JSON**（§2.3 已验证可行）
> - **`fontFamily` 双向堵死** → ADR-05
