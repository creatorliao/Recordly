# 02 · 调查：窗口捕获裁切与系统弹出菜单

> 结论以本仓库源码 + Windows / WGC 公开限制为准。未改产品代码。

## 1. 一句话根因

**窗口模式只认「被选中的那一个 HWND」的外接矩形；Typora 的「主题」下拉是另一扇系统顶层窗（典型类名 `#32768`）。**  
本仓 Windows 主采集是 WGC（`wgc-capture.exe`）。即便窗口模式写成「先抓整屏再裁切」，采集面仍是 WGC，不是 DXGI 桌面复制。在 Windows 10 上，系统菜单往往**根本不会画进 WGC 纹理**；打开菜单也不一定触发新帧。本仓编码器还会在「没有新帧」时重复上一帧，菜单就更不会出现。

整块缺失（而不是只切掉伸出窗外的一截）说明：**不是单纯裁切溢出，而是菜单像素没进采集面。**

## 2. 用户点「窗口 · Typora」之后实际走哪条路

```
HUD 选源（SourceSelector / SourcePopover）
  desktopCapturer → id = window:<HWND>:…
        │
        ▼
useScreenRecorder
  shouldUseNativeWindowsCaptureForSource(window:…) = true
  isNativeWindowsCaptureAvailable()  →  Win10 19041+ 且有 wgc-capture.exe
        │
        ▼
IPC start native Windows capture
  resolveWindowsCaptureTarget() → { kind: "window", windowHandle }
        │
        ▼
wgc-capture.exe  JSON { windowHandle, fps, … }
        │
        ▼
WgcSession::initialize(HWND)
  CreateForMonitor(该窗所在显示器)     ← 不是 CreateForWindow
  每帧 DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)
  CopySubresourceRegion 只拷这块矩形
```

源码锚点：

| 环节 | 文件 | 做什么 |
|------|------|--------|
| 窗口源判定 | `electron/ipc/windowsCaptureSelection.ts` | `window:` → 解析 HWND |
| 启动 helper | `electron/ipc/register/recording.ts` | `config.windowHandle = …` |
| helper 路径 | `electron/ipc/paths/binaries.ts` | **只**解析 `wgc-capture.exe` |
| 窗口初始化 | `electron/native/wgc-capture/src/wgc_session.cpp` `initialize(HWND)` | `CreateForMonitor` + `initializeWindowCrop` |
| 每帧裁切 | 同文件 `updateWindowCropRect` / `onFrameArrived` | 只按**主窗** DWM 外接矩形拷纹理 |
| 无新帧补帧 | `electron/native/wgc-capture/src/mf_encoder.cpp` | 「WGC 静止时停帧，重复上一帧」 |
| 测试锁死 | `electron/ipc/recording/windows.test.ts` | **禁止**源码出现 `CreateForWindow(` |

FFmpeg `gdigrab` `hwnd=` 也会漏菜单，但 **Windows 金路径并不走它**：原生 WGC 失败就直接报错，没有自动退回 gdigrab。浏览器 `getDisplayMedia`（窗口表面）同样漏菜单，只在 WGC 不可用时才会落到这条。

树里另有 `electron/native/windows-capture/`（DXGI `DuplicateOutput` + 同样按主窗裁切）。**当前录制不调用它。** `scripts/build-windows-capture.mjs` 实际编的是 `wgc-capture`，名字是历史残留。

## 3. 为什么 Typora 这张下拉一定是「另一扇窗」

截图是 Windows **原生菜单栏**（带 `(F)/(T)` 助记符），不是页面里的 HTML `<select>`。

Typora 是 Electron。`Menu.setApplicationMenu()` 在 Windows 上走 Win32 `HMENU`：

| 属性 | 主窗（被录的 HWND） | 「主题」下拉 |
|------|---------------------|-------------|
| 典型类名 | `Chrome_WidgetWin_1` 等 | `#32768`（系统菜单） |
| 样式 | 普通顶层窗 | `WS_POPUP`，常带阴影 / layered |
| Owner | — | 主窗 |
| 是否在 `DWMWA_EXTENDED_FRAME_BOUNDS(主窗)` 里 | 是 | **几何上常常落在主窗矩形内，但窗口身份不是主窗** |

微软对「按窗口建 GraphicsCaptureItem」的公开结论：采集的是该窗内容，**不含 owned 窗**（菜单、对话框、tooltip）。见 [WindowsAppSDK #833](https://github.com/microsoft/WindowsAppSDK/issues/833)。评论写明：这些菜单**不是子窗**，扩「子树」也救不了。

Win11 24H2 才有 `GraphicsCaptureSession.IncludeSecondaryWindows`。文档写：并入与主窗相交的 `WS_POPUP` / `WS_EX_TOOLWINDOW`，且**裁在主窗范围内**。第三方实测：**tooltip/popup 可能出现，系统 context menu 仍经常不出现**。本机是 **Windows 10 19044，没有这个 API**。

## 4. 「已经 CreateForMonitor 了，为什么还会漏？」

本仓故意不用 `CreateForWindow`（避免窗口改尺寸把编码器撑出黑边），改成整屏 WGC + 裁切。这能躲开「只抓一扇 HWND」的一部分问题，但**过不了 WGC 自己的菜单限制**：

1. **WGC ≠ DXGI。** `CreateForMonitor` 走 DWM 可采集视觉树，不是桌面复制。Windows 10 上 `#32768` 系统菜单常画在单独的 DWM overlay 里：你看得见，WGC 纹理里没有。
2. **脏区。** 菜单若不算进 capture item，打开菜单不会让主窗/显示器 item 变脏，`FrameArrived` 不来（或来的还是旧画面）。
3. **重复上一帧。** `mf_encoder.cpp` 明确按「WGC 静止停帧」补时间轴。没有带菜单的新帧 → 成片继续播打开菜单之前的画面。
4. **裁切是第二刀。** 即便将来纹理里有菜单，`updateWindowCropRect` 仍只取主窗外接矩形。菜单贴边、投影伸出、或落到主窗外面，仍会被切掉。用户这次是**整块没有**，所以第一刀（像素没进面）是主因，第二刀是同类场景的加重项。

对照：OBS 社区对「窗口采集看不到菜单」的标准回答一直是——改用显示器采集；近期才在 Win11 上尝试 `IncludeSecondaryWindows`。这与本仓症状一致。

## 5. 和相邻问题的边界

| 主题 | 夹 | 是否同一根因 |
|------|----|----------------|
| 成片卡顿、鼠标跟不上 | `R20260906-09` | **否。** 那是时序/帧率；本条是菜单窗不在采集面 |
| HUD 不进成片 | `R20260906-02/17` `18` | **否。** 那是 `setContentProtection` 故意排除 Recordly 自己的条 |
| 使用指南「优先选窗口」 | `R20260906-01/02` | **相关。** 这条建议正好踩中本缺陷 |

改窗口采集后端会碰到 09 的卡顿/光标链路，**不能当成同一张工单一起改**，但动手前必须两边都回归。
