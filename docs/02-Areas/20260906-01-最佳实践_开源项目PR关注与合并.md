# 最佳实践_开源项目PR关注与合并

> 用途：以后拿着这份稿，快速审视一个开源项目的社区 PR / Issue，**只把对得上你工作流、习惯和目标的部分**接到自己的分支上。  
> 每个 PR 的打分与「极高分」筛选工具：**[附录 A · PR 平衡矩阵](#附录-a--pr-平衡矩阵)**。  
> 不是「帮上游当维护者」，也不是「PR 多就多合」。  
> 本篇从 Recordly 这一轮（角色钉死 → 历史提示当诉求账 → 出方案 → **换一个智能体全面审查** → 再拍板）里抽出来，可复用到别的仓库。

---

## 〇、先想清楚：你是谁、拿它干什么、为什么要改

合并 PR 之前，真正决定「看什么、合什么」的不是星星数，而是下面三问。**先写下来，再碰 GitHub。** 历史提示词里反复出现的，就是这三问——漏了这一步，后面分级、打分都会漂。

### 0.1 角色：你是谁

用一句能上名片的话，不要用「用户」「开发者」这种空词。

| 问自己 | 写清楚的样子（Recordly 例） |
|--------|------------------------------|
| 我日常在干什么？ | 培训师，录软件操作给学员看 |
| 成功长什么样？ | 一节课能从「点录制」走到「交出能播的视频」 |
| 失败长什么样？ | 点不动被录软件、讲解没声、导不出、剪到崩溃 |

角色会过滤 80% 的 PR：摄像头虚化、Linux Wayland、九语种 i18n，对「培训师录 Windows 软件」通常不是你的题。

### 0.2 用途：拿它干什么（金路径）

画出你**必须走通的一条路**，用动词连起来，能复述给别人。

```
启动录制 → 停止 → 编辑 → 导出视频
```

这条路就是「核心工作流程」。任何 PR 先问：它是在**保这条路**、**让这条路更快**，还是在旁边新修一条景区小道？

同时写下你为什么选这个开源项目、为什么要改它（而不是换软件或从零写）：

| 问自己 | 想清楚再往下 |
|--------|--------------|
| 它已经替我做了哪一段？ | 录屏+剪辑一体，省掉再丢到剪辑软件 |
| 缺的是哪一段？ | Windows 上点得动、麦不断、项目能存、中文对、本机能装 |
| 改它的理由够不够硬？ | 工作流卡在金路径上，不是「看起来酷」 |

**为什么要改**写不出来，就不要开始合 PR——那是在给上游打工，不是在改造自己的工具。

### 0.3 目标：给智能体（和自己）一套可衡量的尺子

目标要完整、可判断「做没做到」，不要停在形容词。Recordly 用的是四条锚（可换成你的项目名）：

| 编号 | 目标 | 衡量（必须能打勾） |
|------|------|-------------------|
| G1 | 金路径可用 | 录→停→编→导无阻断 |
| G2 | 减轻你最烦的那段劳动 | 例如录完到导出 ≤15 分钟 |
| G3 | 你点名的能力 | 例如字幕 / 讲解声 |
| G4 | 体验好且不过度设计 | 少而稳；改动过大就降级或拒绝 |

后面所有「综合考量」都钉在这把尺子上：**落不进任何一条，就不合。**

范围也要一起钉死（后说的覆盖先说的）：平台、语言、工作分支、你是不是上游维护者。没钉范围，Linux 修复会混进 P0，方案会自己打架。

### 0.4 这一步怎么落到习惯上

1. 打开新仓库的第一天，先写「角色 / 金路径 / 为什么改 / G1–G4 / 范围」——可写在 `AGENTS.md` 或项目夹 `00-诉求`。
2. 用你自己的话多说几轮（历史提示就是这个）：智能体容易漏，你用短句反复钉，比一次写一篇 PRD 更稳。
3. **先有目标，再拉 PR 列表。** 反了就会被社区热度牵着走。

## 一、应该关注哪些内容

关注的是「对你金路径有没有用」，不是「PR 新不新、作者厉不厉害」。

### 1.1 必看（每一次开源改造都看）

| 关注对象 | 看什么 | 为什么 |
|----------|--------|--------|
| **金路径上的断裂** | 点不动、没声音、存不了、导不出、编辑器卡死 | 没有这些，改造没有意义 |
| **你点名的能力** | 字幕、配音、省剪辑、按键显示……以你的 G 为准 | 这是你改它的理由 |
| **默认体验会不会被换掉** | 「有了 A 就没了 B」：追加录制替换独立文件、CUDA 替换 CPU 导出 | 老习惯被偷换，比缺功能更伤 |
| **体量与质量** | 行数、是否动核心、CI、维护者打的 Slop / AI 垃圾标 | 大而危的合进来，回退成本高于收益 |
| **和你范围重叠的部分** | 你的 OS、你的语言、你的分发方式（安装包、进程身份） | 范围外的「好 PR」也是噪音 |
| **重复与依赖** | 同一痛点多个 PR；B 依赖 A；扩展系统已删还在修扩展 | 合错一个会叠冲突或合了白合 |
| **操作方式变不变** | 新入口、新默认、启动流程变了 | 变了就要准备手册，并默认「可选」 |

### 1.2 值得扫一眼、默认不深挖

- 文档收口、失效 marketplace、纯文案：风险低，但只有碰到你真实会读的文档才值得搬。
- 非你平台的修复：记一行「将来若支持 X 再看」，不要进执行队列。
- 冷门增强（headless、远程摄像头、巨型美颜）：方向可以记，本轮不当事做。

### 1.3 明确可以不关注

- 帮上游关别人的 PR、在官方 `main` 上当维护者（除非你真的是）。
- 为「完整支持所有发行版 / 所有语言」去补课。
- 星星、热评、和你金路径无关的架构重构。

## 二、怎么关注，关注哪一些部分

### 2.1 怎么关注（动作，不是心态）

按这条流水线走，不要从「打开一个好看的 PR 就开始 cherry-pick」。

```
钉角色与目标（§〇）
  → 拉 PR / Issue 事实（标题、labels、行数、CI、平台）
  → 按金路径归类（保命 / 提效 / 点名能力 / 范围外 / 过大）
  → 相近 PR 聚成集群，先谈共存再谈二选一
  → 三维打分 + 六问
  → 写出一份「综合方案」（队列、暂缓、拒绝都留痕）
  → 换一个智能体（或另一端）审查方案
  → 用历史提示对账，改掉自相矛盾
  → 你确认
  → 本地分支移植（不是代合上游）
  → 验证 + 留痕；改了操作就改手册
```

**关注时盯的部分（打开每个候选 PR 时看这些，别通读小说）：**

1. **标题与第一段**：它声称修的用户症状，是不是你金路径上的。
2. **平台 / 语言**：文件路径、`#ifdef`、workflow 名，立刻判断是否出范围。
3. **diff 规模**：≤50 / ≤200 / ≤500 / >500 / >2000。超过阈值先降级，不要被描述打动。
4. **默认行为**：有没有改「每次新文件 / 要点一下才开始 / 降噪默认开」。
5. **互斥面**：是否替换导出引擎、替换捕获后端、删除 fallback。
6. **标签**：`Slop`、`DIRTY`、`UNSTABLE`——质量与能否干净 cherry-pick。
7. **和已有集群的关系**：是主方案、补丁，还是重复件。

用 `gh` 拉事实，结论写进项目夹，不凭记忆。

### 2.2 关注哪一些部分（按层）

| 层 | 部分 | 练的时候怎么看 |
|----|------|----------------|
| 症状层 | Issue 红榜：崩溃、无声、点不了 | 先看重复出现的痛，再找对应 PR |
| 能力层 | 开源已经有、正好补你 G2/G3 的 | 按键叠加、区域录制——有价值也要看体量 |
| 工程层 | 行数、模块、测试、CI | 决定 AI 做还是你手工 |
| 体验层 | 默认、入口、手册 | 决定「可选并存」还是「拒」 |
| 范围层 | OS、语言、分发/拦截 | 决定进不进队列 |

## 三、优先关注哪一部分（不跳级）

永远按这个顺序，**不允许**因为某个 PR「很酷」插队。

```
1. 低垂果实     风险低 + 效果好 + 修复简单（文案、精度、几行穿透恢复）
2. 金路径断裂   点得动 / 听得清 / 存得了 / 编得动 / 导得出
3. 你点名的能力 字幕、省剪辑……体量过大就暂缓，方向记下
4. 功能增强     最后，且默认可选
```

并列时的打破规则：

- 同一痛点多个 PR：取**覆盖症状最完整、体量可审**的当主方案，小补丁可以并入，重复件不采用（我们通常也不代关上游）。
- 真互斥（换引擎就丢掉旧引擎）：默认不采用，除非你书面接受失去 B。
- 表面互斥（追加录制 vs 独立文件）：优先**共存设计**——默认保持今天的行为，新能力另开入口。

## 四、练的时候：怎么想、想哪些、怎么做、做哪些

这一节是给「下一次对着新开源项目上手」用的。想和做分开，避免只想不动或只搬不想。

### 4.1 怎么想（思考顺序）

1. **我想成为谁、我要交什么作业？** 角色 + 金路径。
2. **这个软件已经替我做了什么、我为什么还要动刀？** 理由不硬就停。
3. **我的目标完整吗？** 缺衡量就补 G；缺范围就补平台/语言/分支。
4. **这个 PR 落在哪条 G 上？** 落不上就关页。
5. **合了对老的我有没有伤害？** 默认变了吗？会不会困惑？有没有奇怪副作用？
6. **我能不能小步拿下来？** 太大就记「将来以它为基重写」，不要硬吃。
7. **方案自己有没有打架？** 前面当 P0、后面当暂缓——以**后说的、范围更窄的**为准，并改文档。

### 4.2 想哪些（每次桌上只摊这些）

- 角色一句话、金路径一串动词、G1–G4、范围四至（平台/语言/分支/身份）。
- 一张集群表：主题 → 候选 PR → 主方案 / 并入 / 不采用 / 暂缓。
- 一张六问表（每个准备动手的 PR 一行）。
- 一张「暂不采用」表：理由 + 将来何时再看。
- 对开发者工作量的边界：AI 只碰小改；大改你自己点头再碰。

### 4.3 怎么做（操作）

| 步 | 做 | 产出 |
|----|----|------|
| 1 | 把角色/目标/范围写进 `AGENTS.md` 或 `00-诉求` | 尺子 |
| 2 | 导出**当前工作空间**的历史提示，当诉求账，不要靠聊天记忆 | 提示词时间线 |
| 3 | `gh pr list` / `gh issue list`，按金路径归类，不先写「建议立即合并 20 个」 | 调查底稿 |
| 4 | 打分 + 六问 + 冲突分级（真互斥 vs 可共存） | 分级与关联稿 |
| 5 | 写**一份**综合方案：队列、已做、不做、等确认 | 方案真源 |
| 6 | **换一个智能体**审查方案（见 §五） | 审查意见 → 改方案 |
| 7 | 等人确认；未确认不改产品代码 | 拍板记录 |
| 8 | 本地分支 cherry-pick / 手工移植，一个一个验 | 提交 + 留痕四要素 |
| 9 | 操作变了就改教程，写「原来怎样、现在怎样」 | 手册变更提示 |

### 4.4 做哪些（清单，可直接打勾）

**开场**

- [ ] 角色、用途、为什么改、G、范围，都写成字
- [ ] 说明：我们是改造自己的 fork/分支，不是官方维护者

**看 PR**

- [ ] 金路径断裂类已扫完
- [ ] 范围外（其他 OS/语种）已移出队列并留一行
- [ ] 相近 PR 已成集群，主方案已定
- [ ] 互斥项已标记，能共存的已写出默认+可选
- [ ] 低垂果实已单独置顶
- [ ] >500 行 / Slop / 动核心 已标「人工」或「暂缓」

**方案**

- [ ] 只有一份执行真源，旧稿标明「过程稿」
- [ ] 暂不采用的写了「将来何时再看」
- [ ] 历史提示里的诉求都能在方案里找到落点（含安装包、身份、教程——别只盯代码 PR）

**拍板与做**

- [ ] 换端审查过，矛盾已消
- [ ] 人已确认队列
- [ ] 动手时一个 PR 一验，测完再下一个
- [ ] 留痕四要素；手册该改的已改

## 五、用历史提示当诉求账；换智能体审查方案

这两条是这一轮里**特别值得留下的做法**，以后做别的开源项目也照做。

### 5.1 历史提示词：你的目标是「说出来的」，不是「事后猜的」

你在 PI / Cursor 里分段钉角色、金路径、三大诉求、Windows、语言、低垂果实、六问、等确认——这些比事后写的总结更真。

怎么用：

1. 只导出**当前工作空间**的提示（避免被别的仓污染）。
2. 去重压成约束（R1、R2…），**后说的覆盖先说的**（例如后来「Linux 不做」覆盖早先把 Linux 当 P0）。
3. 每条约束在方案里有落点；落不上就是方案漏了（安装包、Electron 身份就曾被漏）。
4. 方案和早期稿打架时，以提示词时间线为准，不要以「先写出来的那份分级表」为准。

智能体容易把「调查报告」当成目标。你要反过来：**提示词里的角色和目标是真源，PR 表只是材料。**

### 5.2 第三方智能体审查：出方案的人不要自己审自己

出了「出版方案」之后，换一端（例如方案是 PI 写的，就拿到 Cursor / 另一模型）做这些事：

| 审查问什么 | 好的结果 |
|------------|----------|
| 是否读全了历史提示、有没有漏诉求？ | 补上漏轨道（构建、教程、等确认） |
| 方案前后是否自相矛盾？ | 统一口径，旧稿降为底稿 |
| 是否还在用上游维护者心态？ | 改成本地移植，不代合不代关 |
| 每个待做项是否过六问、是否过范围？ | 踢掉 Linux/macOS、踢掉弱相关 |
| 打分和队列是否一致？ | 只留一份执行队列 |
| 暂缓/拒绝有没有留痕？ | 将来回看得着 |

规则：

- **审查方先综合提示词和诉求，再改决策**，不要只润色措辞。
- 审查意见写回方案真源，并给人确认，不要审查完直接改代码。
- 两端结论冲突时：回到角色和金路径，而不是回到「哪个模型更自信」。

这就是「综合考量」的落地：不是一个人一次性想完，而是 **目标（人）→ 材料（PR）→ 方案（一端）→ 对账审查（另一端）→ 人拍板**。

## 六、决策时的综合考量（可当口诀）

```
角色对不对 → 金路径在不在 → 落进哪条 G
    → 范围里不在 → 默认伤不伤老人
    → 能不能小步拿 → 和别的 PR 打架吗
    → 提示词有没有漏 → 换一端看过没有
    → 人点头了没有
```

六问（每一个准备合的 PR 都过，无一例外）：

1. 服务哪个目标？
2. 是否不过度设计？
3. 有无回归风险？
4. 用户真的需要吗（不是炫技）？
5. 会带来困惑吗？
6. 会有奇怪影响吗？

打分与筛选的完整工具见 **[附录 A · PR 平衡矩阵](#附录-a--pr-平衡矩阵)**（每个 PR 一张表）。口诀级公式：

```
S = 0.40×风险R + 0.35×目标贡献C + 0.25×效能E
```

低垂果实天然最前，不是因为它「不重要」，而是因为它能用最小代价先让尺子亮绿灯。

## 七、下一次换一个开源项目时的最短路径

1. 写角色、金路径、为什么改、G、范围（半页就够）。
2. 自己分支（不要在心里扮演官方 maintainer）。
3. 拉 PR/Issue，只按金路径分四堆：保命 / 提效 / 范围外 / 过大。
4. 出一页综合方案 + 暂缓表。
5. 导出本工作区历史提示，对账。
6. 换一个智能体审查，改方案。
7. 你确认后，从小到大移植，边验边留痕。
8. 变操作就改你自己的手册。

样例落点（本仓库这一轮）：`docs/01-Projects/R20260906-02-Recordly官方仓库PR与Issue调查分析/12-综合完善方案.md`。智能体执行细则见仓库根 `AGENTS.md` §九。

## 八、反模式（看到就停）

- 没写角色就开始「建议立即合并」。
- 把社区热度、Slop 以外的「看起来完整」当成你的目标。
- 一份文档说必合、另一份说暂缓，还不声明谁是真源。
- 用 `gh pr merge` 替上游关别人的单。
- 审查和起草用同一个上下文、同一套未对过的假设，然后直接改代码。
- 为了功能完整把 >2000 行 / 换引擎的 PR 吃进来。
- 忘了本机要能装、能过内部拦截——「合了 PR 但打不出能用的包」。
- 不过闸门、不填平衡矩阵，只凭印象说「这个分很高」。
- 用极高分让增强类 PR 插队，越过尚未修好的金路径断裂。

## 附录 A · PR 平衡矩阵

> 这是给**每一个候选 PR**用的完整工具：先过闸门，再打三维分，再看象限，最后用筛选机制抽出「极高分」优先考量。  
> 与正文 §三（优先级）、§四（怎么想怎么做）、§六（口诀）配套；智能体短表见 `AGENTS.md` §四 / §九。  
> **每一个准备进入方案队列的 PR 都填一行（或一张卡），不填就不排序、不建议合并。**

### A.1 评估分两层：闸门 ≠ 分数

| 层 | 作用 | 不过 / 分低时 |
|----|------|----------------|
| **闸门** | 决定「能不能进场」 | 直接淘汰或打回，**不算进优先池** |
| **平衡分** | 决定「进场后谁先被考量」 | 按 S 与象限排序，仍要服从「不跳级」 |

只拍分数、不过闸门，会出现「#794 若只看『导出变快』好像贡献很高」这种误判。只过闸门、不打分，会出现「保命的堆在一起，不知先摘哪颗低垂果实」。

---

### A.2 闸门（先筛掉，再打分）

四个闸门**全过**才进入打分。任一不过：记入「不采用 / 暂缓」，写理由。

| 闸 | 问 | 过 | 不过 |
|----|----|----|------|
| **范** | 在你的平台、语言、分支策略里吗？你是在本地移植而不是代合上游吗？ | 是 | 范围外，一行归档 |
| **标** | 能指出服务 G1–G4（或你的等价目标）中的至少一条吗？ | 能 | 落不进目标 |
| **六** | 六问全过吗？尤其④必要 ⑤不困惑 ⑥无怪影响 | 全过 | 拒 / 重设计 / 拆小 |
| **体** | 是否「>2000 行或巨型 Slop 或替换核心引擎」？ | **否**（不是这种） | 淘汰出优先池；人若要碰另开「手工」名单 |

六问打法见正文。闸门是是否题，不要打成 1–5 分混进 S。

---

### A.3 三个评分维度与打分方式

过闸后，每个 PR 打 **R / C / E**，各 1–5 分，**5 分最好**。必须对照量表，禁止「感觉还行打个 4」。

#### 维度 R · 风险（权重 40%）

问的是：**合进去有多安全**（分高 = 更安全，不是「越危险分越高」）。

| 分 | 何时打这个分 |
|----|----------------|
| 5 | ≤50 行，纯文案/配置/单文件，不碰录停编导核心 |
| 4 | ≤200 行，单模块，有测试或能看懂的干净 diff |
| 3 | ≤500 行，涉及核心但局部，CI 可解释 |
| 2 | >500 行，或动核心链路，或 DIRTY/UNSTABLE 且原因不明 |
| 1 | >2000 行，或标 Slop 且未重写，或无测试的高危替换 |

并列时就低不就高（有一项触到 2 的标准，整项就是 2）。

#### 维度 C · 目标贡献（权重 35%）

问的是：**对你已经写下的 G 贡献有多硬**。没有 G 表就先停，回去写 §〇。

| 分 | 何时打这个分 |
|----|----------------|
| 5 | 直接服务 G1（金路径能走）或你点名的 G3（如讲解声/字幕保命段） |
| 4 | 明显服务 G2（省剪辑）或 G4（体验），且角色用得上 |
| 3 | 间接服务（修了周边，金路径更顺一点） |
| 2 | 弱相关（4K 尺寸、播放头进位这类） |
| 1 | 与 G 无关，或只服务上游发版/其他角色 |

#### 维度 E · 效能（权重 25%）

问的是：**痛有多痛、受益面有多大**（站在你的角色，不是全人类）。

| 分 | 何时打这个分 |
|----|----------------|
| 5 | 高频卡点，不做就录不成课 / 走不成金路径 |
| 4 | 明显痛点，多数次使用都会碰到 |
| 3 | 特定场景（4K、VFR、偶发冻结） |
| 2 | 边际改善 |
| 1 | 几乎无感知，或冷门 |

#### 综合分

```
S = 0.40 × R + 0.35 × C + 0.25 × E
```

保留两位小数。**S 只用于过闸之后的排序**，不能用来「救回」没过闸的 PR。

| S | 含义（过闸后） |
|---|----------------|
| ≥ 4.00 | 高优先，进入极高分筛选（A.5） |
| 3.00–3.99 | 审阅后可进「后续队列」 |
| 2.00–2.99 | 按需，不主动 |
| < 2.00 | 过了闸但价值不够，不进方案队列 |

### A.4 平衡矩阵（象限）：看「贡献 × 安全」是否歪

把过闸的 PR 投到二维图上，避免「贡献极高但极危」和「极安全但无用」被同一个 S 糊过去。

```
                目标贡献 C →
           低(1–2)              高(4–5)
        ┌────────────────┬────────────────┐
  高    │  顺手 / 可忽略  │  ★ 优先考量     │
  风    │  安全但弱相关   │  低垂 + 金路径  │
  险    ├────────────────┼────────────────┤
  R     │  不碰           │  高价值高风险   │
  ↓     │  危且无用       │  人手工 / 拆小  │
  低    │                │  不进极高分池   │
        └────────────────┴────────────────┘
```

**怎么读象限（比单看 S 更稳）：**

| 象限 | 条件（经验划分） | 怎么对待 |
|------|------------------|----------|
| ★ 优先 | R≥4 且 C≥4 | 优先考量；再看 E 和是否低垂 |
| 高价值高风险 | C≥4 且 R≤2 | **不进极高分池**；记入手工名单或拆小后再打 |
| 顺手 | R≥4 且 C≤2 | 可选顺手，不得插队到金路径前面 |
| 不碰 | R≤2 且 C≤2 | 不采用 |

E 不单独占轴，用来在同一象限里打破并列：E 高者先。

**每个 PR 的平衡卡（复制填）：**

```
PR #____  标题：________
闸门：范□ 标□ 六□ 体□    （未全勾 → 停，不打分）
R=__  C=__  E=__  S=__
象限：优先 / 高价值高风险 / 顺手 / 不碰
低垂果实？风险低□ 效果好□ 修复简单□   （三勾才算）
默认行为改变？否 / 是 → 手册：____
集群：主题____  角色：主方案 / 并入 / 重复不采用
结论：极高优先 / 后续队列 / 手工 / 暂缓 / 不采用
一句话理由：________
```

**Recordly 例（帮助对齐手感，不是永恒标准）：**

| PR | R | C | E | S | 象限 | 结论 |
|----|---|---|---|---|------|------|
| #823 简中标签 | 5 | 4 | 3 | 4.15 | 优先偏顺手 | 低垂，已合 |
| #542 HUD 拖完恢复 | 5 | 4 | 3 | 4.15 | 优先 | 极高分池 |
| #803 HUD 穿透 | 3 | 5 | 5 | 4.20 | 优先（R 刚过线） | 极高分池，但须全量测 |

| #794 CUDA 导出 | 闸门「体」不过 | — | — | — | 不碰 | 不打分 |

### A.5 筛选机制：怎样抽出「分数极高」的 PR 优先考量

目标：每轮只拿出一小撮真正该先看的，而不是把 S≥4 的二十个 PR 都叫「优先」。

#### 第一步 · 进场

只保留：**四闸全过** 的 PR。  
同一主题集群只留 **1 个主方案**（可加「并入」的小补丁编号，不各算一条极高）。

#### 第二步 · 划优先池（高分）

同时满足才进**优先池**：

1. S ≥ 4.00  
2. 落在「★ 优先」象限，**或**（C≥5 且 R≥3）——金路径硬贡献、风险尚未掉到「高危」  
3. 不是「高价值高风险」象限（那些走人手工名单）

#### 第三步 · 再筛「极高分」（本轮优先考量）

优先池里再过一层，防止池子膨胀：

| 条件 | 作用 |
|------|------|
| **低垂三勾**（风险低 ∧ 效果好 ∧ 修复简单，通常 R≥4 且行数很小） | 无条件排在极高分**最前** |
| 其余优先池成员按 S 降序，S 相同看 C，再看 E，再看行数（小者先） | 排出「先考量谁」 |
| **本轮极高分名额默认最多 8 个**（含低垂） | 超出的留在优先池下一轮，不一次铺开 |
| **金路径尚未修完时，增强类即使 S 高也不得进入极高分前 8** | 不跳级；#655 这类停在「可选顺手」 |

「效果好」：E≥3 且角色用得上。  
「修复简单」：你或 AI 能在一个提交内讲清 diff，且不依赖未合的巨型前置。

#### 第四步 · 输出两张名单（写进方案真源）

```
极高分 · 本轮优先考量（按序）：
  1. …（低垂）
  2. …
手工 · 高价值高风险（不进极高分，等人点头）：
  …
未进池 · 过闸但 S<4 或象限为顺手：
  …
```

智能体只对「极高分」名单建议「确认后按序做」；对「手工」只建议记录，不自动开工。

#### 第五步 · 防作弊（筛选时禁止）

- 用把 C 打满 5、R 也虚高来把增强 PR 塞进极高分。
- 把没过闸的 PR 补一个 S「供参考」。
- 同一痛点三个 PR 都进极高分。
- 因为「社区很火」给 E 加分。
- 极高分名单不经换端审查、不经人确认就改代码。
